# Agent Platform · 0.6.0

Главный продуктовый ориентир — [манифест Fastkore Agent Platform](AGENT-PLATFORM-MARKETING.md), утверждённый владельцем 12 ноября 2026 года. Постановка задач и дальнейшая разработка опираются на эту концепцию.

**Agent Platform — единая корпоративная среда, в которой ИИ работает поверх данных и возможностей Fastkore и помогает сотрудникам выполнять их функции. Агент самостоятельно получает сведения и выполняет порученные действия через CLI и MCP от имени сотрудника, с соблюдением его прав и ролевой модели ERP.**

Из интерфейса агент получает идентификатор карточки либо контекст списка с фильтрами. Необходимые данные он добирает инструментами. CLI — основной канал работы на уровне клиентского приложения Fastkore. Агент выбирает CLI или MCP для каждого шага по доступным операциям и условиям задачи.

Проекты объединяют корпоративную документацию и результаты. Компания централизованно управляет промптами, тематикой запросов, доступом к инструментам и выдачей информации. Для закрытых источников отдельно задаются право агента использовать материал и состав результата, доступного сотруднику. Цель включает аналитику по обращениям, активности сотрудников, действиям и результатам.

Сценарии охватывают прайс-листы, заказы, счета, КП, производственные технологии, задолженность, бухгалтерские документы, закупки и мониторинг цен, работу с обращениями, звонками и письмами, подготовку ответов клиентам, напоминания и аналитику руководителя.

[Сценарии и принципы работы](AGENT-PLATFORM-OVERVIEW.md) · [План реализации](docs/IMPLEMENTATION-PLAN.txt) · [Настройка SSO](docs/FASTKORE-SSO-PILOT.md) · [Результаты проверок](TEST-RESULTS.md).

Актуальная библиотека материалов: [единое ТЗ на упрощение](docs/LIBRARY-SPEC.txt) · [TODO и журнал приёмки](docs/PROJECT-SOURCES-TODO.txt). ТЗ 2.0 задаёт библиотеку текущих файлов с работой агента через дерево, поиск и чтение. Статус реализации ведётся в TODO, прежние документы PROJECT-SOURCES сохранены как история.

Текущая реализация использует TypeScript, Node.js, React, Tailwind, Fastify, SQLite и очередь заданий. Выполнение модели идёт через Codex с продолжением сессии. Описание цели выше задаёт направление развития, а доступность функций отражена ниже.

## Что работает

- Проекты, история, Markdown, вложения, модели, остановка задания.
- Вход сотрудников из Fastkore ERP, локальный вход администратора, назначение участников проекта, личные и общие чаты.
- В «Настройки → Команда» администратор выбирает сотруднику рабочую роль и включает доступ к отдельным проектам через «Проекты» в его строке. Администратор видит все проекты.
- Диктовка вставляет речь в черновик после остановки или отправляет её по нажатию стрелки во время записи. Включается в «Настройки → Сервер». Для доступа действуют права выбранного чата и рабочей роли.
- Очередь: новые вопросы принимаются при занятом сервере, сохраняются после перезапуска и выполняются по общей очереди в пределах заданной параллельности, независимо от модели.
- Настраиваемые рабочие роли и инструкции. Административный доступ назначается отдельно от рабочей роли.
- В «Настройки → Общие инструкции» локальный администратор задаёт общие правила. Платформа передаёт их в Codex как инструкции разработчика. Правила роли и специалиста действуют в пределах общих правил, а доступ проверяется сервером.
  [Где хранятся базовые инструкции](docs/AGENT-INSTRUCTIONS.md)
- Профили специалистов с правилами, моделью, уровнем рассуждения, операциями, источниками и ограничением записи.
- Реестр именованных источников. Регистрация — только настройка, не выдача содержимого.
- Повтор clientRequestId с тем же запросом возвращает прежнее задание; изменённое содержимое с тем же ID даёт 409.
- Перед запуском и во время исполнения повторно проверяются пользователь, сеанс, роль, проект и вложения.
- Для SSO-пилота: подготовка входа в WebView2, одноразовый билет, защищённая cookie-сессия, первый вход без прав и регистрация установок ERP с ротацией ключей. Выполнение с SSO использует отдельный исполнитель Codex. При его отсутствии исполнение выключается.
- Аккаунты исполнителей: Codex (вход ChatGPT), Antigravity (Google) и GLM (Z.ai) с ключом GLM Coding Plan. Сотрудникам видны модели всех активных аккаунтов; подключённые, но неактивные аккаунты скрыты. Добавление — мастером в модальном окне (тип → подключение → автоматическая активация). Ключ GLM — это ключ подписки Z.ai, а не платный OpenAI API; блокировка OpenAI API-ключей не затрагивается. Лимиты GLM платформой не читаются.

## Состояние остальных этапов

Реализован пилот SSO по ТЗ 1.1. Платформа связывает билет с попыткой входа в WebView2, проверяет его на сервере ERP и применяет тему Fastkore. Пилот выключен в базовом Compose. Совместная проверка с Fastkore/WPF ещё не проведена. [Настройка пилота](docs/FASTKORE-SSO-PILOT.md).

В репозитории подключены инструменты чтения Fastkore через MCP и CLI с делегированным доступом сотрудника. Создание и изменение объектов ERP, возврат сформированных файлов и результатов через эти инструменты требуют расширения текущего набора операций. Контролируемая выдача результатов из закрытых источников и цепочки специалистов остаются направлениями разработки.

Профили оценщика, технолога и бухгалтера предсозданы выключенными. Можно настроить их заранее; исполнение закрытых операций технически заблокировано. Профиль с источниками, Skills или операцией кроме chat также не запускается до реализации соответствующей среды.

**Регистрация любого закрытого источника приостанавливает все запуски Codex в приложении**, включая обычный чат и проверку подписки. Причина: общий системный контекст ещё не позволяет надёжно отделить чтение такой папки от обычной работы. До Linux-проверки используйте искусственные/открытые тестовые данные. Сама регистрация не создаёт изоляцию ОС.

Для Docker подготовлены основной сервис и отдельный исполнитель Codex, SSO, подключение CLI и MinIO. Конфигурация проекта использует адрес `https://agentic-platform.fastkore.ru`. Инструкции запуска исполнителя приведены в [CODEX-WORKER.md](docs/CODEX-WORKER.md). Приёмка каждой бизнес-операции проверяет её доступность, полномочия сотрудника и состав выдаваемого результата.

## Локальный запуск на Windows

Нужны Node.js 24.19.0 или совместимый Node 24 с node:sqlite и установленный Codex CLI.

Из исходников:

```powershell
npm.cmd ci
npm.cmd test
npm.cmd run build
node dist/server/index.js
```

Для офисной сети: `node dist/server/index.js --lan`. Архив с Windows-runtime запускается через START-LOCAL.cmd или START-LAN.cmd. Адрес локального компьютера: http://127.0.0.1:8787/; действующий офисный адрес смотрите в настройках.

При первом запуске на самом сервере нажмите «Первичная настройка руководителя» и задайте собственный пароль. Универсального пароля нет. Если учётные записи уже созданы, вход остаётся прежним; миграция не сбрасывает пароли.

В настройках проверьте путь к Codex и авторизацию ChatGPT. API-ключ OpenAI блокируется, автоматической платной подмены нет. Токены событий не показывают точный остаток подписки. Допустимость командного использования ChatGPT-аккаунтов согласуется отдельно: личный Pro не следует считать общей подпиской всех сотрудников.

Для диктовки укажите `BRIDGE_DICTATION_URL` с адресом `/transcriptions` сервиса Whisper и сохраните его токен в `private/dictation/token`. В Docker токен монтируется только для чтения. На Windows `deploy/windows-dictation.ps1 -WhisperRoot C:\Projects\Whisper` запускает отдельный экземпляр Whisper на `127.0.0.1:8766`. Из Docker Desktop укажите `http://host.docker.internal:8766/transcriptions`. В «Настройки → Сервер → Использовать голос» администратор может скачать и выбрать `large-v3-turbo` или `large-v3`. Выбор сохраняется на стороне Whisper. Сервис загружает выбранную модель при запуске и держит её в памяти. Запись обрабатывается во временном WAV. Для браузера и WebView2 нужен доступ к микрофону.

## Роли и специалисты

В «Команда» доступны:

1. Создание сотрудников, блокировка и сброс пароля.
2. Назначение участников выбранного проекта.
3. Назначение ролей Fastkore, которым разрешён вход в проект.
4. Подключение агентов и источников к проекту.
5. Журнал административных изменений.

Сотруднику с доступом к проекту по роли Fastkore доступны подключённые агенты, включённые и поддерживающие чат. Отдельное назначение рабочей роли для этого не требуется. Для библиотеки действуют подключения и разрешения на папки конкретного агента. Рабочие роли платформы ещё используются для сохранённых инструкций и приёмов.

Обычный чат работает по инструкциям проекта, в том числе когда в проекте нет подключённых агентов. При необходимости он выбирает консультанта по описанию из списка подключённых агентов. Через @ сотрудник выбирает консультанта для конкретного вопроса. Под ответом видны агенты, которые действительно консультировали. «Начать отдельный чат» открывает личный чат с выбранным специалистом.

В изолированном исполнителе чат проекта и специалисты могут читать «Справку по Fastkore» и общие регламенты компании. Папки назначаются в библиотеке проекта. Консультант читает папки, назначенные его профилю, с проверкой прав и режима выдачи до передачи результата в чат. Изменение правил агента или рабочей роли создаёт свежий контекст Codex при следующем вопросе с сохранением истории сообщений.

Запись Codex возможна только если разрешена одновременно в настройках сервера и профиле. По умолчанию оба ограничения не дают агенту менять файлы.

Личный чат видят его владелец и администраторы с соответствующим доступом. Владелец или администратор может открыть чат участникам проекта. Под сообщениями участников указаны имена авторов. Пока запросы одного участника выполняются или ожидают запуска, другие могут читать чат. Привязанные чаты Fastkore сохраняют связь с карточкой или списком ERP. **Файлы обычного проекта общие независимо от видимости чата.** Это по-прежнему прототип для доверенной офисной команды.

## Очередь и восстановление

Статусы: queued → running → complete / error / cancelled. Ожидающий вопрос можно отменить. На вкладке «Настройки → Сервер и AI → Модели и очередь» администратор задаёт одно общее число параллельных заданий. Свободные места занимают готовые задания в порядке поступления. Сохранение действует сразу. Уже начатые задания продолжают выполняться. До первого сохранения действует `BRIDGE_EXECUTOR_CONCURRENCY` (4). Ходы одного чата выполняются последовательно, включая смену модели. Fastkore CLI использует свой предел `BRIDGE_FASTKORE_CLI_CONCURRENCY` (4). В очереди может ждать до 100 заданий.

Поставку Fastkore CLI для Linux x64 импортируйте из ZIP. Если рядом есть `<архив>.sha256`, скрипт автоматически сверит хеш ZIP. При необходимости передайте ожидаемый хеш параметром `-Sha256`.

```powershell
& ./deploy/Import-FastkoreCli.ps1 -ZipPath 'C:/Temp/FastkoreCLI-27.0.50.0-linux-x64-sso.zip' -Build
```

Скрипт проверяет `SHA256SUMS` и манифест, помещает поставку в `private/fastkore-cli-pilot/<версия>-sso`, собирает образ и проверяет его каталог команд без подключения к ERP. Работающие контейнеры при импорте не переключаются. Когда совместимая версия Fastkore готова к проверке, обновите тестовый стек командой `./deploy/Update-TestStack.ps1 -CliVersion 27.0.50.0`.

Тайминги ответа сохраняются в `GET /api/runs/<id>` и выводятся как JSON-событие `run.timing` в журнале контейнера приложения. `./deploy/Get-RunTiming.ps1 -RunId <id>` выводит этапы и связанные вызовы ERP. Без `-RunId` показывает последнее задание чата. Время этапов указано в миллисекундах. `erpToolWallMs` считает пересекающиеся вызовы один раз, а `outsideToolsMs` учитывает время исполнителя вне инструментов, включая ожидание провайдера и передачу ответа. В «Журнале доступа» откройте детали вызова ERP и сопоставьте их по ID задания. Для CLI видны выдача билета, время вызова исполнителя и вложенное в него время процесса CLI вместе с gRPC. Для MCP отдельно записывается время HTTP-запроса. Чистое время вычислений модели и обработку запроса внутри ERP эти замеры не показывают.

При обычном завершении сервера активный процесс останавливается; ожидающие задания сохраняются. После аварийного завершения прежнее running становится interrupted и не запускается заново автоматически. Ранее queued остаются в очереди. Неизвестный результат внешнего действия нельзя повторять вслепую.

Отзыв ключа, блокировка или смена рабочей роли прекращают новые действия; выполняемое задание проверяет доступ также во время работы. Уже совершённые изменения файлов или внешней системы автоматически не откатываются.

## SQLite и обновление

Данные находятся в BRIDGE_DATA_DIR; по умолчанию Windows использует %LOCALAPPDATA%/CodexChatBridgeWeb.

При первом запуске с прежним state.json:

- создаётся отдельная копия state.json.pre-sqlite-<timestamp>;
- проекты, чаты, сессии, сообщения и хеши учётных данных переносятся в state.sqlite;
- исходный JSON остаётся без изменений;
- дальнейшая работа ведётся через SQLite; JSON больше не обновляется.

SQLite использует WAL и транзакции. Нельзя копировать только state.sqlite у работающего сервера, игнорируя WAL. Для обычной резервной копии штатно остановите сервер, сохраните всю папку данных и библиотеки проектов. Секреты и резервные копии должны быть недоступны исполнителям и веб-каталогу.

При повреждённой SQLite приложение не подменяет историю устаревшим JSON. Восстановление выполняет администратор из проверенной копии. Возврат к 0.4 возможен только с соответствующей копией JSON; новые данные в старую версию автоматически не переносятся. Версия 0.6 обновляет SQLite до user_version=2; для возврата к 0.5 восстановите её резервную копию, не подставляйте устаревший JSON.

Не запускайте две версии с одной папкой данных. Разные ОС используют разные пути к библиотекам: перенос Windows-истории на Linux требует отдельной проверки и переназначения путей; один Docker-контейнер не исправляет Windows-пути автоматически.

## Базы знаний

В глобальных настройках доступны «Справка по Fastkore» и «База знаний о компании». Локальный администратор загружает, заменяет, скачивает и удаляет файлы, редактирует текстовые документы UTF-8 и краткую памятку каждого раздела. Материалы компании общие для всех агентов данной установки. Файл ограничен 20 МБ. Текст индексируется полностью, PDF и XLSX используют существующее извлечение выдержек. Для остальных форматов сохраняется скачиваемый оригинал с отметкой о недоступности текста.

Четыре руководства из `knowledge/fastkore` включаются в Docker-образ и загружаются при первом открытии базы. Изменённые администратором документы сохраняются при обновлении приложения. Оригиналы, версии, памятки и поисковый индекс находятся в `knowledge.sqlite` внутри папки данных и входят в её резервную копию вместе с WAL.

В режиме отдельного исполнителя агент получает инструмент `knowledge` с действиями `index`, `search` и `read`. Поиск по словам возвращает до пяти выдержек, чтение выдаёт до 4000 символов с версией и номером следующего фрагмента. Краткая памятка и каталог добавляются в контекст при новой сессии и изменении базы. История сессии сохраняется, обновление базы передаётся следующим сообщением. После сокращения истории агент может перечитать необходимый фрагмент. При конфликте версий API отвечает 409.

## Файлы проекта и S3

В разделе «Настройки → Сервер → Хранилище файлов» локальный администратор выбирает диск или S3 для новых файлов проекта, вложений и результатов агента. Каждый файл читается из того хранилища, куда был загружен. Переключение не переносит старые файлы. Для восстановления сохраните SQLite, локальные файлы и объекты S3. При смене S3 endpoint или бакета сначала скопируйте объекты с сохранением ключей.

Для внешнего S3 создайте закрытый бакет и задайте параметры из `.env.example`. Приложению нужны права проверки бакета, чтения, записи и удаления объектов. Для локального запуска можно добавить MinIO к существующему списку файлов Compose:

```sh
mkdir -p private
(umask 077; set -C; openssl rand -hex 32 > private/minio-password)
chmod 0440 private/minio-password
chgrp 1000 private/minio-password
docker compose -f compose.yaml -f compose.minio.yaml up -d --build --wait
```

На Windows создайте `private/minio-password` как текстовый файл UTF-8 с уникальным случайным паролем и ограничьте доступ к нему через ACL. MinIO использует том `minio_objects` и доступен только в отдельной Docker-сети. При первом выборе S3 приложение проверяет соединение и создаёт бакет для локального MinIO. Этот образ собирается из закреплённого [выпуска MinIO Community](https://github.com/minio/minio/releases/tag/RELEASE.2025-10-15T17-29-55Z). Для рабочего окружения можно использовать поддерживаемый S3-сервис.

## Библиотека

Библиотека — общий механизм для документации, договоров, таблиц, исходного кода и других файлов. Материалы лежат в именованных папках («Документация», «Договоры», «Fastkore Platform»). У каждой папки одно актуальное содержимое: версий и истории нет. Папку можно подключить к нескольким проектам; обновление сразу действует во всех.

- В «Настройки → Библиотеки» папки разделены по вкладкам «Обычные» и «Внешние». Администратор создаёт папки, назначает управляющих и проверяет хранилище на вкладке «MinIO / S3».
- «Настроить проект» — единое окно для подключения специалистов и папок. Раздел «Доступ к материалам» задаёт, какие папки получит каждый специалист.
- Переключатель «Активная» приостанавливает использование папки агентами во всех проектах. Файлы, связи и назначения сохраняются. Папки, ранее отмеченные закрытыми, при обновлении становятся неактивными и сохраняют ограничения закрытого анализа.

### Внешняя библиотека

В настройках платформы и в библиотеке проекта есть две кнопки.

- **Обычная библиотека** — для файлов с компьютера. При первом подключении выберите MinIO или Amazon S3, укажите отдельный закрытый бакет и введите ключи доступа. Для соседнего контейнера в общей Docker-сети укажите адрес S3 API по имени сервиса, например `http://minio:9000`. Нажмите «Проверить и сохранить», назовите библиотеку и выберите «Загрузить папку». Сменить ключи можно в разделе «Хранилище MinIO / S3 → Настроить».
- **Внешняя библиотека** — для Dropbox, Google Диска и Яндекс Диска. Выберите диск и нажмите «Подключить». Мастер откроет кабинет провайдера по ссылке, покажет необходимые разрешения. Для Dropbox и Google укажите адрес возврата из мастера. Для нового приложения Яндекс Диска выберите «Для доступа к API или отладки», оставьте фиксированный адрес Яндекса и после входа введите показанный код в мастере. Введите ключи приложения в форму Fastkore и подтвердите вход на стороне провайдера. При следующих подключениях сразу появится кнопка входа. Затем откройте нужную папку, подтвердите выбор и создайте библиотеку.

Настройка доступна администратору. Платформа сохраняет подтверждённые реквизиты в зашифрованном виде в отдельных файлах `s3.env`, `dropbox.env`, `google.env` и `yandex.env` в постоянном каталоге данных экземпляра и применяет их сразу. Существующие настройки окружения используются, пока для сервиса нет сохранённых настроек. Сохраняйте каталог данных вместе с ключом `drive-oauth.key` при резервном копировании.

#### Google Drive: первый вход в режиме Testing

1. В Google Cloud выберите проект для Fastkore и включите [Google Drive API](https://console.cloud.google.com/apis/library/drive.googleapis.com).
2. В Google Auth Platform настройте экран согласия. В [Data Access](https://console.cloud.google.com/auth/scopes) добавьте разрешение на чтение `https://www.googleapis.com/auth/drive.readonly`.
3. В [Clients](https://console.cloud.google.com/auth/clients) создайте OAuth-клиент типа **Web application**. В **Authorized redirect URIs** вставьте точный адрес возврата, показанный мастером вашего экземпляра Fastkore, и сохраните настройки.
4. Откройте [Audience](https://console.cloud.google.com/auth/audience). Сверьте проект в верхней панели с проектом клиента из шага 3. Если аудитория **External**, а статус приложения **Testing**, перейдите к **Test users** и нажмите **Add users**.
5. Введите полный email аккаунта, с которым будете открывать Google Drive. Нажмите **Save** и убедитесь, что email появился в списке.
6. В мастере Fastkore выберите **Google Drive → У меня есть ключи**, введите **Client ID** и **Client secret** и нажмите **Войти через Google**. Выберите аккаунт из шага 5 и подтвердите чтение файлов.
7. Откройте нужную папку, нажмите **Далее**, проверьте название и нажмите **Создать**.

Если Google показывает **403: access_denied** и сообщает, что приложение доступно только одобренным тестировщикам, закройте окно ошибки. Выполните шаги 4–5, нажмите в мастере **Назад → Войти через Google** и выберите добавленный аккаунт. Текущие Client ID и Client secret подходят для повторного входа.


Первая синхронизация начинается после создания. Сервер проверяет активные подключения каждые пять минут и по кнопке «Синхронизировать». При поиске и чтении он сверяет состав, версии и доступность файлов на диске. При изменениях выдача прежнего снимка приостанавливается до завершения синхронизации. Поиск возвращает путь, фрагмент и ссылку на источник. Google Документы и Таблицы экспортируются для индексации в DOCX и XLSX, презентации — в PDF.

Для внешних библиотек S3 не требуется. Каталог `drive-cache/` на сервере содержит закрытые рабочие копии для индексации и чтения. Токены хранятся зашифрованными в `library.sqlite`. Включите каталог кеша, базу и файл ключа `drive-oauth.key` в защищённую резервную копию. «Восстановить связь» позволяет заново авторизовать исходную папку. «Отключить библиотеку» убирает доступ в проектах и запускает очистку локальных данных. Оригиналы остаются у провайдера.

### Обычная библиотека (S3)

Загрузка идёт только через браузер на базе Chromium. «Загрузить папку» и «Обновить из папки» считают выбранную папку полным содержимым: новые файлы добавляются, изменённые заменяются, отсутствующие удаляются. Перед применением показываются количества добавлений, изменений и удалений. «Добавить файлы» добавляет или заменяет файлы с тем же путём, остальные сохраняются. Файл можно удалить из списка папки. Неизменившиеся файлы повторно не передаются и не обрабатываются; совпадающая папка даёт «Библиотека актуальна». После обрыва «Продолжить загрузку» требует выбрать ту же папку и досылает только недостающие части. На папку допускается одна операция; вторая получает «Папка уже обновляется».

До окончания обработки агент использует прежнее содержимое папки, после неё содержимое и индекс переключаются целиком. Если часть файлов не обработана (ошибка извлечения или превышение 30 секунд на файл), обновление не публикуется: в карточке папки доступны «Что не обработано», «Повторить обработку» и «Принять с неполным покрытием». Неподдерживаемые форматы и кодировки видны как «Файлы без поиска».

Профиль «Исходники» отбрасывает DLL/EXE/PDB, пакеты, каталоги сборок, зависимостей и кешей (`bin/`, `obj/`, `node_modules/`, `.artifacts/`, `publish/` и т. п.). Профиль «Документы» убирает только временные и ключевые файлы. Правила видны и меняются перед отправкой. Подозрительные секреты исключаются по умолчанию; включить такой файл может управляющий, решение записывается в журнал.

Агент работает с библиотекой как с каталогом: `library_list`, `library_tree`, `library_search` (точная подстрока, слова или имена файлов) и `library_read` (до 200 строк, с метками страниц и листов документов). В ответе он называет папку, файл и место. Поиск идёт по индексу на сервере; оригиналы читаются диапазонами из MinIO, локальных копий на сервере нет. Режимы выдачи: «Только объяснение» (по умолчанию) и «Короткие цитаты»; ответ проверяется на дословные фрагменты перед публикацией. Права проверяются при каждом обращении и перед публикацией; изменение содержимого во время ответа не проверяется, следующий вопрос использует актуальные материалы.

Поддерживаются текстовые файлы и исходники (UTF-8, UTF-8 с BOM, UTF-16 с BOM, Windows-1251), PDF с текстовым слоем (PDF без текста отмечается «Требуется распознавание»), DOCX, XLSX и CSV. Ссылки агента указывают страницу PDF, заголовок раздела и номер таблицы и строки DOCX (страниц в DOCX нет), лист и диапазон ячеек XLSX с буквами и названиями колонок, строку CSV. Уже загруженные DOCX, XLSX и файлы в Windows-1251 после обновления сервера обрабатываются заново в фоне, содержимое папки при этом не меняется. Файлы прежних «Файлов проекта» при первом запуске переносятся в папку «Файлы проекта «…»» каждого проекта, подключённую к нему; специалисты получают тот же доступ, что был, включая ограничение отдельными файлами.

Хранилище библиотеки использует отдельный закрытый бакет. Для первоначальной настройки доступна форма «Подключить хранилище». Пределы допуска: `BRIDGE_LIBRARY_MAX_FILES` (50 000), `BRIDGE_LIBRARY_MAX_FILE_BYTES` (100 МиБ), `BRIDGE_LIBRARY_DEFAULT_QUOTA` (20 ГиБ). Закрытые папки хранятся, но агенту в этой поставке недоступны; `BRIDGE_LIBRARY_CLOSED_ANALYSIS=verified` включается только после проверки исполнителя, его сессий и журналов.

Резервная копия библиотеки — часть общей копии приложения: `data/library.sqlite` (копировать при остановленном приложении или через `sqlite3 .backup`) и бакет MinIO. Оригиналы восстанавливаются из бакета, индекс — повторной обработкой.

## Подготовка Linux

Файлы Dockerfile и compose.yaml предназначены для ранней проверки приложения. Требуются Docker Engine с Compose, локальная файловая система для SQLite, каталог данных с владельцем UID/GID 1000:1000 и настроенный администратором HTTPS reverse proxy.

1. Скопируйте .env.example в .env и задайте BRIDGE_PUBLIC_ORIGIN без завершающего слеша.
2. Создайте data/ и projects/ с нужными правами.
3. Выполните `docker compose build`, затем `docker compose up -d`.
4. Proxy направляет HTTPS-запросы к 127.0.0.1:8787. Порт приложения не публикуется напрямую в офисную сеть/Интернет.
5. Проверяйте /api/health, авторизацию, перенос данных и перезапуск. Первичная настройка по loopback выполняется внутри серверной среды; SSO не заменяет первичную настройку администратора.

Базовый образ приложения использует `BRIDGE_EXECUTION=disabled`. Overlay `compose.codex.yaml` подключает отдельный исполнитель и устанавливает `BRIDGE_EXECUTION=isolated`. Учётные данные и секреты подключаются во время развёртывания. При выключенном исполнении ожидающие задания сохраняются, настройки и история доступны.

Для создания и редактирования шарнирной тяги в чате подключите [сервис FreeCAD](deploy/freecad/README.md) через `compose.freecad.yaml`. Каждая версия выдаётся как FCStd и GLB.

Готовую среду Codex, его авторизацию, изоляцию и минимальный набор файловых инструментов предстоит подключить на последующих этапах. Не включайте исполнение с закрытыми данными простым удалением переменной: для этого в плане предусмотрены отдельные проверки.

Совместные проверки SSO, WebView2 и операций ERP выполняются с разработчиками Fastkore. Linux CLI подключается отдельным исполнителем по [инструкции](docs/CODEX-WORKER.md) и [контракту пользовательского билета](Fastkore-Agent-Platform-CLI-Ticket-v1.txt).

Результаты и границы проверки описаны в TEST-RESULTS.md. Фактический API текущей версии описан в API.md; будущие маршруты из общего ТЗ не обозначаются как уже работающие.
