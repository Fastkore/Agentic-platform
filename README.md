# Codex Chat Bridge Web · 0.6.0

Промежуточная поставка: этапы 1–2 и наша часть этапа 3 для локального пилота SSO. SQLite, очередь, роли, профили специалистов и вход из Fastkore по одноразовому билету. TypeScript, Node.js, React, Tailwind, Fastify. Ответы модели по-прежнему получаются через `codex exec` с точным продолжением сессии.

[План реализации](docs/IMPLEMENTATION-PLAN.txt) · [Проект контракта SSO](docs/FASTKORE-SSO-CONTRACT-DRAFT.txt) · [Требования к Linux-пилоту](docs/LINUX-PILOT-REQUIREMENTS.txt) · [Результаты проверок](TEST-RESULTS.md).

## Что работает

- Проекты, история, Markdown, вложения, модели, остановка задания.
- Личные аккаунты, API-ключи, назначение участников проекта, личные и общие чаты.
- Очередь: новые вопросы принимаются при занятом сервере, выполняются последовательно и сохраняются после перезапуска.
- Настраиваемые рабочие роли и инструкции. Административный доступ назначается отдельно от рабочей роли.
- Профили специалистов с правилами, моделью, уровнем рассуждения, операциями, источниками и ограничением записи.
- Реестр именованных источников. Регистрация — только настройка, не выдача содержимого.
- Повтор clientRequestId с тем же запросом возвращает прежнее задание; изменённое содержимое с тем же ID даёт 409.
- Перед запуском и во время исполнения повторно проверяются пользователь, ключ, роль, проект и вложения.
- Для SSO-пилота: одноразовый билет, защищённая cookie-сессия, первый вход без прав и явная привязка объекта к чату. Настройка включается отдельно и требует выключенного исполнения до изоляции.

## Состояние остальных этапов

Реализован выключенный по умолчанию кандидат SSO по контракту v1: HTTPS-проверка билета, cookie/CSRF, внешние личности, управление установками и контекст объекта через WebView2 message API. На офисном сервере вход остаётся прежним. [Настройка и границы пилота](docs/FASTKORE-SSO-PILOT.md). Совместная проверка с Linux/Fastkore/WPF ещё не проведена.

Изоляция, контролируемая выдача КП, корпоративные инструменты Fastkore, передача оценщик → технолог и новый API /api/tasks ещё не реализованы.

Профили оценщика, технолога и бухгалтера предсозданы выключенными. Можно настроить их заранее; исполнение закрытых операций технически заблокировано. Профиль с источниками, Skills или операцией кроме chat также не запускается до реализации соответствующей среды.

**Регистрация любого закрытого источника приостанавливает все запуски Codex в приложении**, включая обычный чат и проверку подписки. Причина: общий системный контекст ещё не позволяет надёжно отделить чтение такой папки от обычной работы. До Linux-проверки используйте искусственные/открытые тестовые данные. Сама регистрация не создаёт изоляцию ОС.

Docker/Linux и HTTPS пока не проверены на целевом сервере. Подготовлена конфигурация для проверки самого приложения с выключенным исполнением. Она не является готовым защищённым Codex-исполнителем.

## Локальный запуск на Windows

Нужны Node.js 24.19.0 или совместимый Node 24 с node:sqlite и установленный Codex CLI.

Из исходников:

```powershell
npm.cmd ci
npm.cmd test
npm.cmd run build
node dist/server/index.js
```

Для офисной сети: `node dist/server/index.js --lan`. Архив с Windows-runtime запускается через START-LOCAL.cmd или START-LAN.cmd. Адрес локального компьютера: http://127.0.0.1:8787/; действующий офисный адрес смотрите в настройках.

При первом запуске на самом сервере нажмите «Первичная настройка руководителя» и задайте собственный пароль. Универсального пароля нет. Если учётные записи уже созданы, вход остаётся прежним; миграция не сбрасывает пароли.

В настройках проверьте путь к Codex и авторизацию ChatGPT. API-ключ OpenAI блокируется, автоматической платной подмены нет. Токены событий не показывают точный остаток подписки. Допустимость командного использования ChatGPT-аккаунтов согласуется отдельно: личный Pro не следует считать общей подпиской всех сотрудников.

## Роли и специалисты

В «Команда» доступны:

1. Создание сотрудников, блокировка и сброс пароля.
2. Назначение участников выбранного проекта.
3. Выбор рабочей роли для каждого пользователя.
4. Настройка ролей, специалистов и источников.
5. Журнал административных изменений.

Новая рабочая роль определяет доступные профили и операции. Текстовые инструкции помогают агенту, а фактические разрешения проверяет сервер. В текущей поставке право чтения закрытых источников можно настроить, но выдача этих источников сотруднику пока не реализована.

Перед созданием чата выберите специалиста слева. Профиль закрепляется за новым чатом. Изменение его правил или рабочей роли создаёт свежий контекст Codex при следующем вопросе; история сообщений остаётся. При смене только модели в той же области доступа сессия сохраняется.

Запись Codex возможна только если разрешена одновременно в настройках сервера и профиле. По умолчанию оба ограничения не дают агенту менять файлы.

Личный чат видят его автор и администраторы. Общие чаты доступны участникам проекта для чтения; продолжает их автор или администратор. **Файлы обычного проекта общие независимо от видимости чата.** Это по-прежнему прототип для доверенной офисной команды.

## Очередь и восстановление

Статусы: queued → running → complete / error / cancelled. Ожидающий вопрос можно отменить. Один ход одной сессии исполняется в каждый момент времени. Для очереди установлен предел 100 ожидающих заданий.

При обычном завершении сервера активный процесс останавливается; ожидающие задания сохраняются. После аварийного завершения прежнее running становится interrupted и не запускается заново автоматически. Ранее queued остаются в очереди. Неизвестный результат внешнего действия нельзя повторять вслепую.

Отзыв ключа, блокировка или смена рабочей роли прекращают новые действия; выполняемое задание проверяет доступ также во время работы. Уже совершённые изменения файлов или внешней системы автоматически не откатываются.

## SQLite и обновление

Данные находятся в BRIDGE_DATA_DIR; по умолчанию Windows использует %LOCALAPPDATA%/CodexChatBridgeWeb.

При первом запуске с прежним state.json:

- создаётся отдельная копия state.json.pre-sqlite-<timestamp>;
- проекты, чаты, сессии, сообщения и хеши учётных данных переносятся в state.sqlite;
- исходный JSON остаётся без изменений;
- дальнейшая работа ведётся через SQLite; JSON больше не обновляется.

SQLite использует WAL и транзакции. Нельзя копировать только state.sqlite у работающего сервера, игнорируя WAL. Для обычной резервной копии штатно остановите сервер, сохраните всю папку данных и библиотеки проектов. Секреты и резервные копии должны быть недоступны исполнителям и веб-каталогу.

При повреждённой SQLite приложение не подменяет историю устаревшим JSON. Восстановление выполняет администратор из проверенной копии. Возврат к 0.4 возможен только с соответствующей копией JSON; новые данные в старую версию автоматически не переносятся. Версия 0.6 обновляет SQLite до user_version=2; для возврата к 0.5 восстановите её резервную копию, не подставляйте устаревший JSON.

Не запускайте две версии с одной папкой данных. Разные ОС используют разные пути к библиотекам: перенос Windows-истории на Linux требует отдельной проверки и переназначения путей; один Docker-контейнер не исправляет Windows-пути автоматически.

## Подготовка Linux

Файлы Dockerfile и compose.yaml предназначены для ранней проверки приложения. Требуются Docker Engine с Compose, локальная файловая система для SQLite, каталог данных с владельцем UID/GID 1000:1000 и настроенный администратором HTTPS reverse proxy.

1. Скопируйте .env.example в .env и задайте BRIDGE_PUBLIC_ORIGIN без завершающего слеша.
2. Создайте data/ и projects/ с нужными правами.
3. Выполните `docker compose build`, затем `docker compose up -d`.
4. Proxy направляет HTTPS-запросы к 127.0.0.1:8787. Порт приложения не публикуется напрямую в офисную сеть/Интернет.
5. Проверяйте /api/health, авторизацию, перенос данных и перезапуск. Первичная настройка по loopback выполняется внутри серверной среды; SSO не заменяет первичную настройку администратора.

В образе нет учётных данных OpenAI, Codex CLI, корпоративных секретов или рабочего JSON. BRIDGE_EXECUTION=disabled оставлен намеренно: исполнение и приём новых вопросов закрыты до проверки Linux-среды. Ожидающие задания при этом не запускаются и сохраняются. Настройки, история и учётные записи доступны.

Готовую среду Codex, его авторизацию, изоляцию и минимальный набор файловых инструментов предстоит подключить на последующих этапах. Не включайте исполнение с закрытыми данными простым удалением переменной: для этого в плане предусмотрены отдельные проверки.

Контракт SSO, WebView2 и тестовый Fastkore 2027 предоставляются/согласуются с разработчиками ERP. Windows CLI Fastkore по имеющейся документации не подтверждён для Linux.
