1. ЧТО ДЕЛАЕМ

Развиваем существующую веб-оболочку Codex в корпоративное приложение. Сотрудники работают через браузер либо через тот же веб-интерфейс внутри существующего окна Fastkore (WebView2). Второй нативный чат ERP не разрабатывается; API остаётся для фоновой автоматизации. Проекты и разрешённые библиотеки общие; диалоги, задания и результаты имеют собственные права доступа. Пользователь выбирает именованного специалиста: оценщика, технолога, бухгалтера или универсального помощника.

Codex самостоятельно выполняет многошаговую работу внутри выданных полномочий. Наше приложение определяет, кто может запустить операцию, какие данные и инструменты доступны исполнителю, что можно вернуть пользователю, когда требуется подтверждение и как восстановиться после сбоя. Собственный движок рассуждений не нужен.

Новое ТЗ заменяет прежнее требование настольного Windows-приложения без Docker: целевая поставка теперь Linux, Docker Compose, HTTPS, браузер и HTTP API. Существующий TypeScript/Node.js/React/Tailwind стек подходит; возвращаться к Avalonia или переписывать всё с нуля не требуется.

2. ЧТО ПРОВЕРЕНО И ЧТО ОСТАЁТСЯ НЕПОДТВЕРЖДЁННЫМ

Изучены три присланных документа, комментарий руководителя, исходный код веб-прототипа версии 0.4.0 и доступная документация Fastkore в Downloads. Локальный Codex сообщает версию 0.163.0-alpha.11.2. Проверены справка exec и официальные документы OpenAI. Реальные корпоративные запросы и изменения Fastkore в ходе этого анализа не выполнялись; приложение не перезапускалось.

Уже есть: проекты, история, точное продолжение сессии Codex по ID, Markdown, вложения, выбор модели, отмена, учётные записи, блокировка, персональные API-ключи с хранением хешей, принадлежность к проектам, личные/общие чаты, административный журнал. Веб и API используют общие проверки доступа.

Ограничения исходного прототипа 0.4 (этапы 1–2 ниже уже устранены в 0.5; сведения оставлены для понимания объёма доработки):
- Роли фиксированы: admin и employee. Редактора ролей, профилей специалистов и правил нет.
- Всё состояние хранится в одном JSON. Выполняется одно задание; следующее получает ошибку занятости, а не место в устойчивой очереди.
- Все запуски используют общий системный контекст. Разные рабочие папки и read-only не доказывают изоляцию чтения, истории, секретов или сети.
- Ответ агента непосредственно попадает в пользовательский чат. Для операции с закрытыми закупочными ценами такой способ публикации непригоден.
- Есть автоматические выдержки из файлов проекта. Для защищённых операций нельзя автоматически включать в контекст произвольные файлы общей папки.
- Нет этапов с проверяемой передачей результатов, поиска, контролируемой публикации документов и полного нового API задач.
- Обнаружение Codex ориентировано на codex.exe. На Linux требуется отдельная проверка запуска, остановки всего дерева процессов и восстановления после перезапуска.
- Существующая роль администратора видит все чаты, включая личные. Это нужно явно объяснить пользователям: «личный» сейчас означает скрытый от коллег, а не от администратора.

Утверждение о готовой Linux-интеграции Fastkore пока невозможно. В архиве FastkoreCLI-net10-agent-docs-20261001.zip файл NET10-MIGRATION.md указывает net10.0-windows и win-x64; AGENT-START.md прямо описывает Windows. Переход на .NET 10 сам по себе не делает этот CLI кроссплатформенным.

Найдены отдельные HTTP-контракты, например изменение стадии производственной операции, и исторические примеры MCP-чтения заказов/партий. Это не полный подтверждённый API для расчёта, материалов, документов и бухгалтерии. Наличие описания не означает доступность метода на выбранном сервере сегодня. Пользователь подтвердил, что дополнительных материалов у него нет.

3. РОЛИ, СПЕЦИАЛИСТЫ, БИБЛИОТЕКИ И SKILLS

Разделяем понятия:

Роль сотрудника — какие операции, проекты и результаты ему доступны. Например, менеджер может заказать расчёт и получить КП, но не читать закупочный прайс.

Профиль специалиста — конфигурация запуска Codex: ID, название, назначение, инструкции, модель/усилие рассуждения, источники, инструменты, Skills, ограничения выполнения и допустимые результаты. Профиль «Оценщик» не создаёт отдельную нейросеть.

Набор данных — именованный источник, например «Прайсы поставщиков» или «Материалы и технологии». Один набор может использоваться несколькими специалистами. Администратор связывает источник с доступным серверным расположением; сотрудник передаёт ID, а не произвольный путь.

Операция — разрешённая бизнес-задача, например «подготовить коммерческое предложение». Она задаёт допустимые входы, права, возможные этапы, проверки и состав опубликованного результата.

Skill — штатный SKILL.md с методикой работы и необходимыми материалами/скриптами. Примеры: чтение исходных прайсов, расчёт КП, подготовка технологии, использование конкретных команд Fastkore.

Подключение — настроенный доступ к CLI или HTTP API с ограничениями операций и аргументов. Plugin — необязательная упаковка связанных Skills и интеграций для доставки и обновления.

Предлагаемые начальные роли: администратор, менеджер, технолог, бухгалтер, руководитель. Названия и наборы разрешений редактируются; сложное наследование ролей не требуется. Специалист «Бухгалтер» может быть заведён как профиль, но его реальные операции должны быть описаны владельцем процесса: название само по себе не является готовым бухгалтерским сценарием.

В админке нужны отдельные права: управление пользователями/ролями; назначение доступа к проектам; управление профилями/правилами; запуск операций; чтение конкретных источников; чтение внутренних результатов; публикация результата; подтверждение критических действий. Не обязательно показывать каждый технический флаг пользователю — интерфейс может группировать их понятными переключателями.

Правила разделяем на текстовые инструкции и технические ограничения. Текст влияет на поведение Codex; разрешения, проверка объектов, схема результата и необходимые подтверждения обеспечиваются сервером. Редактор правил не должен позволять сотруднику добавлять произвольный исполняемый код. Для первой версии достаточно поддерживаемых проверок: обязательные поля, типы, единицы, округление, арифметика, наличие исходных данных и необходимость подтверждения.

Право выполнить операцию с закрытым источником не равно праву прочитать источник. Например, менеджер вправе вызвать расчёт, а защищённый исполнитель получает необходимый прайс на основании политики этой операции. Пользователю возвращается только разрешённый результат.

4. АВТОНОМНОСТЬ CODEX И НЕСКОЛЬКО СПЕЦИАЛИСТОВ

Штатный exec сохраняем. Он поддерживает выполнение задач с инструментами, события JSONL, структурированный результат и продолжение сессии. Специально программировать каждый шаг анализа файла или выбор следующего запроса не нужно.

Skills подходят. Codex способен выбирать Skill по описанию и задаче; для критических процедур профиль дополнительно явно задаёт нужную методику. Автоматический выбор — удобство, а не проверка прав и не гарантия правильного выбора. Исполнитель получает только утверждённый набор Skills. Пользовательские загрузки не устанавливают Skills, плагины, hooks, AGENTS.md или конфигурацию.

Plugin полезен позже для упаковки комплекта Fastkore. Для первого работающего сценария достаточно Skills и имеющегося CLI/HTTP. MCP исключён из обязательного периметра согласно последней пометке в дополнении. Наличие старых MCP-примеров не делает его обязательным транспортом.

Штатные подагенты применимы для делегирования в пределах одинакового доступа. Они наследуют sandbox/полномочия родителя; разные инструкции не создают независимую границу безопасности. Совместимость конкретного сценария подагентов с закреплённой версией exec проверяется небольшим тестом. Она не должна блокировать основной сценарий.

Для перехода между разными правами нужен небольшой координатор этапов в нашем сервере:

Заявка пользователя
  -> Оценщик: изучает заявку, разрешённые прайсы и доступные инструменты
  -> При необходимости: формирует ограниченное задание технологу
  -> Технолог: получает характеристики изделия и свою библиотеку
  -> Оценщик: использует технологический результат для завершения расчёта
  -> Сервер: проверяет результат и формирует опубликованное КП

Если технология уже определена, этап технолога пропускается. Потребность в нём может предложить Codex; сервер проверяет, разрешён ли переход в данной операции. Порядок допустимых этапов фиксирован для этого сценария. Универсальный граф и визуальный конструктор не нужны.

Передача между этапами — короткий структурированный результат и разрешённые файлы по ID. Не передаём весь диалог, закрытые источники или сырые журналы. Например, технологу нужны размеры, материал, количество и ограничения; закупочные цены обычно не нужны.

Сохраняем версию входных данных, этап, попытку, ссылки на результаты и внутреннюю сессию. При изменении количества или исходной спецификации зависимые результаты становятся неактуальными; интерфейс показывает пересчёт. Контрольные суммы/ревизии нужны для актуальности, но полноценная система версионирования всех файлов не требуется.

Пользовательский чат и внутренняя сессия специалиста — разные сущности. Один видимый чат может иметь несколько закрытых сессий этапов. Сессию привязываем к заданию, профилю, области доступа и учётной записи Codex. Смена профиля, прав или набора закрытых данных требует проверки совместимости; при изменении границы доступа создаётся новая сессия. Обычный resume старой привилегированной сессии в свободный пользовательский чат запрещён.

5. КАК ОГРАНИЧИТЬ ОБХОД ПРАВ И УТЕЧКИ

Нельзя обещать абсолютную защиту секретов, если модель читает секрет и может свободно отвечать человеку. Фраза «не показывай себестоимость», отдельный Skill, JSON Schema или второй проверяющий агент не дают такой гарантии. Строгая схема ограничивает форму, но текстовые поля и даже числа могут переносить лишние сведения. Продажная цена с известной фиксированной наценкой позволяет вычислить закупочную цену без всякого взлома.

Для описанного в ТЗ режима предлагаем следующие обязательные границы:

А. Единая серверная проверка пользователя и объекта во всех маршрутах: чат, поиск, задание, файл, результат, отмена, уточнение, webhook. API-ключ имеет права своего владельца. Переданный в JSON userId сам по себе не является удостоверением личности.

Б. Изолированное выполнение задания/этапа: только необходимые источники, закрытые источники только для чтения, отдельная рабочая папка для создаваемых материалов, ограниченные CPU/память/время. Исполнитель не получает базу приложения, чаты других пользователей, резервные копии, Docker socket или управление сервером. Общая директория не заменяет эту изоляцию.

В. Отдельно проверяется доступ к учётным данным Codex. Простое подключение auth.json в контейнер только для чтения НЕ скрывает токен от чтения. Требуется проверенная граница между доверенным клиентом Codex и запускаемыми агентом командами. Подходящие ограничения файловой системы/секретов и их работа в Linux-контейнере — ранний обязательный технический тест. При неуспехе не выдаём защищённый режим за готовый и не отключаем sandbox ради запуска.

Г. Сеть ограничивается разрешёнными направлениями. Доступ клиента к OpenAI не означает, что командному инструменту можно предоставить весь Интернет. Для закрытых операций отключаем ненужные внешние инструменты, веб-поиск и произвольные URL. Fastkore доступен через согласованный канал с правами конкретной операции. Проверяем обход через прямой CLI/HTTP, DNS, перенаправления и файловые ссылки.

Д. У закрытой операции есть внутренний результат и опубликованный результат. Сотруднику не отправляются необработанные ответы Codex, stderr, промежуточные таблицы, пути, скрытые страницы/листы или внутренние вычисления. Во время выполнения он видит разрешённые статусы.

Е. Сервер проверяет допустимые поля, типы, размеры и арифметику, затем создаёт документ по утверждённому шаблону. Например: артикул, наименование, количество, продажная цена, сумма, срок. Наименования и идентификаторы сверяются с разрешёнными входами/справочниками; свободные поля минимальны. Поддерживаемые проверки не доказывают отсутствие смысловой утечки — это остаточный риск, который должен принять владелец закрытых данных.

Ж. Загруженные файлы считаются недоверенными данными. Они не могут менять системные инструкции или настройки запуска. Контролируются размеры, типы, архивы, пути, символьные ссылки и загрузка исполняемых расширений. Документы могут содержать вредоносные инструкции; защита должна сохраняться и когда агент им последует.

З. Уточнения сотрудника проходят через контракт операции: изменение количества, параметров изделия, сроков и т. п. Не предоставляем неограниченную переписку с исполнителем, уже прочитавшим закрытый прайс. Произвольный вопрос можно обсудить в отдельном обычном чате без этого прайса.

Если бизнес требует строгого запрета даже косвенного раскрытия закупочных цен, нужен более сильный вариант: закрытые цены не передаются модели, доступной для влияния пользователя; разрешённый расчёт выполняет доверенная функция ERP/расчётный сервис. Это изменение исходного подхода «агент читает Excel» и отдельное решение заказчика, а не обещание, что фильтр решит проблему. Создание собственного универсального расчётного движка в обязательный план не входит.

Полностью привилегированный администратор Linux/хранилища остаётся доверенным лицом: приложение не может гарантированно скрыть данные от владельца самого сервера. Политику видимости личных чатов руководителю нужно явно закрепить.

6. ПОДКЛЮЧЕНИЕ FASTKORE: ЧТО ИСПОЛЬЗУЕМ И ЧТО НЕ ДУБЛИРУЕМ

Документация CLI уже описывает JSON-ответы с success/exitCode/agentContext, чтение схемы и данных, ограничение выбранных полей, проверку прав, ревизии/hash, dry-run, подтверждения и аудит. Эти механизмы следует сохранить. Ошибка 4 означает необходимость перечитать состояние; частичное выполнение/потеря ответа не допускают слепого повторения записи.

В октябрьском комплекте есть локальный Windows broker, который позволяет использовать сохранённые профили без передачи паролей агенту. Но это локальный механизм Windows, а не сетевой Linux-шлюз. Кроме того, BROKER.md прямо указывает: допуск пользователя делегирует использование всех доступных сохранённых профилей и их разрешённых действий. Поэтому общий broker с административным профилем не решает разграничение оценщика и технолога. Требуются ограниченные аккаунты Fastkore и/или дополнительная проверка выбранной операции, профиля и аргументов.

Сравнение вариантов:

Прямой CLI. Минимум нашего кода, если CLI совместим с хостом и сохранённый аккаунт уже имеет строго нужные серверные права. По найденным материалам это Windows-вариант. Широкий аккаунт и инструкция «не выполняй опасные команды» не подходят.

HTTP API. Предпочтительный кандидат для Linux там, где нужные операции действительно опубликованы, защищены и документированы. Нельзя обещать, что отдельный известный endpoint закрывает весь сценарий. Авторизация, ограничения полей и актуальные схемы ещё требуют подтверждения.

Минимальный адаптер. Нужен там, где штатный инструмент не обеспечивает необходимую границу. Он проверяет операцию и аргументы, выбирает разрешённое подключение, обеспечивает секреты, лимиты и аудит, запускает существующий CLI/HTTP и возвращает ограниченный результат. Бизнес-правила Fastkore остаются в Fastkore.

Windows-исполнитель рядом с Fastkore. Резервный вариант, если обязательная операция существует только в Windows CLI. Linux-сервер обращается к небольшому защищённому исполнителю. Это дополнительный компонент, обоснованный конкретной несовместимостью, но он меняет ожидаемую поставку «всё на Linux» и требует отдельного решения. Не добавлять его молча.

MCP. Необязательный вариант использования уже имеющихся инструментов после проверки пользы. Новый MCP-сервер не разрабатываем по умолчанию.

Для настройки подключения администратору нужны: имя, тип, разрешённый адрес/программа, ссылка на секрет, список операций, схемы аргументов, ограничения времени/размера, связанные профили и Skills. Обычное подключение поддерживаемого формата настраивается без правки кода. Произвольный новый протокол или новая бизнес-проверка могут потребовать реализации — «любая система без программирования» не обещается.

Долгоживущие секреты Fastkore не передаются в промпт, командную строку или среду доступной агенту оболочки. Если нужен адаптер, секрет хранится в доверенной части. Исполнитель использует короткоживущее разрешение, привязанное к заданию, профилю и операциям. Нельзя оставлять рядом обходной доступ к исходному API с более широким секретом.

Критическая запись выполняется только после серверного подтверждения конкретного действия. Сохраняются объект, аргументы, ревизия, подтверждающий пользователь и срок действия. Агент не может сам подтвердить своё действие. После изменения аргументов/ревизии подтверждение недействительно. В неинтерактивном exec этот этап организуется приложением: подготовить действие -> ожидать подтверждения -> проверить и выполнить -> продолжить работу. Подтверждение в тексте модели не заменяет его.

7. МИНИМАЛЬНАЯ АРХИТЕКТУРА

Браузер / Fastkore
  -> HTTPS
  -> Существующий Node.js-сервер: пользователи, права, проекты, чаты, задания, API
  -> Устойчивая очередь и небольшой координатор этапов
  -> Изолированный запуск Codex + утверждённые Skills + разрешённые источники
  -> Прямой ограниченный инструмент либо минимальный адаптер Fastkore
  -> Проверка и публикация результата
  -> История пользователя, документ, уведомление ERP

Предлагаемые архитектурные изменения для согласования перед реализацией:
1) Linux/Docker Compose и HTTPS вместо Windows как основной серверной поставки.
2) Изоляция исполнительной среды от самого приложения и других задач.
3) SQLite вместо общего JSON для транзакционной очереди, истории, поиска, этапов и доставки уведомлений. Это встроенная файловая БД, без отдельного сервера БД. Причина замены — связанные изменения должны сохраняться атомарно, а не необходимость «платформы на будущее».
4) Разделение внутренней сессии и публичного диалога/результата для закрытых операций.

Миграция сохраняет существующие ID проектов/чатов, владельцев, сообщения, видимость и хеши паролей/ключей. До миграции создаётся резервная копия; перенос проверяется по объектам и правам. Старые чаты с широким контекстом нельзя автоматически превратить в безопасные закрытые операции. Для них сохраняется прежняя область видимости; новый защищённый сценарий стартует с новой внутренней сессии.

Очередь находится в том же приложении. На первом этапе можно оставить одного исполнителя, но новые задания ожидают очередь и переживают перезапуск. Параллельность добавляется после проверки изоляции и лимитов. Одновременно исполняется не более одного хода одной сессии.

Основные сущности: User, Role, Project, Dataset, AgentProfile, Connection, Operation, Chat, Task, StageAttempt, File/PublishedResult, ApiCredential, Approval, AuditEvent, WebhookDelivery. Это обычные записи приложения, не отдельные сервисы.

Доверенный запуск контейнеров использует фиксированный образ и проверенные пути. Пользователь и Codex не передают произвольные параметры Docker. Если управление контейнерами вынесено в небольшой launcher ради ограничения доступа к Docker daemon, его назначение только запуск/остановка утверждённого исполнения; бизнес-логика остаётся в приложении.

Сессии и необходимая авторизация сохраняются вне одноразового контейнера, но не в общем доступе других задач. Проверяются обновление учётных данных и конкурирующие обращения. Доступность после перезапуска контейнера не означает бесконечную действительность авторизации: отзыв и истечение обрабатываются отдельно.

Нужны обычные инструкции резервного копирования и восстановления БД, файлов, конфигурации и защищённого хранилища авторизации. Собственная система бэкапов не разрабатывается.

8. API И ИНТЕГРАЦИЯ С ERP

Интерактивный сценарий по ТЗ № 3: текущая ERP-сессия -> одноразовый билет -> POST /auth/fastkore/exchange -> онлайн-проверка и атомарное погашение на сервере Fastkore -> Secure/HttpOnly cookie -> наш веб-интерфейс в WebView2. Сервер выбирается только по доверенной конфигурации установки. Пароль ERP и постоянный секрет в клиент не передаются. Пользователь сопоставляется по паре installation_id + fastkore_user_id; роли определяет сама платформа.

Разработчики Fastkore реализуют POST /api/ai/launch-ticket, POST /api/ai/validate-ticket, карточку сервиса с фиксированным GUID типа, существующую кнопку, WebView2 и очистку сессии при смене пользователя. Мы реализуем доверенные установки, обмен билета, cookie/CSRF, сопоставление личности и приём fastkore.context. Форматы согласуются до совместной реализации. Подробное предложение — в FASTKORE-SSO-CONTRACT-DRAFT.txt.

Контекст содержит минимальный указатель на объект, а не его выгрузку или разрешение читать его. Он явно отображается и закрепляется за чатом. SuggestedAgent не расширяет права. Сбой активной интеграции показывает ошибку/повтор без автоматической отправки другому ИИ. Прежний режим кнопки сохраняется при выключенной/ненастроенной интеграции.

Ниже HTTP API применяется для автоматизации, а не обязательного повторного создания чата в ERP.

Внешний контракт сохраняет маршруты исходного ТЗ:
GET /api/agents
POST /api/files
POST /api/tasks
GET /api/tasks/{id}
POST /api/tasks/{id}/messages
POST /api/tasks/{id}/cancel
GET /api/tasks/{id}/results
GET /api/files/{id}

Существующие маршруты проектов/чатов остаются там, где нужны текущему интерфейсу. При переходе на новый сервис задач они используют те же проверки и публикацию; старый маршрут не должен остаться обходом защиты.

Создание задания принимает projectId, agentProfileId, operationId, текст/параметры, fileIds, clientRequestId и необязательную ссылку на объект ERP. Сервер возвращает taskId и состояние. ID внутренней сессии Codex не нужен внешнему клиенту и не предоставляется как возможность произвольного resume.

GET /api/agents возвращает только разрешённые профили и публичное описание возможностей. Внешний клиент не получает скрытые инструкции, пути или секреты. Для задач через API профиль лучше выбирать явно. Автовыбор в интерфейсе может предлагать только доступные профили; сервер повторно проверяет выбранную операцию.

Повтор clientRequestId в пределах пользователя/интеграции с тем же содержимым возвращает ту же задачу. Повтор того же ID с другим содержимым — конфликт. Для повторяемых сообщений и записей ERP также нужны устойчивые идентификаторы, чтобы сетевой повтор не создавал второй ход или вторую запись.

Самый простой вариант идентификации сотрудника в ERP — его персональный ключ приложения. Если позднее нужен один сервисный ключ от всей ERP, потребуется отдельное доверенное делегирование с проверяемой привязкой пользователя. Нельзя дать сервисному ключу произвольно указывать userId и автоматически действовать с его правами.

Webhook настраивается администратором заранее; задача не задаёт произвольный URL. Защита — согласованный механизм аутентификации/подписи, проверка адреса и повторов. Событие содержит минимальный разрешённый результат или ссылку для авторизованного получения. Доставка хранится отдельно от вычисления и повторяется независимо: сбой webhook не запускает расчёт снова. Сетевые тайм-ауты при записи в ERP требуют сверки фактического результата, а не безусловного повтора.

9. ИНТЕРФЕЙС

Сохраняем существующую контрастную палитру; приближаем организацию к Codex: слева проекты/диалоги и поиск, в центре переписка, внизу удобное многострочное поле и вложения, рядом выбор доступного специалиста и модели. Детали задания и результаты открываются в дополнительной панели.

Профиль показывает понятное назначение, а не технические параметры запуска. Состояния задания: в очереди, выполняется, нужен ответ, нужно подтверждение, завершено, ошибка, отменено, прервано. В закрытом сценарии показываем безопасные этапы и опубликованные результаты.

Администратору доступны пользователи, роли, проекты/источники, профили, правила, подключения и аудит. Сотруднику — его профиль, пароль, персональные ключи и разрешённая работа. Поиск по названиям и тексту учитывает права до формирования фрагментов, количества результатов и пагинации. Внутренние закрытые журналы в обычный поиск не попадают.

10. ПОДПИСКА CHATGPT

Техническая возможность exec использовать сохранённую ChatGPT-авторизацию подтверждается документацией. Автоматический переход на платный API при ошибке не нужен и запрещён требованиями. Токены из событий показывают использование, но не доказывают тип тарификации и точный остаток подписки.

Отдельная существенная поправка к раннему обсуждению: большой лимит личного Pro не является подтверждением, что этим аккаунтом разрешено обслуживать нескольких сотрудников через общий сервер. OpenAI описывает личный аккаунт как предназначенный для его владельца. Для командного запуска нужно согласовать допустимую модель аккаунтов/рабочего пространства и её соответствие условиям поставщика.

Архитектура должна хранить явную привязку пользователя/исполнения к авторизации Codex; не смешивать личные сессии разных владельцев. Официальная документация также описывает Codex access tokens для определённых Enterprise-сценариев автоматизации; это вариант для проверки применимости, а не обещание доступности в текущем Pro.

Наш API-ключ сотрудника и учётные данные OpenAI — разные вещи. Первый разрешает доступ к нашей оболочке, не превращает её в OpenAI API и не решает вопрос допустимости общего аккаунта.

Linux-размещение означает, что оболочка, файлы и выполнение инструментов находятся на своём сервере. Работа с моделью OpenAI остаётся сетевой; необходимые фрагменты данных могут попадать в модельный контекст. «Сервер у нас» не означает полностью локальную обработку моделью. Перед загрузкой реальных закрытых данных применяются согласованные правила организации.

11. ПОРЯДОК РЕАЛИЗАЦИИ И ПРОВЕРКИ

Этап 0. Среда и контракт интеграции — частично выполнен.
Закрепить Node/Codex, проверить Linux/Docker/HTTPS, хранение авторизации, sandbox, секреты, сеть и остановку процессов. Согласовать три SSO-операции, контекст, хранение/ротацию секрета, срок сессии и поведение блокировки. Сейчас локальная среда проверена, Docker/Compose подготовлены с выключенным исполнением. Linux-хост отсутствует; пользователь даст адрес позже. Контракт предложен, совместная реализация Fastkore не подтверждена. Неподтверждённые возможности не включать.

Этап 1. Хранилище, миграция и очередь — реализован в 0.5.
SQLite, резервная копия исходного JSON, сохранение всех ID/владельцев/учётных данных, атомарная очередь, отмена, дедупликация по пользователю и содержимому. Предусмотрены уникальная внешняя личность и поля будущей веб-сессии/ERP-контекста; сам SSO ещё не реализован. Проверены перезапуск, последовательность ходов, откат транзакции и отказ от подмены повреждённой SQLite устаревшей историей. Сбой не выдаёт частичный response как готовый результат.

Этап 2. Роли, источники и профили — реализован административный контур 0.5.
Пользователи, рабочие роли и правила, разрешённые профили/операции, реестр источников, модель/усилие/ограничение записи специалиста. Проверки одинаковы для браузера и персонального API-ключа, действуют во время работы и при запуске очереди. Изменение правил начинает свежую сессию; отзыв роли/ключа останавливает работу. Источники/Skills/закрытые операции только настраиваются и пока не исполняются. Регистрация закрытого источника блокирует все запуски в этой версии. Проверки бизнес-результатов относятся к этапам 4–5.

Этап 3. HTTPS, SSO и встроенный режим — следующий.
После согласования контракта реализовать нашу часть обмена билета на cookie-сессию, CSRF, доверенные установки, минимальные права первого входа, выход/истечение и сообщение контекста WebView2. ERP-разработчики параллельно выполняют свою часть. Сначала проверить с имитатором билетов, затем с настоящей Fastkore 2027. Результат: правильная личность и объект без повторного пароля; отказ на повтор/просрочку/подмену билета и произвольный адрес проверки; корректная смена ERP-пользователя. Срок сессии и скорость отзыва только со стороны ERP согласуются: проверка билета при входе не означает мгновенный отзыв всех старых сессий.

Этап 4. Изоляция и публикация результатов.
Подключить проверенный Linux-исполнитель: необходимые read-only источники, отдельное рабочее место, недоступность базы/чужих чатов/авторизации/Docker daemon, ограничения сети и инструментов. Разделить внутренние материалы и опубликованный результат. Проверить прямой обход, ошибки, журналы, имена файлов и поисковые фрагменты. До приёмки изоляции закрытые профили остаются выключенными. При задержке ERP разрешено выполнять независимые работы этого этапа, сохраняя SSO-приёмку открытой.

Этап 5. Оценщик: исходные Excel -> КП.
Штатный Skill читает необходимые части исходных файлов без обязательной нормализации. Неясности и отсутствующие данные явно запрашиваются. Сервер проверяет контракт, поля и арифметику, формирует согласованный документ. Проверить актуальность формул Excel. Приёмка — реальная небольшая заявка и эталонный расчёт после проверки защиты.

Этап 6. Оценщик -> технолог -> оценщик.
Ограниченные структурированные результаты между раздельными сессиями и источниками; необязательный этап технолога; повтор неудачного этапа; пересчёт зависимых результатов при изменении входа. Технолог не получает лишний прайс, результат относится к актуальной версии той же заявки.

Этап 7. Инструменты Fastkore и критические действия.
Подключить необходимые чтения текущего объекта через подтверждённый CLI/HTTP, затем согласованные записи. SSO-контекст сам по себе не доказывает право на объект; секрет проверки билетов не становится ключом к ERP-данным. Использовать штатные guards/dry-run/аудит, подтверждать конкретное действие и проверять фактический результат перед повтором. Windows-исполнитель добавляется только при доказанной необходимости и согласовании, поскольку найденный CLI предназначен для Windows.

Этап 8. API автоматических заданий и уведомления.
Реализовать /api/tasks, файлы, результаты и уточнения, устойчивую idempotency и защищённую доставку webhook. Те же права, что в веб-интерфейсе. Сбой доставки не перезапускает расчёт/запись. Интерактивная переписка уже предоставляется нашим интерфейсом в WebView2; второго нативного чата ERP нет.

Этап 9. Интерфейс, совместная приёмка и поставка.
Завершить навигацию в стиле Codex, поиск с правами, админку, профили, документы и адаптацию к окну WebView2. UX проверяется и по мере выполнения этапов. Проверить 11 критериев первого ТЗ с уточнением интерактивной работы и 10 шагов ТЗ № 3. Пользователь открывает заказ, нажимает прежнюю кнопку, входит без пароля и обсуждает этот объект разрешённым агентом. Выход/смена пользователя не раскрывают чужие данные. При выключенной интеграции действует прежний режим; при сбое активной нет автоматической смены ИИ. Передать исходники, сборку, Compose, инструкции логина/SSO/бэкапа/обновления и результаты испытаний.

Каждый этап завершается сборкой и необходимыми тестами. Имитаторы не заменяют реальную совместную приёмку. Проверки утечки включают вложенные инструкции, запрос цен по частям/в кодировке/примечаниях, подмену ID и извлечение промежуточных материалов. Они подтверждают проверенные ограничения, а не абсолютную невозможность утечки.

12. ЧТО ОБЯЗАТЕЛЬНО, ЧТО УСЛОВНО И ЧТО НУЖНО УТОЧНИТЬ

Обязательно: HTTPS, SSO по одноразовому билету, встроенный WebView2-режим и видимый контекст ERP; роли и серверные права; профили и обычные настройки; Skills; Linux-поставка; история/поиск; устойчивая очередь; изоляция; закрытые/опубликованные результаты; исходные Excel; ограниченная цепочка специалистов; API и доставка результата ERP; понятная авторизация; реальные проверки и документация.

Условно, только при доказанной необходимости: упаковка в Plugin; MCP; штатные подагенты внутри exec; переход выполнения на app-server; Windows-исполнитель; дополнительная граница выдачи секретов. App-server уже используется прототипом для каталога моделей — это не требует переводить на него сами задания.

Не входят: собственный агентный движок, микросервисная платформа, универсальный граф процессов, маркетплейс, отдельный сервер БД без причины, RAG/векторная БД по умолчанию, перенос всей ERP в нашу систему, универсальная нормализация прайсов, новая система резервного копирования.

Вопросы владельцу продукта/разработчикам Fastkore перед соответствующей интеграцией:
1) Какие конкретно операции первого сценария доступны через CLI/HTTP на целевой версии? Нужны их схемы, способ авторизации, тестовый сервер и аккаунт с ограниченными правами. Есть ли Linux CLI? Если нет HTTP-покрытия, приемлем ли небольшой Windows-исполнитель?
2) Какой состав КП разрешён менеджеру: цена за единицу, итог, срок, наименование, допущения? Какие поля закрыты? Приемлем ли остаточный риск косвенного вывода себестоимости из разрешённого результата?
3) Какие записи действительно нужны: сохранить расчёт, создать документ, изменить заказ, отправить КП? Кто подтверждает каждую критическую операцию?
4) Видит ли руководитель личные чаты сотрудников? Рекомендация для сохранения текущего поведения: да, но это прямо указано в интерфейсе; коллеги не видят их.
5) Какую допустимую модель ChatGPT-аккаунтов/рабочего пространства используем для сотрудников? Личный Pro на всех нельзя считать согласованным решением без проверки условий.
6) Кто предоставляет Linux-хост, адрес/сертификат HTTPS и небольшую контрольную заявку с эталонным результатом?

Отсутствие ответов не мешает реализовать общую основу и тестовые сценарии на искусственных данных. Оно мешает объявить готовой промышленную интеграцию и включить реальные закрытые данные/критические записи. Заглушка API не считается проведённой приёмкой с Fastkore.

Текущее положение: промежуточная версия 0.5.0 реализует этапы 1–2, сборка и 30 тестов успешны. Рабочая история сохранена; реальный Codex ChatGPT/resume проверен. Далее — Linux/HTTPS и согласованная SSO-интеграция. Пользователь сообщит адрес Linux позже. Репозиторий Fastkore/Agentic-platform становится местом дальнейшей работы. Открытые проверки не отмечаются завершёнными.
