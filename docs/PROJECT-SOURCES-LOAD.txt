ИСТОЧНИКИ ПРОЕКТА — НАГРУЗОЧНЫЙ ЗАМЕР (AC14, ПРЕДВАРИТЕЛЬНЫЙ)
17.11.2026 · исполнитель. Это уменьшенный замер, НЕ приёмочный: целевой корпус ТЗ — 50 000 файлов и 10 ГиБ на согласованном стенде.
Сырые данные: docs/project-sources-load-50k.json. Повтор: npx tsx tools/sources-load.mts --files 50000 --gib 10 --uploads 5 --work <папка>.

СТЕНД
Контейнер исполнителя: 2 vCPU Intel Xeon 2.30 GHz, 7,8 ГиБ RAM, Linux 6.18, Node 24.22.1, локальный диск (NVMe за виртуализацией).
Хранилище объектов — файловый драйвер (MinIO недоступен), сеть — loopback HTTP. Платформа — отдельный процесс; загрузка — утилита
tools/source-upload.mjs через HTTP API с токеном источника, параллелизм частей 4.
Корпус: 50 000 файлов C# в 3 500 папках, 1 078 441 277 байт (≈1,0 ГиБ), детерминированный генератор; плюс 4 параллельные загрузки
по 1 000 файлов (≈21 МБ) в другие источники.

РЕЗУЛЬТАТЫ
Полная загрузка 50 000 файлов (одновременно с 4 другими сессиями)      160,1 с   (≈6,7 МБ/с, ≈312 файлов/с)
Параллельные малые загрузки, 1 000 файлов каждая                      7,6–16,4 с
Подготовка для агента (индексация 50 000 файлов)                       138,6 с
Повторная загрузка без изменений                                       33,5 с, передано 0 частей, повторно использовано 50 000 файлов
Изменено 5 000 файлов, обрыв после 1 600 частей, возобновление         81,5 с суммарно; после возобновления 3 400 частей; дублей нет
Пиковая память процесса платформы (VmHWM)                              459 МиБ
Поиск (точная подстрока), 5 параллельных читателей, 1 000 запросов     p50 8,6 мс, p95 15,6 мс
Чтение 200 строк, 5 параллельных читателей, 1 000 запросов             p50 3,7 мс, p95 10,4 мс
Цель ТЗ p95 ≤ 2 с выполнена на этом объёме; на 10 ГиБ не измерялось.

РАЗМЕР ИНДЕКСА
Индекс триграмм без позиций (миграция v3, detail=none) ≈ 1,9× объёма текста на один снимок; до миграции — ≈3,4×.
Индекс строится на снимок: при 3 снимках почти одинакового корпуса sources.sqlite занял 6,4 ГБ.
Оценка для 10 ГиБ: ≈19 ГиБ индекса на снимок.
План (не реализован): индексировать текст по объекту (blob), а не по файлу снимка, чтобы неизменившиеся файлы разных версий
разделяли строки индекса; это сократит объём и время подготовки новых версий пропорционально доле неизменившихся файлов.

ВЫВОДЫ И ОГРАНИЧЕНИЯ
- Память загрузчика и сервера не растёт пропорционально каталогу: манифест и статус постраничные, части по 8 МиБ.
- Пропускная способность ограничена числом запросов на файл (мелкие файлы); для 10 ГиБ ожидаемо десятки минут на 2 vCPU.
- Не измерено: 10 ГиБ, MinIO по сети, 5 разных пользователей с отдельными сеансами, холодный кеш, восстановление из копии на объёме.
- AC14 считать НЕ выполненным до прогона на согласованном стенде.
