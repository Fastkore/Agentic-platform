1. ЦЕЛЬ И ПРИНЯТЫЕ ПРОДУКТОВЫЕ РЕШЕНИЯ

Дать сотрудникам возможность задавать вопросы по большим каталогам исходного кода, документации и прайс-листов. Агент находит подтверждение в нужной версии материалов, прослеживает логику и объясняет результат. Основной сценарий — поддержка FastCore Business с доступом к исходникам конфигурации и платформы. В существующем коде и интерфейсе используется написание Fastkore; не переименовывать продукт или идентификаторы в рамках этой задачи.

Источник — именованный корневой каталог со всеми вложенными каталогами и файлами, кроме явно исключённых. Он содержит описание назначения и правила доступа. Источник не равен отдельному файлу, бакету, проекту чата или профилю специалиста.
Снимок источника — неизменяемое состояние принятого каталога после одной завершённой загрузки. Для исходников указывается версия; для прайс-листов — период действия. Дата загрузки хранится отдельно.
Проект — основное место настройки использования источников. Например, в проекте «Техническая поддержка» подключены Fastkore Business, Fastkore Platform и документация. Специалисты этого проекта получают назначенный им набор материалов.
Источники хранятся в общем реестре установки. Один источник и снимок можно подключить к нескольким проектам без повторной загрузки и копирования содержимого. Общий реестр сам по себе не даёт сотруднику доступа.
Содержимое хранится в закрытом S3-совместимом хранилище MinIO. База приложения содержит каталог, состояния загрузки, версии, связи, права и поисковые индексы.
Git не является обязательным условием. Пользователь выбирает папку на своём компьютере.

2. ОБЯЗАТЕЛЬНОЕ ОБСЛЕДОВАНИЕ ПЕРЕД РЕАЛИЗАЦИЕЙ

Прочитать README.md, AGENT-PLATFORM-MARKETING.md, AGENT-PLATFORM-OVERVIEW.md, docs/IMPLEMENTATION-PLAN.txt, docs/CODEX-WORKER.md и применимые AGENTS.md. Указанные далее наблюдения относятся к рабочему дереву на 17.11.2026 и должны быть сверены с актуальным кодом.
Не заменять стек: TypeScript, Node.js, React, Fastify, SQLite, существующая очередь и исполнитель. Новые инфраструктурные компоненты вводить только при доказанной необходимости; для первой версии достаточно существующей базы и MinIO.
В рабочем дереве уже есть незакоммиченные изменения других задач. Сначала зафиксировать git status; не сбрасывать, не перезаписывать и не включать чужие изменения в свой коммит. Особое внимание: server/workspace.ts, server/corporate.ts, server/app.ts, shared/types.ts и настройки специалистов уже изменяются.

Проверенная основа:
- server/file-storage.ts: S3 для вложений; ключ projects/<projectId>/<fileId>, чтение файла целиком, предел 20 МиБ. compose.minio.yaml содержит отдельную внутреннюю сеть MinIO. Это заготовка подключения, а не готовое хранилище каталогов.
- server/knowledge.ts и shared/knowledge.ts: разделы fastkore/company, содержимое BLOB в knowledge.sqlite, FTS5, фрагменты по 4000 символов; 500 файлов и 256 МиБ суммарно. Нет структуры каталогов и индексации типичных расширений исходного кода.
- server/knowledge-tools.ts: index/search/read; server/knowledge-routes.ts: административные операции. Проверить подключение инструментов для каждого поддерживаемого исполнителя.
- server/documents.ts: attachmentName оставляет только имя файла; применять его к относительному пути каталога нельзя.
- server/upload-admission.ts: одиночная загрузка до 20 МиБ, один активный запрос на пользователя, таймаут 60 секунд. Новый протокол загрузки каталога не должен наследовать эти ограничения как общий предел каталога.
- shared/types.ts: Dataset хранит directory, projectIds, classification; AgentProfile.datasetIds и WorkRole.readDatasetIds являются существующими настройками. Их наличие не означает готового исполнения.
- server/corporate.ts: saveDataset регистрирует папку на сервере; unavailable блокирует профили при наличии restricted-источника, а также профили с datasetIds. Не снимать блокировку без замены эквивалентными серверными и исполнительными ограничениями.
- client/ProjectSpecialistsDialog.tsx, ProjectAgentPolicy и server/corporate.ts: есть подключения специалистов к проекту, разрешения инструментов и отдельных файлов библиотеки.
- server/workspace.ts и server/worker-files.ts: обычные файлы могут передаваться исполнителю и превращаться в результаты. Закрытые исходники нельзя автоматически включать в этот маршрут.

3. ПОЛЬЗОВАТЕЛЬСКИЙ ИНТЕРФЕЙС И МЕСТА НАСТРОЙКИ

3.1. Проект → «Источники» — основной экран.
Показывать имя, тип, выбранную версию либо правило выбора по дате, период действия, состояние индексации, число файлов, объём, дату обновления, назначенных специалистов и режим результата. Действия: создать источник и загрузить каталог; подключить существующий; загрузить новый снимок; выбрать снимок/набор версий; настроить специалистов; отключить от проекта; посмотреть историю.
Создание источника из проекта создаёт его в реестре и подключение к текущему проекту. Новый источник виден управляющим; чтение агентом включается только после явного назначения специалистам и готовности снимка. Доступ всем специалистам по умолчанию запрещён.
Технические настройки бакета и S3-ключи в этом экране не показывать.

3.2. Проект → «Связи» — сводка, доступная из экрана источников и специалистов.
Матрица: строки — источники, столбцы — подключённые специалисты. В ячейке — разрешённое использование и режим выдачи. При выборе ячейки видны эффективные права и причина недоступности, если есть.
Рядом показывать выбранный набор версий: «Business A → Platform X → Документация D», либо режим «Прайсы на дату». Вся сводка строится сервером из тех же политик, которые проверяются при выполнении; отдельные несогласованные настройки в UI запрещены.

3.3. Проект → «Специалисты» → выбранный специалист.
Показывать его источники именно в текущем проекте, разрешённые действия и выдачу; редактирование использует те же привязки, что матрица. Глобальный профиль специалиста задаёт методику и верхние ограничения, но не подключает источники ко всем проектам автоматически.

3.4. Настройки → «Источники» — общий административный реестр.
Показывать владельца/управляющих, тип, снимки, квоту, состояние, а также «Где используется»: проекты, привязки, специалисты, активные наборы версий. Перед удалением или изменением политики показывать затронутые связи. Управляющий проектом видит только разрешённые ему проекты; глобальный администратор — все связи установки.

3.5. Настройки → «Сервер / Хранилище».
Подключение MinIO, отдельный закрытый бакет источников, проверка соединения, лимиты и состояние обработчиков. Секреты остаются на сервере.

3.6. Чат и обращение поддержки.
Компактный индикатор используемого набора версий/даты. В ответе — разрешённые ссылки на основание: источник, снимок, относительный путь и строки либо раздел документа. Ссылка не является ссылкой скачивания. Пользователь без права просмотра оригинала видит только разрешённые метаданные основания.
Обычному сотруднику нельзя менять привязки, версии проекта и права. При нескольких допустимых версиях он может выбрать только заранее разрешённый проектом набор.

4. МОДЕЛЬ ДАННЫХ И ЕДИНЫЙ ИСТОЧНИК ПРАВДЫ

Названия сущностей ниже логические; согласовать с текущими типами, сохранив смысл и ограничения.
Source: id, installation/tenant scope при наличии многопользовательской границы организации, name, description, kind (code/documents/prices/mixed), classification, managers, policyRevision, createdAt, archivedAt.
SourceSnapshot: id, sourceId, label/version, createdBy, uploadedAt, validFrom, validTo, state, manifestHash, totalFiles/bytes, indexedFiles, extractionErrors, indexGeneration, exclusionRules и результат предварительной проверки. После ready содержимое и манифест неизменяемы.
SourceFile: snapshotId, fileId, relativePath, blobId, sha256, size, mediaType, encoding, extractionState, lineCount; уникальность пути внутри снимка. Папки восстанавливаются из путей; пустые папки можно сохранять отдельной записью манифеста.
Blob: opaque id, source scope, objectKey, sha256, size, lifecycle state. Повторное использование проверенных объектов — внутри того же источника; не делать глобальную межорганизационную дедупликацию с раскрытием наличия файлов.
UploadSession: actorId, sourceId, expectedRevision, manifest, file states/parts, expiry, progress, failure code. Состояние устойчиво к перезапуску.
ProjectSourceBinding: id, projectId, sourceId, selector (pinned snapshot / effective-date), approvedSnapshotIds для выбора по дате, allowed actions, output policy, revision, enabled. Запреты источника не расширяются привязкой.
ProjectSpecialistSourceGrant: projectId, profileId, bindingId, enabled и дополнительные сужающие ограничения. Уникальный ключ связи; отсутствие записи означает отсутствие доступа.
ProjectSourceBundle: projectId, id, label, immutable revision, набор bindingId→snapshotId, проверенные связи зависимостей, состояние active/archived. Позволяет атомарно назначить совместимую пару конфигурации и платформы.
SourceDependency: snapshotId конфигурации → конкретный snapshotId платформы, вид связи и кто подтвердил. Не выводить совместимость автоматически из одинаковых номеров версий.
RunSourceScope: runId, projectId, actorId, profileId, выбранные binding/snapshot IDs, effectiveDate, revisions политик и индекса. Фиксируется при постановке задания в очередь; актуальные разрешения перепроверяются при запуске, каждом инструменте и публикации.

Ссылки защищаются внешними ключами/эквивалентными транзакционными проверками. Обновление политик требует expected revision; конфликт даёт 409. ProjectAgentPolicy и новые привязки имеют одну каноническую модель: не поддерживать параллельно расходящиеся projectIds/datasetIds и матрицу.

5. ВЕРСИИ, ДАТЫ И ВЫБОР ИСТОЧНИКОВ

Код: по умолчанию явно закреплённый снимок и набор совместимых версий. Загрузка новой версии не переключает работающие проекты. Выбор нового набора — отдельное действие управляющего, атомарное для всех входящих привязок.
Чат закрепляет выбранный набор; изменение набора проекта не меняет молча уже начатый диалог. При переключении показывается событие и создаётся новый контекст исполнителя, чтобы старый код не остался скрытым основанием ответа. В истории сохраняется указание прежних версий.
Прайсы: validFrom обязателен для режима выбора по дате; validTo необязателен. Интервал [validFrom, validTo), даты YYYY-MM-DD в явно заданной бизнес-зоне проекта; createdAt/uploadedAt — UTC timestamps. Для старого снимка период меняется только отдельной аудируемой редакцией метаданных; содержимое неизменно.
Дата расчёта берётся из явно проверенного контекста операции либо из указания пользователя. Если её нет, агент спрашивает или использует явно настроенное правило проекта «текущая бизнес-дата», обозначая эту дату в ответе. Никогда не подменять дату действия датой загрузки.
Выбор по дате осуществляется только среди ready-снимков, допущенных в данной привязке. Пересечение периодов даёт конфликт и требует выбора; отсутствие подходящего периода даёт «Нет действующего источника». Не выбирать произвольно самый новый файл.
Документы: можно закрепить снимок или выбрать по периоду действия. Отдельные источники имеют собственные версии; вся документация не обязана обновляться вместе с кодом.
Переходы к зависимому коду разрешены только внутри выбранного набора и доступных источников. Для отсутствующей платформы агент сообщает, что цепочка не проверена полностью.
Удалённые из нового каталога файлы отсутствуют в новом снимке; прежний снимок остаётся воспроизводимым. Изменение исходников на диске во время загрузки обнаруживается проверкой размера/хеша и требует повторной передачи файла.

6. ЗАГРУЗКА КАТАЛОГА

Обязательный первый клиент — браузер: выбор каталога с сохранением относительных путей, без необходимости Git или установки CLI. Проверить Chromium и используемый WebView2; при недоступности выбора каталога показать понятное объяснение и поддержанный способ через локальную утилиту.
Локальная утилита — второй клиент того же API, входит в полный объём ТЗ: команда с путём, sourceId, версией/датами, сервером; dry-run, загрузка, возобновление и отчёт. Авторизация короткоживущим ограниченным токеном пользователя через существующую модель доступа. Пароли и S3-ключи не передаются в аргументах команд и логах. Утилита не открывает произвольную локальную папку по запросу сервера/модели.
Сначала сканирование и манифест, затем предварительный просмотр: дерево, количество, объём, типы, исключения, ошибки и отличия от выбранного предыдущего снимка. Абсолютный путь на компьютере не нужен серверу и не сохраняется в общем журнале.
По умолчанию исключать .git, node_modules, bin, obj, кеши, временные файлы, файлы окружения с секретами, закрытые ключи и архивы резервных копий. Полный список отображается и сохраняется в сессии. Не считать все конфигурационные XML/JSON секретами. Сканировать подозрительные секреты; их загрузка приостанавливается до исключения либо явно аудируемого решения управляющего. Не обещать полного обнаружения секретов.
Браузерное исключение не гарантирует обнаружения символьных ссылок. Локальная утилита не следует symlink/junction/reparse points и не выходит за выбранный корень. Сервер всегда проверяет пути независимо от клиента.
Пути относительные, разделитель '/', без абсолютных путей, drive prefixes, '..', '.', пустых компонентов, NUL и управляющих символов. Проверять декодирование, длину и Unicode. На межплатформенном импорте отклонять неоднозначные коллизии регистра/нормализации с указанием файлов; не перезаписывать молча. Пользовательский путь никогда не применяется как произвольный серверный filesystem path.
Манифест передаётся страницами. Файлы загружаются с ограниченным параллелизмом; большие файлы частями. Не собирать каталог или ZIP целиком в RAM. Архивный импорт и распаковка не входят в первый этап и не подменяют загрузку каталога.
Сервер проверяет размер и SHA-256 принятого содержимого. Клиентский хеш не является доказательством наличия или корректности объекта. Пропуск неизменившихся объектов разрешён только после серверной проверки их принадлежности тому же источнику и доступности пользователю.
Каждая операция создания/завершения имеет ключ идемпотентности. Повтор с другим содержимым даёт 409. Повтор одной части не создаёт дубль; конфликт содержимого отклоняется. Авторизация проверяется также при возобновлении и завершении.
«Обновить из папки» сравнивает пути, хеши и период действия с последним готовым снимком либо явно выбранной базой. При совпадении возвращается существующий снимок без новой версии и индексации. При изменении отправляются недостающие объекты и создаётся новый снимок. Явное создание отдельной версии с теми же файлами доступно, когда нужно зарегистрировать отдельный релиз.
После разрыва соединения пользователь повторно выбирает папку, если браузер утратил доступ, и продолжает с подтверждённых частей/файлов. При несовпадении манифеста требуется новая сессия либо явно пересогласованный файл до фиксации снимка.
Отмена, срок жизни сессии и сборка бесхозных объектов обязательны. Сбой MinIO или перезапуск приложения не должен давать ready для неполного снимка. Занятый обработчик возвращает состояние очереди, а не теряет принятую работу.
В UI показывать отдельно «Передача файлов» и «Подготовка для агента»: байты/файлы, текущий этап, ошибки, повтор, отмена. Принятый оригинал без текста получает честный статус «Не доступен для поиска».

7. ХРАНЕНИЕ И ФОНОВАЯ ОБРАБОТКА

Использовать отдельный закрытый бакет источников с минимальными полномочиями серверного сервиса. Один бакет может хранить много источников. Внутренняя структура ключей: sources/<sourceId>/blobs/<blobId>; дерево хранится в манифесте и SourceFile. Ключи непрозрачны для пользователя и агента.
Настройки хранилища источников отделить от переключателя local/s3 обычных вложений. Переключение вложений не должно менять расположение или доступность уже загруженных источников. При отсутствии S3 экран показывает «Хранилище источников не настроено»; не складывать закрытые материалы в библиотеку проекта автоматически.
SQLite хранит метаданные, индексы и задания обработки, но не оригиналы новых каталогов. Индексы содержат закрытый текст и защищаются наравне с оригиналами.
Состояния: uploading → verifying → indexing → ready; ошибки failed, отмена cancelled; удаление/архивирование отдельно. Готовность требует проверенного манифеста и завершённой обработки всех файлов с явным результатом для каждого.
Допускается ready с известными неподдерживаемыми форматами: UI и инструменты показывают покрытие и перечень пропусков. Сбой поддерживаемого анализатора не маскировать как полный успешный индекс; разрешение частичного покрытия — явное решение управляющего с предупреждением в ответах агента.
Индексация выполняется устойчивой фоновой очередью с ограничениями CPU/RAM/времени, lease/heartbeat, восстановлением после остановки и идемпотентностью. Извлечение PDF/Office — изолированными процессами/worker с лимитами. Не исполнять загруженный код, макросы и скрипты, не ставить зависимости из загруженного каталога.
Индекс готовится новой генерацией и включается атомарно. Не смешивать результаты разных snapshot/indexGeneration. Кеши ключуются снимком и областью доступа; изменение политики инвалидирует доступ.
Удаление источника: сначала архивирование/отключение; физическое удаление только когда нет действующих привязок, заданий и защищённых удержанием снимков. Поддержать явное снятие зависимостей, политику срока хранения и сборку только объектов с нулевыми ссылками. Не удалять используемые другими проектами версии.
Резервная копия согласует SQLite, манифесты и MinIO; проверка восстановления входит в приёмку. После восстановления проверяются наличие объектов и хеши, а индекс можно перестроить. Для SQLite не копировать один файл работающей WAL-базы.

8. ИНДЕКСАЦИЯ И ИНСТРУМЕНТЫ АГЕНТА

Первая работающая версия: дерево, точный поиск имени/подстроки/идентификатора, полнотекстовый поиск, чтение диапазона строк и подтверждённые ссылки на источник. Векторный поиск необязателен и не заменяет точный поиск. Не вводить внешнюю платную службу индексации без отдельного согласования.
Перед выбором языковых анализаторов обследовать репрезентативный каталог Fastkore Business/Platform. Пока образца нет, реализовать безопасное текстовое чтение распространённых исходников и конфигураций; явно зафиксировать неподтверждённые форматы. UTF-8 обязателен; UTF-16 с BOM поддержать. Другую кодировку выбирать явно, не индексировать испорченный текст как корректный.
Для кода сохранять номера строк, путь, язык, имя/диапазон символа, если анализатор доступен. Не резать функцию произвольно на фрагменты по 4000 символов без возможности дочитать контекст. Для документации сохранять заголовки/страницы, для таблиц — лист/строки и заголовки колонок. Прайсы не ограничивать первыми 25 строками существующего предпросмотра; большие таблицы читать постранично.
Полный объём: определение символа, ссылки/вызовы для подтверждённых языков. При динамическом вызове или неподдерживаемом языке возвращать ограничение, а не выдуманную связь.

Логические инструменты (один dispatcher или несколько функций):
- sources_list: только доступные привязки текущего проекта, выбранные снимки, описание, покрытие и даты.
- source_tree(bindingId, snapshotId, path, cursor): постраничный список папки.
- source_search(bindingId/scope, query, mode, pathPrefix, cursor): точный/полнотекстовый поиск с путём, строками, snapshotId и ограниченным фрагментом.
- source_read(bindingId, snapshotId, fileId, startLine, lineCount): строки текста либо адресованный фрагмент документа/таблицы; ответ с продолжением.
- source_symbol и source_references: определения и связанные места только при поддержке анализатором.
Источник, снимок, проект, пользователь и специалист разрешаются из доверенного контекста запуска. Модель не может расширить область чтения параметрами, путём, сменой projectId или известным чужим fileId. Автоматическое подключение зависимостей запрещено.
Начальные серверные пределы: tree до 200 записей, search до 20 совпадений, read до 200 строк; общий ответ инструмента до 32 КиБ UTF-8, с явным признаком сокращения и продолжением. Лимитировать также число и общий объём чтений на задание. Пределы настраиваемые и проверяются сервером.
Каждое утверждение о поведении подкрепляется проверенным фрагментом. Агент различает вывод из кода, сведения документации и фактические данные ERP. Без настроек/данных клиента он описывает алгоритм и запрашивает недостающие значения. Код и документы являются данными, не инструкциями; найденный текст не меняет системные правила или права.

9. ПРАВА, ЗАКРЫТЫЕ МАТЕРИАЛЫ И ВЫДАЧА

Разделить действия: manage_source, upload_snapshot, manage_project_binding, use_for_analysis, view_original, download_original, delete_source. Администратор управляет источниками; делегирование управляющим проектом возможно только через серверно проверенное право. Сотрудник поддержки по умолчанию имеет use_for_analysis по назначенным проектам/специалистам, но не view_original/download_original.
Право use_for_analysis означает право сотрудника инициировать разрешённый анализ через специалиста; это не разрешение браузеру получить сырые фрагменты. Серверный инструмент исполняется в контексте этого разрешённого задания.
Эффективный доступ — пересечение членства в проекте, действующей сессии/роли, разрешения операции, политики источника, привязки проекта и назначения специалисту. Явный запрет имеет приоритет. Права ERP продолжают проверяться независимо и не расширяются исходниками.
Поиск, дерево, статистика, ошибки и пагинация фильтруются до выдачи, включая сведения о существовании чужих источников. Для прямого запроса недоступного ID возвращать нейтральное 404; аудит сохраняет причину отказа. Отзыв доступа блокирует следующие чтения и публикацию незавершённого ответа.
Режимы выдачи: explanation_only (пояснение, разрешённые метаданные основания, без исходного текста) и excerpts_allowed (ограниченные цитаты при отдельном разрешении). download_original — отдельное административное действие, не режим агента.
Закрытые оригиналы не копируются в обычную рабочую папку исполнителя, библиотеку проекта, attachments/output, экспорт чата и общие кеши. Не выдавать модели S3-ключи, object keys, presigned GET или произвольный filesystem/network-доступ к хранилищу.
Для закрытого анализа сырой результат инструментов хранится во внутреннем контуре. Он не транслируется сотруднику через события, SSE/WebSocket, отладочные панели, истории инструментов, API run details или экспорт. Открывать пользователю только разрешённый итог и метаданные оснований. Проверить все поддерживаемые провайдеры; неподдерживаемый режим закрытого анализа блокируется, а не откатывается к обычному чату.
До проверки политики публикации ответ закрытого анализа не стримится пользователю. Контроль должен охватывать текст, вложения, ссылки, кодировки/архивы, таблицы, сообщения ошибок и уточняющие вопросы. Файловую выдачу для explanation_only отключить сервером. Проверять совпадения с исходным текстом и ограничения цитирования; фильтр/вторая модель — дополнительные меры, а не доказательство отсутствия утечки.
Смена прав, проекта, специалиста или набора версий требует нового контекста исполнителя/инвалидации прежней сессии, иначе старые прочитанные фрагменты останутся в памяти. Уже опубликованные разрешённые ответы нельзя отозвать из памяти пользователя; история хранит исходный scope и не открывает оригиналы по новым ссылкам.
Абсолютная гарантия невоспроизведения текста моделью, которая читает исходники, не заявляется. Гарантируется серверный запрет скачивания/экспорта оригиналов и отсутствие прямого пути доступа. Если владелец требует полного исключения передачи кода модели, нужен другой режим: заранее подготовленная проверенная документация без исходников в контексте; это отдельное изменение требований.
Перед реальными закрытыми данными проверить допустимость выбранного внешнего провайдера исполнения, хранение его сессий/журналов и существующую политику организации. Не подключать новый внешний сервис для исходников автоматически.
Текущую глобальную блокировку restricted заменить адресной только после проверки изоляции на целевом Linux. Обычные чаты затем должны работать независимо от наличия закрытых источников; закрытый анализ остаётся недоступным на непроверенных исполнителях.

10. API И СОГЛАСОВАННОСТЬ

Использовать авторизацию и соглашения существующего Fastify API. Ни один endpoint не доверяет userId/profileId из тела вместо контекста сеанса/задания. CSRF/origin-защита для cookie mutations — по существующей модели приложения, с тестами для новых маршрутов.
Предлагаемые группы маршрутов:
- /api/admin/sources: реестр, создание, политика, архивирование; выдача только разрешённым управляющим.
- /api/admin/sources/:sourceId/snapshots: список, метаданные, периоды и зависимости.
- /api/admin/sources/:sourceId/uploads: создание сессии; /:uploadId/manifest — страницы; /files/:fileId/parts/:part — загрузка; /status, /complete, /cancel — управление. Точные методы документировать в API.md до сдачи.
- /api/projects/:projectId/source-bindings: просмотр и изменение привязок с revision.
- /api/projects/:projectId/source-bundles: совместимые наборы, выбор активного набора.
- /api/projects/:projectId/source-matrix: эффективные связи и причины отказов.
- Оригиналы — отдельные административные маршруты с view/download проверками; агентские инструменты не используют браузерный download endpoint.
Изменяющие операции журналируются; создание/завершение загрузок идемпотентны. Коды: 400 валидация, 401 отсутствие сеанса, 403 запрещённое административное действие, 404 недоступный объект, 409 конфликт/неоднозначная версия, 413 квота, 429 лимит, 503 временная недоступность хранилища. Ошибки не содержат секретов и внутренних путей.
До приёма байтов резервировать квоту с учётом параллельных сессий; при отмене освобождать. Дополнительная проверка перед ready. Операции между SQLite и S3 строятся как восстанавливаемые шаги: сначала проверенные объекты, затем атомарная фиксация ссылок; бесхозные объекты очищает отложенный сборщик.

11. МАСШТАБ, ОГРАНИЧЕНИЯ И НАБЛЮДАЕМОСТЬ

Целевой приёмочный каталог: 50 000 файлов, суммарно 10 ГиБ; до 100 МиБ на файл; не менее 5 одновременных сессий загрузки разных пользователей с ограниченной общей конкуренцией. Это требования к новой подсистеме, а не изменение лимитов обычных вложений.
Лимиты файлов, размера, глубины (начально 64), длины пути (начально 1024 символа), одновременных операций и дисковой квоты задаются конфигурацией. Слишком большой текст обрабатывается потоком или получает явный статус ограниченного покрытия; он не должен приводить к падению API.
Память загрузчика не растёт пропорционально суммарному размеру каталога; манифест/дерево тоже постраничные. Интерфейс использует ленивое дерево и виртуализацию длинных списков.
На стенде зафиксировать CPU/RAM/диск/сеть и размеры корпуса; измерить полную и повторную загрузку, восстановление, индексацию, p50/p95 поиска и чтения, пиковую память. Цель для прогретого индекса на согласованном стенде: p95 поиска/чтения до 2 секунд при 5 параллельных заданиях. Не объявлять соответствие без замеров; отклонения описывать с причиной и планом.
Аудит: actor, project, specialist, source, snapshot, run, действие, решение доступа, revision, время, объём, результат. Не писать исходники, секреты, полный текст запроса или токены в обычные журналы. Доступ к внутренним диагностическим данным ограничен.
Метрики: очередь, ошибки, прогресс, пропуски форматов, размер индекса, S3-задержки, квоты и бесхозные объекты. Администратор видит причину «источник не готов» без доступа к серверной консоли.

12. СОВМЕСТИМОСТЬ И МИГРАЦИЯ

Сохранить общую базу Fastkore/company и обычные вложения: не переносить их автоматически и не расширять их доступ. При необходимости дать отдельный явный импорт документа в новый источник.
Существующие Dataset с server directory оставить как legacy-конфигурацию без автоматически открытого доступа. Мастер импорта может создать новый источник из выбранного администратором серверного каталога с теми же проверками и предварительным просмотром. Браузер не получает произвольную серверную файловую навигацию.
Перенос datasetIds/readDatasetIds/projectIds — отдельная версионируемая миграция с отчётом. Не превращать старое право чтения в неограниченное использование во всех проектах. Неоднозначные назначения остаются выключенными до настройки.
Миграции SQLite транзакционные, повторяемые и с проверкой версии; резервная копия и инструкция отката обязательны. Обновить API.md, README.md и документы развёртывания. Изменения в уже редактируемом IMPLEMENTATION-PLAN.txt делать точечно, сохраняя чужую работу.
Перенос чата между проектами не переносит привязки источников. Проверить доступ к истории, сбросить контекст исполнителя, показать несовпадение источников. Передача задачи другому специалисту не переносит его права или сырые фрагменты автоматически.

13. ПОЭТАПНАЯ РЕАЛИЗАЦИЯ

Этап A — обследование и контракты: карта текущих модулей, каноническая модель связей, миграции, API, проверка форматов реального образца и способа изоляции. Зафиксировать неопределённости в TODO; отсутствие образца не блокирует базовый загрузчик/текстовый поиск, но блокирует заявление о поддержке всех форматов Fastkore.
Этап B — каталог и загрузка: реестр, снимки, MinIO, возобновляемые сессии, манифесты, хеши, очередь и браузерный выбор папки. Проверять на искусственных данных.
Этап C — проектные связи: экран источников, матрица, специалисты, наборы версий, периоды прайсов, effective scope и его фиксация в заданиях.
Этап D — знания: индексация, дерево, поиск, чтение, ссылки, инструменты и анализ цепочки Business → Platform. Анализаторы символов для подтверждённых языков.
Этап E — закрытый анализ: права, внутренние результаты инструментов, контроль публикации, изоляция, отзыв доступа и адресная замена блокировки. До этого этапа закрытый сценарий не включать для реальных материалов.
Этап F — эксплуатация: локальная утилита, нагрузка, аварийные сценарии, сборка мусора, резервное восстановление, документация и финальная приёмка.
Полное выполнение включает A–F. Частичный этап не выдавать за реализацию всего ТЗ. Публикация/перезапуск production и загрузка реальных исходников не являются частью написания кода и не выполняются автоматически.

14. ОБЯЗАТЕЛЬНЫЕ СЦЕНАРИИ ПРИЁМКИ

AC01. Загрузить каталог с вложенными папками, кириллицей и одинаковыми именами файлов в разных папках: пути и содержимое сохранены, файлы различимы.
AC02. Оборвать передачу, закрыть клиент, перезапустить сервер, продолжить: подтверждённые объекты не загружаются повторно, частичный снимок не виден агенту, дубликатов нет.
AC03. Повторить запросы завершения и части; подменить хеш/размер; изменить файл при чтении; превысить квоту параллельными загрузками: корректные конфликты, нет повреждённого ready и превышения резерва.
AC04. Проверить '..', абсолютные пути, кодированные разделители, Unicode/регистр, symlink/junction у утилиты и вредоносный манифест: выход за корень и неоднозначные записи отклоняются.
AC05. Новый снимок добавляет/изменяет/удаляет файлы; старый остаётся доступен разрешённым заданиям. Неизменившиеся данные не пересылаются. Новый снимок не меняет активные привязки сам.
AC06. Один источник подключён к двум проектам и двум специалистам с разными правами: дерево, поиск, чтение, матрица и API согласованы; неизвестный/чужой ID не раскрывает содержимое и метаданные.
AC07. Business A связан с Platform X, Business B — с Y. Проверить вопрос, затрагивающий обе части: ответ использует одну выбранную пару, содержит проверяемые строки, не смешивает версии.
AC08. Прайсы с датами: границы периода, открытый конец, пересечение, пробел, загрузка задним числом и отсутствие даты в вопросе. Выбор воспроизводим и не зависит от upload time. Нужная цена после 25-й строки найдена.
AC09. Сотрудник explanation_only получает объяснение, но не оригинал через download, attachments, экспорт, события, журнал инструментов или ошибки. Администратор скачивает только при отдельном разрешении.
AC10. Попытки получить исходник целиком/частями/base64/файлом, инструкции внутри кода, ссылки на внешний адрес и запрос выгрузить каталог проверены. Отчёт различает технически закрытые каналы и остаточный риск текстового воспроизведения моделью.
AC11. Отозвать право во время очереди/чтения/публикации; сменить специалиста/проект/набор; перенести чат: новые чтения и публикация запрещены, старый контекст не переиспользуется, соседний разрешённый проект работает.
AC12. Недоступный MinIO, падение индексатора, неподдерживаемая кодировка/формат и частичная индексация: честные статусы, безопасный повтор, нет потери старой рабочей версии.
AC13. Удаление/архивирование источника, занятого другим проектом или заданием; очистка отменённой загрузки; резервное восстановление: ссылки и используемые объекты не повреждены.
AC14. Нагрузка по разделу 11 с протоколом стенда и измерений. Маленький smoke-test не заменяет нагрузочный отчёт.
AC15. Регрессии: обычные чаты, общая база знаний, библиотека проекта, SSO, роли, специалисты, выдача обычных результатов и все поддерживаемые провайдеры. Для неподдержанного закрытого режима — явный запрет.
AC16. На реальном обезличенном/разрешённом образце подготовить набор минимум из 10 вопросов поддержки: расчёты, происхождение поля, условия ветвления, ошибка, зависимость платформы, недостаток данных. Ожидаемые основания заранее проверяет человек; измерить правильность ссылок, версий и честность ограничений.

15. ПЕРЕДАЧА ВНЕШНЕМУ АГЕНТУ И ПОСЛЕДУЮЩАЯ ПРОВЕРКА

Внешний агент реализует ТЗ и обновляет PROJECT-SOURCES-TODO.txt после каждого законченного этапа. Для каждого пункта указать изменённые файлы/коммит, команды и результаты проверок, ограничения и следующий шаг. Секреты, исходники пользователя и полные дампы журналов в отчёт не включать.
Автоматические проверки должны проверять поведение и границы доступа, восстановление и согласованность, а не только повторять реализацию. Выполнить npm.cmd test и npm.cmd run build на Windows либо эквивалентные команды на целевой ОС; результат Linux-проверки изоляции и MinIO-интеграции фиксировать отдельно. Старые посторонние ошибки не скрывать и не чинить несвязанные области без необходимости.
Подготовить воспроизводимую инструкцию ручного прохода UI: создание проекта, загрузка каталога, настройка пары версий, назначение поддержки, вопрос, отказ скачивания, обновление и откат. Добавить скриншоты ключевых экранов без секретов и личных данных.
Финальный пакет: исходный код и миграции; актуальные API/инструкции; тестовые фикстуры; результаты тестов/нагрузки/восстановления; список известных ограничений; инструкции установки и отката; заполненный TODO.
Исполнитель помечает «реализовано» и «проверено исполнителем», но не закрывает независимую приёмку. Основной агент после передачи проверяет diff, запускает релевантные проверки и проверяет AC-сценарии; замечания возвращаются в тот же TODO. Готовность к production фиксируется только после этой проверки и устранения блокирующих замечаний.
