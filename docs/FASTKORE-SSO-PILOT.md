# Fastkore SSO по ТЗ 1.1

Пилот доступен при настройке HTTPS и включении Compose overlay. Для совместной проверки используйте отдельный экземпляр с собственным HTTPS-адресом и каталогом данных. Контракт обмена из черновика v1 заменён ТЗ 1.1.

## Настройка платформы

1. Проверьте локальный вход администратора и сделайте резервную копию SQLite. Платформа принимает локальные пароли только у администраторов. При обновлении прежние пользовательские API-ключи и локальные сеансы сотрудников отзываются. Существующие учётные записи можно связать с ERP вручную, а новым сотрудникам профиль создаётся при первом успешном входе.
2. Настройте HTTPS reverse proxy. Задайте точный BRIDGE_PUBLIC_ORIGIN без завершающего слеша, например https://agentic-platform.fastkore.ru. В BRIDGE_TRUST_PROXY укажите адрес proxy, который видит процесс приложения. Proxy должен выставлять собственные X-Forwarded-Proto и X-Forwarded-For и сохранять публичный Host, включая порт, если он нестандартный. Порт приложения остаётся закрытым для внешних клиентов. Не записывайте в журнал тела и заголовки запросов входа.
3. Создайте закрытый каталог private и файл private/fastkore-sso.key из 32 случайных бинарных байтов. Сохраните копию ключа отдельно от резервной копии SQLite. Файл должен читаться процессом приложения (UID 1000 в образе) и не должен быть доступен посторонним или лежать в каталогах проектов. Команда создания файла, которая откажется перезаписывать существующий ключ:

~~~sh
node -e "const fs=require('node:fs');fs.mkdirSync('private',{recursive:true,mode:0o700});fs.writeFileSync('private/fastkore-sso.key',require('node:crypto').randomBytes(32),{flag:'wx',mode:0o600})"
~~~

4. Запустите пилот командой:

~~~sh
docker compose -f compose.yaml -f compose.sso.yaml up -d --build
~~~

Вне Docker задайте BRIDGE_SSO_KEY_FILE абсолютным путём к тому же ключу. Для работы Codex вместе с SSO добавьте [отдельный исполнитель](CODEX-WORKER.md) через `-f compose.codex.yaml`. Без него используется BRIDGE_EXECUTION=disabled. Храните ключ ERP вне каталогов проектов.

Платформа получает публичный CA ERP через `fastkore.ServerInfo/GetTlsCertificates`. Имя хоста в адресе ERP должно присутствовать в SAN серверного сертификата. После сверки отпечатка платформа проверяет цепочку TLS с полученным CA и сохраняет сертификат для выбранной установки и её HTTPS-адреса. При смене CA повторите сверку через «Проверить подключение».

Для прежних ERP без `GetTlsCertificates` администратор может передать доверенный корневой PEM при развёртывании. В Docker сохраните его в `private/fastkore-ca/ca.pem`, задайте `BRIDGE_FASTKORE_CA_FILE=/run/fastkore-ca/ca.pem` и пересоздайте `app` с `compose.sso.yaml`. Вне Docker задайте `NODE_EXTRA_CA_CERTS` абсолютным путём к PEM.

1. В карточке сервиса Fastkore Agent Platform укажите базовый HTTPS-адрес платформы, нажмите «Подключить» и скопируйте код, который выдаст ERP. Код действует 5 минут. ERP открывает страницу платформы по адресу `/?settings=fastkore`.
2. Войдите как локальный администратор платформы и откройте «Настройки → Вход из Fastkore». Выберите установку или добавьте новую, указав название и адрес ERP. Нажмите «Проверить подключение», сверьте SHA-256 с разделом «Сертификат TLS и отпечаток CA» в консоли ERP и нажмите «Отпечаток совпадает». Логин и пароль ERP для этой проверки не требуются.
3. Вставьте код и нажмите «Подключить». Платформа отправит `POST /api/ai/pair` на origin зарегистрированного сервера ERP и включит вход после подтверждения. При потере ответа повторите попытку с тем же кодом до его истечения.

Ключ подключения хранится в SQLite под AES-256-GCM. ERP получает проверочное значение по HTTPS. Для смены адреса ERP отключите установку, сохраните подтверждённый адрес и выполните сопряжение заново. При смене публичного origin платформы также нужен новый код. Действие «Ротация ключа» в управлении установкой требует свежий код. После подтверждения ERP платформа сохранит новый ключ и отзовёт прежние сеансы и незавершённые обмены установки. Идентификатор установки и связи с пользователями сохраняются.

Действующие ручные установки можно перевести на привязку по коду. Для совместимости с прежним протоколом ручная регистрация доступна локальному администратору через маршруты, описанные в [API.md](../API.md).

Старые установки из BRIDGE_SSO_CONFIG не импортируются автоматически. Для перехода с черновика v1 зарегистрируйте установки по ТЗ 1.1 и согласуйте новые идентификаторы. Явная привязка ERP-личности сохраняет доступ к истории выбранного пользователя платформы.

## Что настроить на стороне ERP

- Доступный из контейнера точный HTTPS URL проверки билета. Если используется корпоративный CA, предоставьте сертификат CA. ERP должна проверять TLS и на участке за reverse proxy.
- Для сопряжения нужна сборка Fastkore с действием «Подключить» в карточке сервиса GUID 33040cfb-9073-43a5-a184-5039db13924b и серверным `POST /api/ai/pair`. Для ручного подключения по прежнему протоколу задайте `AgentPlatformEnabled` и `AgentPlatformKeyVerifier` по ТЗ 1.1.
- Используйте сборку Fastkore с CreateAgentPlatformLaunchTicket(loginChallenge) и WebView2, который выполняет верхнеуровневую POST-навигацию в том же профиле. Для проверки нужны два тестовых сотрудника и проект, который доступен только одному из них после назначения роли и членства. В WPF проверяйте точный origin источника сообщений и ограничивайте навигацию и новые окна origin пилота.

## Последовательность входа

1. WebView2 открывает GET /auth/fastkore/start?theme=dark или theme=light. Платформа устанавливает cookie подготовки на 120 секунд и отправляет {type:"fastkore.sso.challenge",version:1,login_challenge}.
2. WPF по своей действующей TLS-сессии вызывает CreateAgentPlatformLaunchTicket(loginChallenge). ERP выдаёт непрозрачный одноразовый билет на 60 секунд.
3. WebView2 делает POST /auth/fastkore/exchange с Content-Type application/x-www-form-urlencoded. Поля формы ровно version=1, installation_id, ticket и login_challenge. Профиль WebView2 сохраняет cookie подготовки. POST принимает совпадающий или отсутствующий Origin. Нативная навигация WebView2 может прислать `Origin: null` вместе с `Sec-Fetch-Site: none`. В этом случае платформа также требует действующие cookie подготовки, `login_challenge` и билет ERP. Перенаправления на другой origin для запроса с билетом запрещены.
4. Платформа отправляет на зарегистрированный ERP URL JSON {version:1,installation_id,ticket,audience:"fastkore-agent-platform",login_challenge} с серверным Bearer-ключом. ERP погашает билет атомарно и возвращает {version:1,valid:true,installation_id,audience,user:{id,display_name}}. Идентификаторы — GUID в нижнем регистре.
5. Платформа удаляет cookie подготовки, устанавливает HttpOnly Secure сессию с абсолютным сроком 30 минут и возвращает 303 на /?embedded=fastkore&theme=light или dark. При неопределённом результате начните новый вход с новым билетом.
6. Встроенная страница читает /api/auth/me через cookie. Она отправляет {type:"fastkore.ready",version:1,installation_id,fastkore_user_id,theme} после применения темы. Хост сверяет личность с выданным билетом. Для обновления темы хост посылает {type:"fastkore.ui",version:1,theme} через PostWebMessageAsJson и получает fastkore.ui.applied. При 401 страница сообщает fastkore.sso.required с reason="session_expired".
7. При смене ERP-пользователя используйте новый приватный профиль WebView2. Сворачивание сохраняет окно и сессию. POST /api/auth/logout отзывает текущий сеанс. Если logout не доставлен, действует абсолютный срок сессии.

Общие приёмочные проверки на клиенте Fastkore — вход без пароля и доступ к проекту, смена ERP-пользователя, светлая и тёмная темы, повторное раскрытие окна, новый вход после ротации и отказ для старого сеанса. Серверные тесты с имитацией ERP и локальным HTTPS не заменяют совместную проверку.
