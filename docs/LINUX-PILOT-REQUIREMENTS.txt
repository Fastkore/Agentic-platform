Исторический план подготовки первой тестовой среды. Основная концепция проекта
закреплена в манифесте ../AGENT-PLATFORM-MARKETING.md, текущая конфигурация исполнителей —

описывают состояние на дату исходного обследования.

Подготовлена версия 0.6: хранение, очередь, роли, профили и кандидат SSO для совместного пилота. Linux-изоляция, SSO и совместная работа с реальной Fastkore ещё требуют проверки.

Для администратора Linux:
- Отдельный тестовый Linux-хост с поддерживаемым Docker Engine и Compose. Обычная локальная файловая система для SQLite; сетевое хранилище для её активного файла не использовать.
- Для предварительного запуска самого веб-приложения ориентир 2 CPU и 2–4 ГБ памяти; это не замер потребления полноценного исполнителя Codex. Запас под его инструменты определяется испытаниями.
- Выделенные каталоги данных и тестовых проектов, доступные пользователю контейнера UID/GID 1000:1000. Реальные закрытые прайсы на первом шаге не загружать.
- HTTPS-имя и доверенный сертификат, доступные офисным компьютерам и WebView2. HTTPS reverse proxy направляет запросы к 127.0.0.1:8787. Сам порт приложения не открывать наружу без необходимости.
- BRIDGE_PUBLIC_ORIGIN — точный HTTPS origin. Не принимать адрес проверки билетов из пользовательского запроса; не отключать TLS-проверку ради теста.
- Исходящий HTTPS-доступ платформы к заранее согласованному endpoint проверки билетов Fastkore. Для будущего Codex отдельно потребуется доступ к OpenAI и проверенная изоляция сети его команд.
- Способ доступа разработчика к тестовой среде либо возможность администратора выполнить подготовленные команды и передать результаты. Пароли и приватные ключи в переписку не отправлять.

Dockerfile и compose.yaml включены в исходники 0.6. Они подготовлены для проверки приложения, но здесь не запускались: Docker/Linux на текущем Windows-компьютере отсутствуют. По умолчанию BRIDGE_EXECUTION=disabled. В образ не включены авторизация OpenAI, Codex CLI и корпоративные секреты. Удаление этой переменной не заменяет приёмку изоляции.

Для разработчиков Fastkore:
- Согласовать небольшой контракт из FASTKORE-SSO-CONTRACT-DRAFT.txt и FASTKORE-SSO-PILOT.md: выдача билета, атомарная онлайн-проверка и наш обмен на веб-сессию.
- Назначить постоянный GUID типа интеграции и стабильный installation_id тестовой установки.
- Реализовать выдачу билета по действующей ERP-сессии, проверку права запуска, срок/назначение и однократное погашение.
- Хранить отдельный секрет установки только на сервере; его полномочия ограничить проверкой билетов. Определить процедуру ротации.
- Предоставить тестовый Fastkore 2027 с прежней кнопкой «Ассистент ИИ», WebView2, POST-входом и обменом контекстом после готовности страницы.
- Передавать фактический стабильный тип и ID объекта. Номер заказа для отображения не считать GUID.
- Обеспечить выход и очистку/разделение профиля WebView2 при смене ERP-пользователя.
- Уточнить требуемое время отзыва уже созданной веб-сессии при блокировке только в ERP: однократная проверка билета сама по себе мгновенный отзыв не обеспечивает.
- Предоставить точный контракт необходимых чтений/записей Fastkore, тестовый объект и аккаунт с минимальными правами. По найденным материалам CLI предназначен для Windows; Linux-совместимость или полноту HTTP API требуется подтвердить.

Совместная приёмка:
1. Правильный пользователь входит в WebView2 без повторного пароля.
2. Подмена, просрочка, повтор и одновременное предъявление одного билета отклоняются.
3. Платформа не принимает произвольный сервер проверки и не передаёт секрет в клиент.
4. Видимый контекст чата совпадает с выбранным объектом; доступа к чужому объекту нет.
5. После выхода и смены ERP-пользователя нет чужих чатов, черновиков и cookie.
6. При сбое включённой интеграции нет отправки данных прежнему ИИ-провайдеру.

Для проверки нашей платформы сначала можно использовать имитатор билетов и искусственные данные. Такая проверка не заменяет испытание реального Fastkore/WebView2. Допустимая схема ChatGPT-аккаунтов для сотрудников согласуется отдельно от входа SSO.
