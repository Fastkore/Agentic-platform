FASTKORE AGENT PLATFORM — УЧЁТ ТЗ № 3
11 ноября 2026 года

Статус: предложение интеграционного контракта для согласования. Реализация платформы возобновлена; версия 0.5.0 содержит очередь, SQLite и рабочие роли. SSO ещё не реализован и не согласован с разработчиками ERP.

1. ИЗМЕНЕНИЕ СЦЕНАРИЯ

ТЗ № 3 имеет приоритет в вопросах встраивания интерфейса и входа из ERP. Пользователь нажимает существующую кнопку «Ассистент ИИ», а Fastkore открывает наш веб-интерфейс в WebView2. Второй чат средствами ERP не разрабатывается. HTTP API задач, файлов и результатов остаётся для автоматизации.

Сохраняются ранее согласованные требования к Codex exec, Skills, ролям, профилям, очереди, закрытым данным, истории, поиску, Linux-поставке и корпоративным инструментам. SSO не решает совместимость Windows CLI с Linux и не заменяет авторизацию Codex в OpenAI.

2. РАЗДЕЛЕНИЕ РАБОТ

Разработчики Fastkore:
- карточка предопределённого сервиса и постоянный GUID типа интеграции;
- стабильный ID конкретной установки, отдельный секрет и его защищённое серверное хранение;
- выдача билета по действующей ERP-сессии и проверка права запуска интеграции;
- атомарная онлайн-проверка и погашение билета;
- переключение существующей кнопки между прежним режимом и WebView2;
- передача контекста текущего объекта, управление профилем WebView2 и очистка при смене пользователя;
- отсутствие автоматического перехода к другому ИИ-провайдеру при сбое активной интеграции.

Наша платформа:
- реестр доверенных установок Fastkore в существующих настройках подключений;
- обмен билета на защищённую cookie-сессию;
- сопоставление пользователя по паре installation_id + fastkore_user_id;
- применение собственных ролей и ограничений;
- поддержка встроенного интерфейса и сообщения с контекстом;
- выход, истечение сессии, понятные ошибки и проверки доступа.

GUID типа интеграции, installation_id и fastkore_user_id — разные идентификаторы. GUID типа одинаков для всех установок; installation_id различает конкретные установки. GUID типа назначают разработчики Fastkore, не выдумываем его в нашей поставке.

3. ПРЕДЛАГАЕМЫЙ КОНТРАКТ V1

Имена маршрутов ниже взяты из ТЗ. Структуры уточняют предложение для согласования, а не описывают уже работающий API Fastkore.

А. Fastkore: POST /api/ai/launch-ticket

Аутентификация: текущая ERP-сессия. Сервер сам определяет пользователя; client-supplied userId не является основанием для входа. Проверяются включённая интеграция, право запуска и состояние пользователя.

Ответ:
{
  "installation_id": "<стабильный ID установки>",
  "ticket": "<непрозрачный случайный одноразовый билет>",
  "expires_at": "<UTC ISO 8601>"
}

Предлагаемая длительность билета — 60 секунд, энтропия — не менее 256 бит. На стороне Fastkore хранится проверочный хеш и привязка к пользователю, установке и назначению fastkore-agent-platform. Билет — чувствительный краткоживущий секрет; тело запроса/ответа не записывается в журнал.

Б. Agent Platform: POST /auth/fastkore/exchange

WebView2 выполняет HTTPS POST-навигацию. Для этого входа предлагаем application/x-www-form-urlencoded с двумя полями: installation_id и ticket. Билет отсутствует в query string, fragment, истории и постоянном хранилище страницы. Размер тела ограничен. Возврат только на фиксированный локальный путь интерфейса, без пользовательского returnUrl.

Платформа находит доверенную активную установку по installation_id. URL проверки, секрет и параметры TLS берутся из серверных настроек. Входящий запрос не может менять адрес проверки, пользователя или роль.

В. Fastkore: POST /api/ai/validate-ticket

Платформа отправляет серверный запрос по HTTPS на заранее настроенный адрес. Предлагаем Authorization: Bearer <отдельный секрет установки>. Секрет разрешает только проверку билетов, не чтение произвольных объектов ERP. Не следуем HTTP-перенаправлениям; ограничиваем время и размер ответа; применяем контроль разрешённого адреса. Для офисной ERP допускаются настроенные внутренние адреса, а не произвольный адрес от клиента.

Тело:
{
  "installation_id": "<ID установки>",
  "ticket": "<билет>",
  "audience": "fastkore-agent-platform"
}

Успешный ответ:
{
  "valid": true,
  "installation_id": "<тот же ID установки>",
  "audience": "fastkore-agent-platform",
  "user": {
    "id": "<стабильный ID пользователя ERP>",
    "display_name": "<отображаемое имя>"
  }
}

HTTP 200 допускается только после атомарного погашения ещё действительного билета. Одновременные предъявления одного билета не могут оба дать успех. Действительность учётной записи и право запуска повторно проверяются в момент погашения. ERP-роли не импортируются в ответ как автоматически доверенные роли нашей платформы.

Неверный серверный секрет — 401/403. Недействительный, истёкший или погашенный билет — отказ без создания сессии. При неоднозначном сетевом сбое после погашения пользователь получает новый билет; платформа не принимает старый локально и не переключается к другому ИИ.

После успешной проверки платформа создаёт новый идентификатор сессии, устанавливает cookie и отвечает 303 на фиксированный путь интерфейса. Билет и постоянный токен не возвращаются JavaScript страницы.

4. ИДЕНТИЧНОСТЬ И СЕССИИ

В базе нужна уникальная внешняя связь (installation_id, fastkore_user_id) -> platform_user_id. Имя или логин не используются для автоматического объединения учётных записей. Если требуется привязка к уже существующему локальному пользователю, её выполняет администратор явно. Одноимённый пользователь ERP никогда автоматически не становится нашим администратором.

При первом SSO-входе допустима учётная запись без доступа к проектам/профилям. Пользователь увидит объяснение, что доступ должен назначить администратор. SSO-пользователь не получает фиктивный пароль и не проходит локальную первоначальную настройку руководителя.

Cookie в рабочем HTTPS-режиме: __Host-bridge_session, Secure, HttpOnly, Path=/, без Domain; SameSite=Lax как начальный вариант для проверки в целевом WebView2. Cookie хранит случайный идентификатор; сервер хранит хеш и срок действия. Персональные Bearer API-ключи остаются отдельным способом автоматизации.

Текущий интерфейс использует Bearer из sessionStorage. Для SSO добавляется определение пользователя через серверную cookie-сессию. Старый токен из sessionStorage не должен переопределять пользователя нового SSO-входа. Неоднозначная комбинация разных личностей в cookie и Authorization отклоняется. Веб-запросы с cookie требуют защиты от CSRF; прежней проверки Origin без обязательности для изменяющих запросов недостаточно. Общую защиту Origin/CSP не отключаем ради интеграции.

WebView2 загружает платформу как верхнеуровневую страницу. Это не требует разрешить встраивание сайта в произвольные iframe или ослабить X-Frame-Options/frame-ancestors. При HTTPS за reverse proxy доверяем только настроенному proxy, а не произвольным X-Forwarded-* заголовкам клиента.

Предлагаемый срок SSO-сессии для пилота — 30 минут, после истечения WebView2 получает новый билет штатным путём ERP. Это предложение требует согласования. Блокировка пользователя в самой платформе и отключение установки прекращают доступ немедленно на очередной серверной проверке. Блокировку только в ERP существующая cookie-сессия не узнает автоматически: без отдельного канала отзыва она выявится при следующем входе/онлайн-подтверждении. Не обещаем мгновенный общий logout, которого нет в трёхмаршрутном контракте.

Выход через платформу отзывает сессию на сервере и удаляет cookie. При выходе/смене пользователя ERP её клиент вызывает выход и очищает соответствующий профиль WebView2 либо использует отдельный профиль для каждой личности. Даже при сетевом сбое следующий ERP-пользователь не должен получить прежние cookies, localStorage, черновики, историю или уже загруженную страницу. Разделение только по Windows-пользователю недостаточно, если внутри одной Windows-сессии меняются пользователи ERP.

В журнале допустимы ID установки/операции, время, результат и безопасный код ошибки. Билеты, cookies, Authorization и серверные секреты не логируются. Хранение секретов включается в существующий доверенный механизм подключений, вне доступного агентам файлового пространства; секрет не выдаётся обратно через админский GET.

5. КОНТЕКСТ ОБЪЕКТА

После загрузки и установления сессии страница сообщает хосту о готовности. Предлагаем версионированный обмен:
Страница -> WebView2-хост: { "type": "fastkore.ready", "version": 1 }
Хост -> страница:
{
  "type": "fastkore.context",
  "version": 1,
  "entityType": "<фактический стабильный тип>",
  "entityId": "<фактический стабильный ID>",
  "suggestedAgent": "estimator"
}

Это уточнение минимального сообщения из ТЗ. Номер 1677 — пример для пользователя; он не должен подменять GUID, если API Fastkore требует GUID. Отображаемый номер можно получить отдельно как подпись.

Хост проверяет точный доверенный origin перед передачей сообщения и ограничивает навигацию/новые окна. Веб-страница проверяет формат, длины и разрешённые типы. Для WebView2 используется штатный chrome.webview message API, а не произвольный исполняемый скрипт из содержимого документа. Постоянные секреты через сообщения не передаются.

Платформа отправляет полученный контекст на свой сервер с действующей сессией. Installation ID берётся из подтверждённой внешней личности, а не из произвольного сообщения. suggestedAgent используется только среди разрешённых профилей. При недоступном профиле показывается выбор из разрешённых.

Контекст — ссылка, а не разрешение читать объект. Доступ проверяется при обращении к Fastkore, включая объекты, которые пользователь вручную подставил в запрос. Если служебный аккаунт Fastkore шире прав сотрудника, нужен явный механизм проверки/делегирования прав сотрудника; одно наличие SSO эту проблему не решает.

В чате отображается текущий объект ERP. Получение нового контекста не меняет скрытно объект уже существующего диалога. В первом варианте предлагается новый чат с этим объектом или явное продолжение ранее связанного чата с тем же объектом. Отправка задачи начинается только после действия пользователя; открытие кнопки само по себе не запускает анализ или запись в ERP.

6. ИЗМЕНЕНИЕ ПОРЯДКА РАБОТ

Этапы 0–1 прежнего плана сохраняются: проверка среды, миграция хранения и очередь. В схеме данных заранее учитываем внешние личности и привязку чата к объекту ERP, не переписывая остальное ради WebView2.

На этапе 2 ролей и пользователей добавляются внешние связи и минимальные права первого SSO-входа. Роли платформы остаются самостоятельными.

После появления HTTPS и основного контроля доступа добавляется этап 3 обновлённого основного плана: доверенные установки, обмен билета, cookie/CSRF, выход и встроенный режим. Его можно проверять с отдельным тестовым сервером билетов, но это не заменяет приёмку с Fastkore. Нумерация этапов в редакции 2 основного плана является актуальной.

Далее сохраняются защищённое исполнение, оценщик и передача технологу. На этапе Fastkore проверяется получение фактического объекта по контексту. Этап внешнего API и webhook остаётся для фоновых заданий; обязательное воспроизведение интерактивного чата средствами ERP исключается.

В окончательную приёмку добавляются: реальный вход по кнопке в WPF, отсутствие второго логина/поля ввода, правильная личность и объект, повторное открытие, истёкший/повторный билет, два одновременных обмена, неверный секрет, подмена установки/URL/объекта, блокировка, смена ERP-пользователя, сетевой сбой и возврат старого режима только при отключённой интеграции.

Необходимые внешние зависимости: реализация двух ERP-методов и WPF-части разработчиками Fastkore; согласованный контракт; HTTPS-связность между серверами; целевая тестовая установка Fastkore 2027. Эти части отсутствуют в текущем репозитории веб-оболочки. Их нельзя объявить выполненными после одной доработки нашего сервера.

Текущее состояние: хранилище/очередь и административные роли/профили реализованы в 0.5.0, сборка и 30 тестов успешны, офисная история сохранена. Следующий этап — HTTPS/SSO после получения Linux-среды и согласования контракта.
