# HTTP API · v0.6

Базовый адрес: `http://<IP-сервера>:8787`. На том же адресе `/` открывает веб-чат.

HTTP-маршруты обслуживают веб-интерфейс. Для локального администратора интерфейс передаёт временный токен сеанса через `Authorization: Bearer`. Сотрудники используют cookie-сессию Fastkore с CSRF. Персональные ключи для внешних клиентов отозваны, маршруты их выпуска удалены.

Руководитель видит все проекты и чаты. Сотрудник — назначенные проекты, свои чаты и общие чаты проекта. Общие чаты других авторов доступны сотруднику только для чтения. Новые чаты личные; видимость меняет руководитель. Автор и руководители могут продолжать чат, менять модель и отменять его задания. Для недоступного проекта/чата/задания возвращается 404; административная операция сотрудника — 403. Проекты и количество чатов также отфильтрованы.

POST без полей отправляйте с телом `{}` и Content-Type application/json, кроме multipart-загрузки. Настройки, диагностика, проверка CLI/подписки, импорт истории и подключение папок доступны только руководителю. Список чатов включает ownerId, ownerName и visibility. /api/status включает user, busy и activeRun: чужое личное задание не раскрывается, но busy сообщает общую занятость.

Маршруты статистики принимают `timeZone` (например, `Europe/Moscow`, по умолчанию `UTC`). В `total`, `days` и `unattributed` возвращаются дневные суммы входных и выходных токенов за период до 370 суток. `unattributed` содержит расход заданий, для которых в истории нет известного автора.

Архив исключён из обычных списков и поиска. Руководитель может читать историю и скачивать результаты из архива. Для отправки сообщений чат нужно восстановить. Архивирование чата с заданием в очереди или в работе возвращает 409. При удалении платформа очищает историю чата и его собственные файлы результатов. Загрузки проекта остаются доступны в проекте, а расход токенов остаётся в сводке.

Для связанных чатов `context` — снимок `fastkore.context` версии 1. Карточка определяется GUID справочника и объекта. Для списка учитываются вид, плитка, каталог, папка, родитель, связь, режим удаления, фильтр и UID элемента управления. Выбор строки в списке сохраняет тот же чат. Поиск ограничен текущим пользователем и установкой ERP. Для отправки в связанный чат передайте соответствующий снимок в `fastkoreContext`.

Создание проекта или чата не начинает диалог с моделью. Первый вопрос создаёт сессию Codex. Последующие вопросы продолжают сессию основного профиля, пока действуют те же разрешения и настройки исполнения.

## Отправка вопроса

```json
{
  "text": "Перечисли доступные Excel-файлы и кратко опиши их содержимое",
  "attachmentIds": [],
  "clientRequestId": "chat-question-001"
}
```

`text` обязателен, до 60 000 символов. `attachmentIds` — до 8 ID файлов, ранее загруженных **в этот проект**. Полные локальные пути вместо ID не принимаются. `recommendedSpecialistId` передаёт рекомендацию для одного вопроса. Основной агент решает, нужна ли консультация, и выбирает среди профилей, доступных пользователю в проекте.

`clientRequestId` учитывается отдельно для каждого пользователя и необязателен, до 100 символов. Используйте уникальное значение на каждый логический вопрос. Повтор идентичного запроса возвращает прежнее задание. Изменение текста, набора вложений, модели, рекомендации специалиста или чата при том же ключе даёт 409. Дедупликация сохраняется в SQLite без прежнего ограничения последними 500 заданиями.

Ответ: HTTP 202, Location: /api/runs/{id}.

```json
{
  "id": "<runId>",
  "projectId": "<projectId>",
  "chatId": "<chatId>",
  "status": "running",
  "progress": "Проверяем подключение Codex…",
  "createdAt": "2026-11-10T12:00:00.000Z"
}
```

Проверяйте GET /api/runs/{id}, например раз в секунду. Статусы: queued → running → complete, error, cancelled. Занятый сервер принимает новые вопросы в очередь; предел — 100 ожидающих заданий. После аварийного перезапуска прежние running получают interrupted, а queued сохраняются и ожидают запуска. При complete готовый текст находится в `response`, расход токенов — в `usage`, если CLI его сообщил. Ошибка — в `error`; неуспешное задание не публикует частичный response как готовый результат. При ошибке авторизации сообщения в чат не добавляются, но задание содержит причину. Соединение клиента может закрыться: уже принятое задание продолжится на сервере. /api/status возвращает только доступные пользователю queuedRuns; чужое личное задание не раскрывается.

Токены не показывают точный остаток или вид тарификации. API-ключ Codex всегда блокируется; поддерживается текущий вход ChatGPT серверного пользователя.

## Выбор модели

GET /api/models возвращает `{models: [{id, name, description, isDefault}], fetchedAt, source: "codex"}`. Идентификатор нужно брать из этого ответа. Каталог формирует Codex; присутствие в каталоге не гарантирует доступность для каждого аккаунта. Неизвестный ID при сохранении выбора даёт 400; ошибка реального доступа отображается в задании. Нет автоматического перехода на другую модель.

- PATCH /api/settings с `{ "model": "<id>" }` задаёт модель сервера; `{ "model": "" }` — автонастройку Codex.
- PATCH /api/projects/{projectId}/chats/{chatId} с `{ "model": "<id>" }` сохраняет модель чата; пустая строка включает наследование от сервера. Активный чат менять нельзя: 409. Session ID и история сохраняются.
- POST сообщения также принимает необязательное поле `model`. Если оно задано, выбор сохраняется для этого чата перед выполнением задания. Без поля сохраняется прежний выбор чата.
- Приоритет: фиксированная модель профиля → модель чата → модель сервера → настройки самого Codex. В заданиях и ответах помощника поле `model` содержит явно переданный идентификатор; при автонастройке CLI поле может отсутствовать.
- Изменения модели применяются к следующим вопросам. Выбор сохраняется в SQLite и переживает перезапуск; старые состояния JSON загружаются без потери данных. Пока у чата есть ожидающие/активные задания, менять его модель нельзя.

Сохраните cliPath отдельно, прежде чем менять модель: API не принимает в одном PATCH одновременную смену пути к CLI и непустой модели.

## Ошибки

Тело ошибки: `{ "error": "Описание" }`. Основные коды: 400 — неверные поля/путь, 401 — сеанс отсутствует или недействителен, 403 — недостаточно прав, чужой Origin или удалённый local-login, 404 — неизвестный/недоступный объект, 409 — конфликт идентификатора/ревизии/настроек или закрытый пока профиль, 413 — превышен размер файла, 429 — ограничение входов/очереди, 503 — остановка сервера или выключенное исполнение. Ошибки выполнения модели приходят в состоянии уже принятого задания; не рассчитывайте получить их в исходном HTTP-запросе.

Прототип предназначен для доверенной офисной команды. Очередь устойчивая, с одним исполнителем. Рабочий Windows-сервер пока использует HTTP; Linux/HTTPS и изолированное выполнение не прошли целевую проверку. Файлы обычных проектов общие независимо от видимости чатов. Для LAN используйте START-LAN.cmd. Ограничение входов: 10 на IP за 10 минут.

## Роли, профили и источники · 0.5

GET /api/agents возвращает разрешённые профили: id, name, description, model, available и необязательное unavailableReason. Внутренние инструкции и пути не включаются. Новый чат принимает необязательный agentProfileId (по умолчанию universal). Несуществующий или запрещённый профиль даёт 403; настроенный профиль с ещё неподтверждённой средой — 409 до запуска Codex.

Администратор получает/сохраняет настройки:

| Метод | Адрес | Поля записи |
| --- | --- | --- |
| GET | /api/admin/roles | Список рабочих ролей |
| PUT | /api/admin/roles/{id} | name, enabled, profileIds, operationIds, readDatasetIds, instructions |
| GET | /api/admin/profiles | Список профилей и причины недоступности |
| PUT | /api/admin/profiles/{id} | name, description, instructions, enabled, model, reasoningEffort, operationIds, datasetIds, skillIds, allowWrite, outputMode, необязательные icon и instructionFiles |
| GET | /api/admin/datasets | Список источников с серверными путями |
| PUT | /api/admin/datasets/{id} | name, directory, projectIds, classification |
| GET | /api/admin/operations | Поддерживаемые идентификаторы операций |

PUT передаёт все поля записи. Для обновления требуется revision из последнего GET; несовпадение даёт 409. Для создания revision отсутствует. ID — 2–64 символа: первая латинская буква, затем строчные буквы/цифры/подчёркивание/дефис. Обычные сотрудники не читают и не меняют эту конфигурацию.

reasoningEffort: low, medium, high, xhigh. outputMode: chat или restricted. classification: shared или restricted. Список operationIds: chat, estimate, technology, accounting. Сейчас запускается только обычная операция chat без дополнительных источников/Skills. Остальные настройки можно подготовить; они не означают, что бизнес-сценарий реализован.

POST /api/users дополнительно принимает roleId; PATCH /api/users/{id} принимает name, roleId, role (admin/employee), disabled и password. role — административный уровень, roleId — рабочая роль. Должен оставаться хотя бы один активный администратор. Смена рабочей роли немедленно применяется к дальнейшим операциям и проверяется во время выполнения.

После изменения правил профиля/роли следующая работа получает свежую внутреннюю сессию. Ранее созданные сообщения сохраняются. Профиль с активными/ожидающими заданиями не меняется до их завершения.

Регистрация любого restricted-источника закрывает ВСЕ запуски Codex в этой версии до проверки изоляции. Ограничение нельзя обойти выбором universal или проверкой подписки. Хранение записи источника само по себе не создаёт изоляцию файлов.

Fastkore SSO по ТЗ 1.1 включается отдельной конфигурацией. Совместная приёмка с ERP остаётся открытой.

## Веб-вход Fastkore · ТЗ 1.1

Нужны HTTPS, конкретный доверенный proxy, `BRIDGE_SSO_KEY_FILE` и изолированный исполнитель Codex либо `BRIDGE_EXECUTION=disabled`. Сотрудник входит через SSO. Профиль создаётся при первом успешном обмене по паре `installation_id` и GUID сотрудника и используется при последующих входах. [Настройка пилота](docs/FASTKORE-SSO-PILOT.md).

| --- | --- | --- |

| GET | /api/auth/me | Для SSO возвращает `user`, `setupRequired`, `source` и `authentication` с ID установки и пользователя ERP, сроком сеанса, `csrfToken` и `canChangePassword:false` |
| GET | /api/auth/browser-session | Для обычной загрузки сайта без Bearer. Без cookie возвращает `{authenticated:false,fastkoreEnabled}`. С SSO-cookie также возвращает `user`, `setupRequired:false` и `authentication` |

| POST | /api/admin/fastkore/installations/{id}/tls | HTTPS и локальный администратор. `{fingerprint}` подтверждает CA для сохранённого адреса установки. При смене подтверждённого CA прежние сеансы отзываются |
| PATCH | /api/admin/fastkore/installations/{id} | Локальный администратор. Поля `name`, `enabled`, `validateTicketUrl`, `confirmValidateTicketUrl`. Для нового URL сначала отключите установку и подтвердите адрес |
| POST | /api/admin/fastkore/installations/{id}/pair | HTTPS и локальный администратор. Принимает `{pairingCode}` и включает вход после подтверждения ERP. Возвращает метаданные установки |
| POST | /api/admin/fastkore/installations/{id}/pair/rotate-key | HTTPS и локальный администратор. Принимает `{pairingCode}` и подтверждает новый ключ в ERP. После подтверждения отзывает сеансы и начатые обмены установки |
| POST | /api/admin/fastkore/installations/{id}/rotate-key | HTTPS и локальный администратор. Ротация для ручного подключения. Однократно возвращает новый ключ и отзывает сеансы и начатые обмены установки |
| GET, PUT | /api/admin/fastkore/identities | Локальный администратор просматривает или задаёт явные связи `{installationId,externalUserId,userId}` |

ERP открывает `/?settings=fastkore` на публичном адресе платформы. Сервер платформы отправляет `{version:1,pairing_code,platform_origin,installation_id,erp_key_verifier}` на `/api/ai/pair` на origin из сохранённого адреса проверки билетов. Подтверждение ERP имеет формат `{version:1,paired:true,installation_id}`. При потере ответа повтор с тем же кодом использует тот же ключ. Поля `pairingStatus`, `pairedAt` и `pairingRotationPending` показывают состояние в метаданных установки.

Для изменяющих запросов с cookie обязательны `Origin: <BRIDGE_PUBLIC_ORIGIN>` и `X-CSRF-Token: <csrfToken>`, включая multipart и выход. Смешанные cookie и Authorization получают 409. SSO-сессионный токен через Bearer не принимается.

Первый SSO-вход создаёт пользователя без пароля и проектов с ролью `sso_pending` без рабочих прав. Сеанс действует до 30 минут. Блокировка только в ERP учитывается при следующей выдаче или погашении билета. Контекст ERP-объекта не передаётся в этом протоколе.

В ответе `/api/ai/validate-ticket` Fastkore может вернуть `user.roles`, массив `{ id, name }`. Платформа сохраняет полный снимок в текущем SSO-сеансе и возвращает его в `authentication.roles` в обоих маршрутах чтения сеанса. Пустой массив означает отсутствие ролей, отсутствующее поле означает, что Fastkore не передал набор. Идентификатор роли используется вместе с `authentication.installationId`, название предназначено для отображения. Снимок не влияет на рабочую роль, проекты или права ERP.

Каталог полученных ролей доступен администратору через `GET /api/admin/erp-roles`. Запись содержит GUID роли, installationId, name, installationName, lastSeenAt и userCount. При повторном поступлении того же GUID от той же установки обновляется название. `GET /api/users` включает erpRoles с последними полученными наборами по установкам. Наборы сохраняются после завершения сеансов.

`DELETE /api/admin/erp-roles/{installationId}/{roleId}` удаляет запись из каталога. Следующий успешный вход, в котором ERP снова передаст эту роль, добавит её заново. Удаление и изменения каталога сохраняются транзакционно.

Для HTTPS-ответа `validate-ticket` лимит составляет 64 КиБ в UTF-8 с учётом всего JSON. Превышение лимита или некорректный набор ролей отклоняют обмен целиком.
