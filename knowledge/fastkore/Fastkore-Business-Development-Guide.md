# Fastkore Business: дополнение к руководству агента

Этот документ применяется только при работе с конфигурацией или надстройкой
**Fastkore Business**. Сначала обязательно прочитать:

1. `FastkoreCLI-Agent-Guide.md` — безопасная работа через CLI;
2. `Fastkore-Platform-Development-Guide.md` — универсальная модель платформы;
3. этот документ — предметные правила Fastkore Business.

Дополнение не превращает CLI в предметно-зависимый клиент. CLI читает схему и выполняет
штатные операции платформы, а агент использует этот документ, чтобы не обходить бизнес-логику.

## 1. Источники истины

Для конкретного сервера приоритет имеют его фактическая схема и конфигурация:

1. переносимый паспорт конфигурационного контекста, собранный read-командами CLI с целевого
   сервера;
2. экспорт VCS этой же конфигурации и версии, если он специально разрешён владельцем;
3. рабочий макрос того же контекста на том же сервере;
4. исходники точно установленной версии Fastkore Business — только если доступ к ним отдельно
   предоставлен владельцем;
5. это руководство и другие примеры.

Исходники Fastkore Business не являются зависимостью CLI и не входят в его дистрибутив.
Их не следует раздавать агентам, прикладывать к заявке или копировать в рабочий репозиторий
ради исследования конфигурации. Сервер может работать на другой версии, поэтому даже при
разрешённом доступе к исходникам нельзя переносить GUID, имена полей или внутренние значения
в серверную запись без сверки через CLI.

Английские `MacroName`, `FieldName` и имена `Id.*` являются программными идентификаторами.
Русские названия предназначены для интерфейса и поиска. Не переводить программное имя по
русской подписи и не конструировать его самостоятельно.

### 1.1. Переносимый паспорт конфигурационного контекста

Перед работой агент получает минимальный снимок **с целевого сервера**, а не исходники
Business. Такой паспорт описывает только выбранный контекст: GUID и стабильные имена
Solution/компонента, типы, поля, связи, элементы конфигурации, определения workflow и
доступные пользователю действия. Он не должен включать прикладные записи, секреты,
Credential Manager, журнал с полным `Data` или исходники макросов, пока они не нужны для
конкретной задачи.

Сегодня паспорт собирается следующей read-only последовательностью. Это несколько вызовов
публичных API внутри одного логического запроса агента: платформа выдаёт схему, дерево Solution
и workflow разными сервисами, поэтому обещать один серверный round-trip было бы неверно.

```powershell
# 1. Выбрать компонент только по данным целевого сервера.
& $cli schema entity-set list --profile dev --json
& $cli schema entity-set show --profile dev --entity-set '<entity-set-guid>' --json

# 2. Получить только дерево выбранной Solution и метаданные нужного элемента.
& $cli solution tree --profile dev --solution '<solution-guid>' --json
& $cli element show --profile dev --element '<element-guid>' --solution '<solution-guid>' --json

# 3. Если задача относится к процессу, получить его топологию.
& $cli workflow definition list --profile dev --entity-set '<entity-set-guid>' --json

# Полное определение запрашивать только для конкретной задачи и в разрешённом контуре:
# ответ содержит исходники прикреплённых макросов.
& $cli workflow definition show --profile dev --workflow '<workflow-guid>' --json

# 4. Для создания или изменения прикладной записи получить её фактический контракт.
& $cli data create describe --profile dev --entity-set '<entity-set-guid>' --json
```

Агент сохраняет из ответов только относящиеся к задаче GUID, `MacroName`, `FieldName`,
`CodeName`, ревизии и явно требуемые настройки. Локализованные подписи используются только
как пояснения. Если для задачи необходимо полное определение workflow или `element show`,
полученный исходный код макросов остаётся в защищённом рабочем контуре и не добавляется в
обычный паспорт. До любой записи паспорт перечитывается в необходимой части; ревизию нельзя
считать действительной после чужого изменения.

Планируемая единая команда `context snapshot` может оркестрировать эту ограниченную
последовательность в один JSON-документ CLI. До её появления не имитировать полный снимок
через `vcs export`, массовое чтение данных или неограниченный обход всех элементов: это и
избыточно, и может раскрыть исходники либо конфиденциальную конфигурацию.

## 2. Карта исходников Business (только при отдельно разрешённом доступе)

Этот раздел — справочник для сопровождающего, которому владелец уже предоставил исходники
ровно той версии Business. Он не нужен для штатной работы CLI или для формирования паспорта
конфигурационного контекста. При отсутствии такого доступа использовать публичный контракт
целевого сервера и зарегистрированные команды/переходы, не искать замену во внутренних API.

При разрешённом исследовании поведения начинать с соответствующего раздела:

| Область | Основной каталог или файл |
|---|---|
| Заказы и их процессы | `Business\Data\Orders` |
| Сметы и позиции | `Business\Data\Estimate` |
| Бухгалтерские документы | `Business\Data\AccountingDocuments` |
| Складские движения | `Business\Data\Warehouse` |
| Производственные позиции и операции | `Business\Data\Production` |
| Обращения, письма и коммуникации | `Business\Data\Communication` |
| Регистрация надстройки и команд | `Business\BusinessExtensionProvider.cs`, `Business\Extensions` |

Файлы `*.Designer.cs` полезны для проверки типизированных свойств, связей и GUID в этой
версии исходников. Они не отменяют проверку фактической схемы сервера.

## 3. Типизированный код надстройки и код макроса — разные среды

В исходниках Business встречаются типы `SalesOrder`, `EstimateEntity`, `StoreAction`,
`ProductionOperation` и другие. Макрос часто получает динамический `SelectedEntity` или
`EventEntity` и не обязан видеть все внутренние типы надстройки.

Перед переносом фрагмента из Business в макрос проверить:

- доступна ли сборка Business в `References`;
- добавлен ли нужный namespace в `Usings`;
- является ли вызываемый метод публичным;
- соответствует ли тип макроса его переменным контекста;
- есть ли рабочий макрос, вызывающий тот же API.

Внутренний или `protected` метод из надстройки нельзя подменять придуманным динамическим
свойством. Если публичной точки входа нет, следует использовать зарегистрированную команду,
переход или событие платформы.

## 4. Заказы и сметы

### 4.1. Смета продажи создаётся автоматически

В текущем исходном коде `SalesOrder.OnCreated()` создаёт основную `SellingEstimate` и связывает
её с заказом. Аналогично предметные типы других заказов могут создавать свою смету в
`OnCreated()`.

Поэтому после штатного создания заказа:

1. перечитать созданный заказ;
2. получить уже созданную связь `Estimate`;
3. только затем создавать и связывать позиции сметы.

Не создавать вторую смету вручную, если фактическое событие сервера уже создало первую.

### 4.2. Нумерация

Номер заказа обычно формируется платформой или обработчиком Business. Не присваивать номер
вручную без прямого требования и проверки событий создания.

### 4.3. Позиции сметы

Перед созданием позиции через CLI получить из схемы:

- точный тип позиции для вида сметы;
- свойства `Number`, `Quantity`, `Price` и их фактические типы;
- связи со сметой, номенклатурой, единицей и прочими объектами;
- направленность и кратность каждой связи.

Создавать объект и каждую связь поэтапно, как это сделал бы пользователь. После каждого шага
перечитывать прямую и при необходимости обратную сторону связи. Не переносить пример с
`order.Estimate.EstimatePosition.AddLink(position)` без подтверждения имён текущей схемой.

## 5. Складские движения

Складское движение — не просто запись со свойством `Status`. Изменение статуса запускает
предметную логику остатков, резервов, позиций и документов.

В коде надстройки используется `StoreAction.ChangeStatus(...)`, а значения определены enum
`Fastkore.Business.Data.Warehouse.StoreActionStatus`:

`NotApplyed`, `Applyed`, `Reserve`, `Expected`, `ToSupply`, `Supplying`, `WaitingCollect`,
`Collect`, `Complete`, `OnTheWay`, `Given`, `Receipt`, `Production`.

Правила:

- не заменять переход прямым `Status = 1` или другим числом;
- в макросе вызывать только подтверждённую публичную предметную точку входа;
- перед `ChangeStatus` использовать требуемый рабочим примером `Edit()` и ту же транзакцию;
- через CLI предпочтительно выполнять доступную пользователю зарегистрированную команду или
  переход и обрабатывать её вопросы/формы;
- после операции читать объект, связанные позиции и журнал.

## 6. Бизнес-процессы заказов

Этапы и переходы зависят от установленной конфигурации. Даже процессы с одинаковым
`codeName` могут иметь разные наборы этапов на разных серверах.

Перед макросом или выполнением перехода:

1. прочитать определение процесса через CLI;
2. выбрать процесс, этап и переход по GUID;
3. прочитать все макросы перехода: условия, проверки, форму ввода, действия во время и после;
4. проверить флаг множественного выполнения и фактический контекст (`SelectedEntity`,
   `SelectedEntities` либо иной подтверждённый параметр);
5. проверить доступность перехода под целевым профилем;
6. для выполнения использовать ревизию, явное разрешение побочных эффектов и подтверждения.

Нельзя присваивать значение свойства этапа вместо штатного перехода, если требуются проверки
или действия процесса.

### 6.1. Именование: примеры из поставляемой конфигурации

Источник этих примеров — исторические сохранённые определения поставочной конфигурации, а не
названия C#-классов. Они не поставляются с CLI и не являются обязательным материалом для
агента. Перед изменениями получить определение соответствующего процесса на целевом сервере
через CLI; число процессов и имена в поставочной конфигурации не являются контрактом сервера.

В редакторе БП четыре самостоятельных поля. Заполнять их осмысленно, не подставлять одно
название во все поля:

| Наименование (`Name`) | Наименование в макросах (`CodeName`) | Имя свойства (`PropertyName`) | Имя свойства в макросах (`PropertyCodeName`) |
|---|---|---|---|
| Продажа | `SalesOrderWorkflow` | Статус продажи | `SalesStage` |
| Закупка | `PurchaseOrderWorkflow` | Статус закупки | `PurchaseStage` |
| Плановый заказ | `PlanOrderWorkflow` | Статус планового заказа | `PlanOrderStage` |
| Рекламация | `ClaimOrderWorkflow` | Статус рекламации | `ClaimStage` |
| Возврат | `ReturnOrderWorkflow` | Статус возврата | `ReturnStage` |
| Закупка транспорта | `TransportOrderWorkflow` | Статус закупки транспорта | `TransportStage` |
| Заявка на закупку | `PurchaseRequestWorkflow` | Статус заявки на закупку | `PurchaseRequestStage` |
| Запрос поставщику | `SupplyRequestWorkflow` | Статус запроса поставщику | `SupplyRequestStage` |
| Поездка | `TripWorkflow` | Статус поездки | `TripStage` |

Это образцы соглашения Business, не жёсткое ограничение платформы:

- Для **нового** аналогичного процесса выбирать английский PascalCase с предметным смыслом:
  обычно `<Subject>Workflow` для БП и `<Subject>Stage` для свойства текущей стадии.
  Основа не обязана совпадать буквально: у продажи это `SalesOrder` и `Sales`.
- Русское название БП обозначает процесс, название свойства — его состояние. Для заказов
  предпочтительно «Статус продажи», «Статус закупки», а не неоднозначное «Статус».
- Не получать существующее программное имя переводом русской подписи или механическим
  добавлением суффикса. Например, из «Статус продажи» нельзя вывести `SalesStatus`:
  в этой конфигурации контракт называется `SalesStage`.
- В том же файле есть `ProjectWorkFlow` → `ProjectStatus`, `RouteWorkFlow` → `RouteStatus`,
  `VacationStatus` → `VacationStatus`, `QualificationWorkFlow` → `Qualification`.
  Встречаются и `Status`, и разные написания `Workflow`/`WorkFlow`. **Сохранять их точно**,
  включая регистр; не исправлять существующие идентификаторы ради единообразия.
- Есть старые определения без программных имён. Их не дополнять автоматически в рамках
  другой правки. Отсутствие имени не разрешает угадывать его; выбирать объект по GUID.

`SalesOrderWorkflow` обозначает БП, а `SalesStage` — свойство стадии объекта. Это видно и в
`Business\Data\Orders\SalesOrder.Designer.cs`: `SalesStage` возвращает стадию процесса
`OrderSet.SalesOrderWorkflow.Guid`. Имя вспомогательного класса `SalesOrderStageWorkflow`
в исходниках — третья сущность, его нельзя подставлять в `CodeName` определения.

### 6.2. Стадия, переход и макрос имеют разные названия

Примеры стадий из той же «Продажи»:

| Подпись стадии | Программное имя стадии |
|---|---|
| Новый | `New` |
| Подготовка КП | `InWork` |
| Ожидает оплату | `PaymentAwaiting` |
| Выполняется | `InProgress` |
| Готов к отгрузке | `Ready` |
| Выполнен | `Complete` |

Стадия описывает состояние; подпись кнопки перехода — действие пользователя, например
«Начать выполнение» или «Вернуть на доработку». В существующем файле встречаются и кнопки
с подписью состояния («Выполнен»); не переименовывать их автоматически.

Отдельно у макроса есть своё имя: в переходах «Начать выполнение» используются `OnStart`
и `OnStarted`, а при передаче менеджеру — `GenerateSelectManagerInputForm`, `OnAssignManager`,
`OnManagerAssigned`. Это имена макросов в соответствующих слотах, не `CodeName` перехода.
В файле есть и описательные русские имена макросов. Выбирать понятное имя по назначению
макроса и его слоту, сохраняя имена программных объектов в коде без перевода.

У нескольких переходов может быть одна подпись кнопки, но разные исходные стадии,
условия и действия. Для изменения выбирать GUID перехода внутри конкретного GUID БП,
а не первое совпадение по подписи. Не приписывать переходу имя `OnStarted` только потому,
что так называется его макрос. Если программное имя нового перехода необходимо,
согласовать его по смыслу действия и проверить коллизии; не выдавать предложенное имя
за существующее в Business.

Общие правила полей CLI и смысл «Обновление включено» приведены в разделе 2.1
`Fastkore-Platform-Development-Guide.md`.

## 7. Производство

Производственные позиции, операции, задания и группировки связаны предметными обработчиками.
Прямое изменение статуса может преждевременно завершить позицию или пропустить зависимые
действия.

Текущий исходный код содержит публичную точку
`ProductionOperationWorkflow.SetCompleted(IEnumerable<Entity>)`, которая находит штатный
переход в завершённое состояние и выполняет его для операций. Это пример правильного подхода,
но перед использованием в макросе нужно подтвердить доступность сборки, namespace, типы и
совместимость версии сервера.

Для CLI сначала искать пользовательскую команду или переход. После выполнения проверять:

- статус выбранной операции;
- остальные операции той же производственной позиции;
- дочерние и сгруппированные позиции;
- задания и их статусы;
- журнал объекта и общий журнал событий.

Не считать, что закрытие одной операции должно или не должно завершать позицию, пока не
прочитаны все операции, группировки и события этой версии.

## 8. Бухгалтерские документы и платежи

Создание или изменение бухгалтерского документа может запускать нумерацию, расчёт сумм,
формирование связей с заказом, организацией, контрагентом, платежами и файлами.

Перед записью:

- определить точный тип документа по схеме;
- прочитать события компонента и команды пользователя;
- не задавать вычисляемые суммы и номер, если их формирует штатная логика;
- связывать документ с заказом и сметой только подтверждёнными связями;
- после операции сравнить объект, связи и журнал.

Если задача касается только подготовки данных отчёта, не создавать бухгалтерский документ.

## 9. Коммуникации и файлы

Для файлов Fastkore Business полностью действуют правила платформенного руководства. Папка
ссылок создаётся через `FileSet` и `FileService`, а не как обычный объект компонента «Файлы».

Обязательные `Usings`:

```text
Fastkore.Platform.Model.Data.Files
Fastkore.Platform.Presentation.Services
```

Правильный шаблон:

```csharp
FileSet fileSet = new FileSet(EventEntity.AsEntity.Connection);
string rootPath = FileService.GetDefaultLinkFolder(EventEntity.AsEntity);

var customerFolder = FileService.CreateDefaultLinkFolder(
    fileSet,
    rootPath + "/Файлы заказчика");
EventEntity.File.AddLink(customerFolder);

var technologistFolder = FileService.CreateDefaultLinkFolder(
    fileSet,
    rootPath + "/Файлы технолога");
EventEntity.File.AddLink(technologistFolder);
```

Не использовать `CreateEntity` с GUID компонента файлов и типа папки: это обходит файловую
модель, путь по умолчанию и правила уникальности.

## 10. Команды надстройки

Business содержит как конфигурационные команды с макросами, так и команды C#-надстройки.
Для headless-выполнения агент должен:

1. получить список доступных команд для конкретного объекта и пользователя;
2. проверить видимость и доступность;
3. вызвать штатную команду;
4. вернуть и заполнить стандартные вопросы и формы без предметного угадывания;
5. получить `alerts`, `questions`, `forms` и при наличии точный `ResultJson`;
6. проверить объект и журнал.

Нельзя создавать специальную зависимость CLI от Business только ради разбора результата.
Если Business-команде нужен машинный read-only результат, она может вернуть его через обычную
форму или журнал платформы.

## 11. События и радиус воздействия

Особенно тщательно читать обработчики до изменения:

- `Order`, `Estimate`, `EstimatePosition`;
- `AccountingDocument`, платежи и денежные операции;
- `StoreAction` и позиции движения;
- `ProductionPosition`, `ProductionOperation`, задания и группировки;
- `CommunicationEntry` и файлы.

Одна установка свойства может создать смету, пересчитать сумму, создать связь, изменить
остаток или запустить переход. Предварительная проверка должна описывать эти ожидаемые эффекты.

## 12. Правила переносимости

Между конфигурациями переносится алгоритм, но не клиентские данные. Без проверки запрещено
переносить GUID:

- организаций, складов и подразделений;
- пользователей, групп и ролей;
- статей движения денег и счетов;
- значений клиентских списков;
- команд, отчётов и HTTP-служб;
- любых объектов предметных данных.

Не копировать токены, пароли, `Authorization`, адреса webhook и другие секреты из примеров.

## 13. Обязательный порядок работы через CLI

Для любой нетривиальной операции Business:

1. выбрать профиль и проверить подключение без раскрытия секрета;
2. прочитать solution, компонент, тип, свойства и связи;
3. прочитать события, команды, доступы и бизнес-процессы;
4. найти рабочий аналог того же типа;
5. сформировать минимальный план по одному объекту или одной связи на шаг;
6. выполнить `check`/`dry-run`, если команда их поддерживает;
7. перечитать ревизию перед записью;
8. запросить требуемое подтверждение и использовать `--change-note`;
9. выполнить штатную операцию с разрешением побочных эффектов только в согласованной области;
10. перечитать объект, обе стороны связей и журнал объекта;
11. при частичном результате остановиться и показать его, а не повторять запись вслепую.

## 14. Контрольный список Business

Перед применением агент обязан подтвердить:

```text
[ ] Версия и фактическая схема сервера прочитаны через CLI
[ ] MacroName, FieldName, типы и связи не угаданы
[ ] Код надстройки не перепутан с контекстом макроса
[ ] Смета заказа не создаётся повторно
[ ] Нумерация не подменяется без требования
[ ] Статус склада меняется штатной предметной операцией
[ ] Статус процесса меняется переходом, а не числом
[ ] Производственная операция использует штатный workflow
[ ] Для файлов используются FileSet и FileService
[ ] События целевых и связанных компонентов прочитаны
[ ] Клиентские GUID и секреты не перенесены
[ ] Изменение минимально и проверяемо по журналу
```

Если критический пункт не подтверждён, агент продолжает read-only исследование и не записывает
изменения.
