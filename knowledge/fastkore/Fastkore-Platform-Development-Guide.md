# Fastkore: руководство по разработке для внешнего агента

Порядок чтения для CLI Dev: AGENT-START.md. Общие и выбранные тематические разделы
читать полностью, включая обязательные предусловия; всё руководство перечитывать не требуется.

Этот документ дополняет `FastkoreCLI-Agent-Guide.md` правилами разработки макросов и
конфигурации на платформе Fastkore. Он универсален и не зависит от Fastkore Business.

Для конфигурации Fastkore Business дополнительно прочитать
`Fastkore-Business-Development-Guide.md`. Business-дополнение не заменяет этот документ.

## 1. Сначала определить уровень кода

В Fastkore существуют разные программные среды. Код между ними нельзя переносить механически.

| Уровень | Где выполняется | Основная модель |
|---|---|---|
| Макрос конфигурации | Command, Event, Access, Workflow, HTTP Service, Scheduler | динамические Entity и Macro API |
| FastkoreCLI | отдельный headless-клиент | типизированные команды CLI с проверками и ревизиями |
| Надстройка | собранная C#-сборка | типизированная Model API, транзакции и extension-классы |

Перед написанием кода агент обязан назвать уровень. Пример из надстройки может подтверждать
назначение API, но не доказывает, что все его классы и переменные доступны в макросе.

## 2. Источники истины

Для развёрнутого сервера приоритет такой:

1. `schema entity-set show`, `solution tree`, `element show` и другие read-команды CLI;
2. текущая конфигурация и экспорт VCS с этого же сервера;
3. актуальный исходный код платформы или используемой надстройки;
4. рабочий макрос того же типа и контекста;
5. документация и примеры;
6. предположение — недопустимый источник для записи.

Нельзя угадывать:

- GUID компонента, типа, свойства, связи, роли или элемента;
- `MacroName`, `FieldName`, `MacroPropertyName`;
- направленность и кратность связи;
- тип значения списка;
- доступную переменную контекста;
- namespace, Reference или Function Library;
- этап или внутренний ключ бизнес-процесса.

Если символ не подтверждён схемой либо рабочим аналогом, остановиться и продолжить поиск.

### 2.1. Имена и флаги определения бизнес-процесса

Не смешивать название процесса, его программное имя и свойство стадии объекта:

| Поле редактора | Поле модели | `workflow definition list` | `workflow definition show`: определение |
|---|---|---|---|
| Наименование | `Name` | `name` | `name` |
| Наименование в макросах | `CodeName` | `codeName` | `codeName` |
| Имя свойства | `PropertyName` | `stagePropertyName` | `stageProperty.name` |
| Имя свойства в макросах | `PropertyCodeName` | `stagePropertyCodeName` | `stageProperty.codeName` |
| Включён | `IsEnabled` | `enabled` | `enabled` |
| Обновление включено | `IsLocked` | `locked` | `locked` |

Это соответствие **читаемого ответа**, не шаблон записи. Для записи предварительно прочитать
контракт поддерживаемой команды; нельзя передавать read-ответ целиком как update-спецификацию.

Правила агента:

1. Для нового БП заранее определить обе понятные подписи и оба программных имени.
   Для новых программных имён предпочитать осмысленный английский PascalCase без пробелов,
   дефисов и ключевых слов C#. Принятые суффиксы сверять с конфигурацией, не навязывать
   универсальный шаблон всем конфигурациям.
2. Проверить коллизии в целевом компоненте, включая другие БП, свойства, связи и наследование.
   Программное имя свойства стадии — не подпись формы и не имя процесса.
3. При изменении существующего определения сохранять программные имена побайтно, даже
   если подпись была переименована или английское имя выглядит устаревшим. Изменение
   `CodeName`/`PropertyCodeName` — отдельное изменение программного контракта: проверить
   макросы, фильтры, формы, интеграции и код надстройки, а не делать это попутно.
4. Стадия описывает состояние, переход — действие. Подпись команды, программное имя
   перехода и имя его макроса — разные поля; ни одно не заменяет другое.
5. Выбирать существующие БП, стадии и переходы по GUID. Подписи могут повторяться;
   при неоднозначном программном имени тоже использовать GUID.
6. В плане и после записи проверять все четыре поля имён по отдельности. Если нужное
   поле пока нельзя передать через CLI, сообщить ограничение, не обходить его прямой
   правкой экспортов конфигурации.

Особенно важно: `locked` в этом ответе **не означает извлечение другим пользователем
или запрет ручного редактирования**. Флажок «Обновление включено» прямо связан с
`IsLocked` в `Constructor\Workflow\WorkflowPropertiesControl.xaml`.
Штатная установка `.fkwf` вызывает `EntityWorkflowScheme.Import(..., checkLocked: true, ...)`:
для уже существующего БП сохраняются текущие `IsEnabled` и `IsLocked`; при `IsLocked = false`
его определение пропускается, при `true` разрешено обновление из поставки.
Это отдельная настройка от включённости процесса и от извлечения/регистрации изменений
(`State`, `LockedBy`; в `definition show` также `lockedByGuid` и `lockedByName`).

Не переключать «Обновление включено» ради получения доступа к редактированию. Не менять
этот флаг без согласования: включение может привести к замене локальных доработок при
следующей установке, отключение — к пропуску новых версий поставляемого БП. Состояние
флага проверять на сервере, а не выводить из имени, происхождения или отсутствующего XML-поля.

Примеры именно Fastkore Business находятся в разделах 6.1–6.2 отдельного
`Fastkore-Business-Development-Guide.md`; CLI остаётся универсальным.

## 3. Обязательный цикл агента

1. Проверить профиль и сервер командой `auth test`.
2. Прочитать `agent describe "имя команды" --json` для незнакомой команды; повторно использовать контракт для той же сборки (cliBuildId). Полный каталог читать только при поиске неизвестной команды.
3. Найти Solution, компонент, тип, свойства и связи.
4. Прочитать целевой элемент и его ревизию.
5. Определить тип и контекст макроса.
6. Изучить релевантные примеры похожей задачи или нужного приёма, проверить совместимость
   контекста, включая простое чтение полей;
   подтвердить типы и связи. Если аналога нет, зафиксировать поиск и проверить API по
   руководству/исходникам. Правила выбора и сохранения примеров — раздел 6.
7. Экспортировать текущую версию исходника.
8. Подготовить минимальное изменение в отдельном файле; проверить читаемость и сохранение
   отображаемых значений по разделу 6 до компиляции.
9. Выполнить `validate` с текущим hash и `--warnings-as-errors`.
10. Для поддерживаемой операции выполнить `--dry-run`.
11. Повторно прочитать ревизию непосредственно перед записью.
12. Применить только после разрешения пользователя и с `--change-note`.
13. Повторно прочитать элемент, проверить журнал и экспорт VCS.
14. Сохранить новый повторно используемый приём по шаблону `Fastkore-Macro-Recipes.md`,
    указав фактический уровень проверки; обновить существующий рецепт вместо дубликата.

Нельзя автоматически заменять конфликтующий hash или revision флагом `--force`.

## 4. Контексты макросов

### Command

Обычно доступны:

```csharp
SelectedEntity
SelectedEntities
UI.LinkOwner
UI.SelectedEntities
```

`EventEntity` в Command не использовать без подтверждённого контракта.

Перед написанием Command.Action обязательно читать [инструкцию по командам](Fastkore-Command-Agent-Guide.md):
progressName должен содержать текст операции, placement — выбранные места отображения.
Это metadata элемента, macro apply исходника не меняет эти настройки.

### EventHandler

Основной объект:

```csharp
EventEntity
```

В зависимости от события могут быть доступны:

```csharp
ChangedProperty
ChangedLink
LinkedEntity
OldPropertyValue
ToStage
Transition
```

Переменная должна соответствовать конкретному типу события.

### EntityAccess

Возможны:

```csharp
CheckEntity
AccessEnabled
CommandEnabled
CommandId
CommandText
```

### HTTP Service

```csharp
PostData
ResultData
```

### Workflow-проверка

Контекст проверки перехода определяется самим элементом перехода. Нельзя автоматически считать,
что там существует `SelectedEntity`: сначала прочитать рабочую проверку того же вида или контракт,
возвращаемый CLI.

## 5. Изменение Entity в макросе

В макросе конфигурации не использовать обычные ORM-паттерны:

```csharp
entity.Save();
context.SaveChanges();
repository.Update(entity);
```

Обычное изменение выполняется присваиванием:

```csharp
EventEntity.Name = "Новое имя";
EventEntity.Deadline = Now.AddDays(2);
```

Платформа сохраняет изменение в окружающей транзакции макроса.

`Edit()` также не вызывается автоматически перед каждым присваиванием.

### Когда `Edit()` нужен

Перед использованием транзакционного контекста на исходном объекте:

```csharp
SelectedEntity.Edit();

SelectedEntity.AsEntity.Transaction.SetContext(
    "Order",
    SelectedEntity
);

UI.CreateEntity(
    Id.Task.Guid,
    Id.Task.Type.OrderTask
);
```

Специализированный API может иметь собственное требование `Edit()`. Такое требование должно быть
подтверждено рабочим примером или реализацией API.

## 6. Идентификаторы и схема

Для исходника макроса первый выбор — прямой доступ через подтверждённые программные
свойства и связи текущего объекта. Приоритет GUID в CLI относится к адресации ресурсов,
а не к стилю макроса. Когда метод требует идентификатор, предпочитать `Id.*` текущей схемы:

```csharp
Id.Order.Guid
Id.Order.Type.SalesOrder
Id.Order.Prop.Deadline
Id.Order.Link.Contractor
```

Raw GUID допустим только когда:

- нужная операция не решается прямым доступом через подтверждённое свойство или связь;
- в текущей схеме нет соответствующего `Id.*`;
- GUID прочитан с того же сервера;
- значение не является клиентским секретом или переносимым предположением;
- причина зафиксирована в описании изменения.

Имена интерфейса локализованы и не заменяют `MacroName`, `FieldName` или GUID.

### 6.1. Изучение примера до генерации

Сначала искать релевантные макросы похожей задачи, работы с нужным объектом, связью или
API в целевой конфигурации или её актуальном экспорте, затем в решении «Примеры макросов».
Точного аналога задачи не требуется. Предпочитать тот же контекст; для другого проверить
совместимость переменных, транзакций и доступного API. Читать все макросы не требуется:
если существенная часть задачи не покрыта примерами, продолжить адресный поиск.
Прочитать исходник, Usings,
References, Function Libraries и схему используемых свойств/связей. Исходники надстройки
уточняют API, но не заменяют пример макроса. Найденный код проверять на соответствие
текущим правилам: само наличие в конфигурации не доказывает корректность или выполнение.
Если подходящего примера нет, указать, где искали, и подтвердить API документацией или
реализацией. Не обходить поиск написанием собственного универсального слоя доступа.

Не создавать `ReadDisplayValue(Guid)`, `ReadLinkDisplayValue(Guid)`, reflection-обёртки
или словари GUID для обычного доступа, доступного через Macro API. Использовать текущий
объект и его связи, не искать их заново без причины. Helper допустим для действительно
необходимого форматирования, подтверждённой семантики или повторяемой логики; причину
объяснить. Число строк само по себе не является критерием качества.

### 6.2. Читаемость не должна менять смысл

Перед компиляцией проверить:

- тип каждого значения подтверждён; `dynamic` не делает произвольное приведение безопасным;
- для списка и стадии получена нужная подпись штатным подтверждённым API: `(string)` и
  `ToString()` не гарантируют отображаемое значение;
- вероятность, статус и стадия процесса различены по схеме и требованиям;
- `null`, пустая строка и подпись отсутствующего значения обработаны по исходной логике:
  `??` не заменяет `IsNullOrWhiteSpace`;
- для дат подтверждены тип, часовой пояс при необходимости и значение отсутствующей даты;
- для денег и процентов подтверждены культура, точность и единица хранения (доля или процент);
- каждый raw GUID, helper, повторный запрос и приведение имеют конкретную необходимость.

Например, замена чтения отображаемого статуса на
`(string)order.OrderProbability ?? (string)order.Status` не считается исправлением без
проверки типов, назначения полей и правил fallback. Прямой доступ по имени улучшает
читаемость, но не доказывает эквивалентность. Имена из примера пользователя также проверять.
Успешная компиляция не проверяет динамические свойства и фактические подписи.

В отчёте кратко назвать пример-источник и выбранный подход; новые проверенные приёмы
сохранить по [правилам рецептов](Fastkore-Macro-Recipes.md). Перед следующей задачей
прочитать релевантные рецепты и проверить их применимость к текущей версии.

## 7. Поиск объектов и фильтры

Один объект:

```csharp
var order = FindEntity(
    Id.Order.Guid,
    F("$Guid", "=", orderGuid)
);
```

Набор объектов:

```csharp
var orders = FindEntities(
    Id.Order.Guid,
    F("$Type", "=", Id.Order.Type.SalesOrder)
);
```

Если в цикле нужны связи, заранее загрузить их подтверждёнными `LP(...)`:

```csharp
IEnumerable<dynamic> orders = FindEntitiesWithLinks(
    Id.Order.Guid,
    F("$Type", "=", Id.Order.Type.SalesOrder),
    LP(Id.Order.Link.Contractor),
    LP(Id.Order.Link.Estimate, Id.Estimate.Link.EstimatePosition)
);
```

Фильтр составляется только из идентификаторов текущей схемы. Сериализованный фильтр нельзя
переносить на другой компонент.

## 8. Связи и удаление

Это три разные операции:

```csharp
owner.Contact.AddLink(contact);       // добавить связь
owner.Contact.RemoveLink(contact);    // удалить связь
contact.Delete();                     // удалить сам объект
```

Перед записью проверить направленность, второе macro-имя и кратность связи. Для одиночной связи и
коллекции синтаксис может различаться.

## 9. Создание обычного объекта

В макросе:

```csharp
var task = CreateEntity(
    Id.Task.Guid,
    Id.Task.Type.OrderTask
);

task.Subject = "Новая задача";
task.StartTime = Now;
```

`Save()` после этого не вызывается. Нужно учитывать все события создания компонента: они могут
заполнить поля, создать связанные объекты либо запретить операцию.

Через CLI обычные записи создаются только командой `data create` после `data create describe` и
`data create validate`, с точным GUID типа, подтверждением и разрешением побочных эффектов.

## 10. Transaction Context

Контекст передаёт данные в объект, создаваемый в той же цепочке:

```text
Command
  -> Edit исходного объекта
  -> Transaction.SetContext
  -> UI.CreateEntity
  -> EntityCreating
  -> Transaction.GetContext
```

Ключ контекста и ожидаемый тип должны совпадать точно. Нельзя использовать context как глобальное
хранилище между независимыми транзакциями.

## 11. Файловая подсистема — обязательное специальное правило

Файлы и папки Fastkore не являются обычными объектами произвольного компонента. Для них есть
специализированные классы:

```csharp
FileSet
FileService
FileEntity
FolderEntity
```

Обязательные `using`:

```csharp
Fastkore.Platform.Model.Data.Files
Fastkore.Platform.Presentation.Services
```

Если компилятор не находит `FileSet` или `FileService`, сначала проверить эти `using`. Нельзя
заменять неизвестный символ собственным `CreateEntity`.

### 11.1. Запрещённый способ создания папки

Такой код создаёт обычные Entity компонента файлов и не соблюдает файловую модель:

```csharp
var customerFolder = CreateEntity(
    new System.Guid("150f4c00-608f-4dc3-87c0-4cb1a482311e"),
    new System.Guid("f4fac64f-550a-42d8-b1d1-c5818c9f2021")
);

customerFolder.Name = "Файлы заказчика";
EventEntity.File.AddLink(customerFolder);
```

Запрещено исправлять этот код подбором других GUID. Архитектурно неверен сам `CreateEntity`.

### 11.2. Правильное создание связанных папок

```csharp
FileSet fileSet = new FileSet(EventEntity.AsEntity.Connection);

var customerFolder = FileService.CreateDefaultLinkFolder(
    fileSet,
    FileService.GetDefaultLinkFolder(EventEntity.AsEntity) + "/Файлы заказчика"
);

EventEntity.File.AddLink(customerFolder);

var technologistFolder = FileService.CreateDefaultLinkFolder(
    fileSet,
    FileService.GetDefaultLinkFolder(EventEntity.AsEntity) + "/Файлы технолога"
);

EventEntity.File.AddLink(technologistFolder);
```

Для Command вместо `EventEntity` использовать подтверждённый `SelectedEntity`:

```csharp
FileSet fileSet = new FileSet(SelectedEntity.AsEntity.Connection);
string basePath = FileService.GetDefaultLinkFolder(SelectedEntity.AsEntity);
```

### 11.3. Что делает API

`GetDefaultLinkFolder` формирует платформенный путь, учитывая компонент, объект, дату и настройки
файловой связи. `CreateDefaultLinkFolder` создаёт `FolderEntity` через `FileSet`, транзакцию и
штатную регистрацию версии.

При конфликте имени текущая реализация может подобрать имя с суффиксом `(2)`, `(3)` и далее.
Поэтому повторяемое событие должно иметь явную стратегию идемпотентности: сначала проверить,
нужно ли создавать и связывать папку повторно. Нельзя молча плодить папки при каждом сохранении.

### 11.4. Перемещение файла

Подтверждённая операция дерева файлов:

```csharp
copiedFile.AsEntity.MoveTo(folder.AsEntity);
```

`MoveTo` меняет положение файла в файловом дереве. Не нужно дополнительно добавлять тот же файл в
папку через выдуманную связь. Связь файла или папки с бизнес-объектом — отдельная операция и
выполняется только через реальную файловую связь владельца.

### 11.5. Другие операции

В платформе существуют, в частности:

```text
FileService.GetDefaultLinkFolder
FileService.CreateDefaultLinkFolder
FileService.ReplaceInvalidFileNameChars
FileService.AddLinkedFiles
FileService.AddFile
FileService.AddFiles
```

Перед использованием проверить точную перегрузку в текущей версии. Нельзя придумывать методы
`CreateFolder`, `SaveFolder`, `MoveFile` или `AddFolder` для Macro API.

### 11.6. Проверка файлового макроса

Перед применением подтвердить:

- выбран правильный контекст (`EventEntity` или `SelectedEntity`);
- добавлены оба namespace;
- используется `FileSet` соединения владельца;
- базовый путь получен через `GetDefaultLinkFolder`;
- папка создаётся через `CreateDefaultLinkFolder`;
- связь существует в схеме и доступна нужному типу;
- повторный запуск не создаст нежелательные дубликаты;
- нет `CreateEntity` для папки;
- нет лишнего `AddLink` после `MoveTo` внутри дерева.

## 12. Usings, References и Function Libraries

Это три независимых механизма:

- `Usings` делает namespace видимым;
- `References` подключает сборку компилятору макроса;
- `Function Libraries` подключает библиотеку функций к конкретному макросу.

Платформа автоматически добавляет каждому C#-макросу следующие `using`:

```text
System
System.Collections.Generic
System.Collections.ObjectModel
System.Linq
System.Text
System.Threading.Tasks
System.Xml
System.IO
System.Windows
Fastkore.Platform.Model.Data
Fastkore.Platform.Model.Extensibility.Macros
Fastkore.Platform.Model.Extensibility.Macros.en
Fastkore.Platform.Model.Extensibility
```

При выключенном английском API вместо
`Fastkore.Platform.Model.Extensibility.Macros.en` подключается пространство имён
`.ru`. Не добавлять перечисленные пространства имён в поле `Usings` повторно. В
частности, `System.Collections.Generic` и `System.Linq` уже доступны без явного
подключения.

В Dev/.NET 10 компилятор подключает базовые .NET/WPF-сборки по расположению типов,
TRUSTED_PLATFORM_ASSEMBLIES текущего процесса, Fastkore.Platform.Model.dll,
Fastkore.Platform.Presentation.dll и входные сборки установленных надстроек.
System.Text.Json и System.Net.Http входят в runtime-набор; новые References для них
в текущем Dev не нужны. Не переносить имена/пути DLL .NET Framework из старой поставки.
На установленной целевой версии подтвердить зависимости macro validate.

Подключённые Function Libraries дополнительно передают макросу свои `Usings` и
`References`. Перед добавлением зависимости сначала прочитать текущие metadata
макроса и его библиотеки функций. Существующие дополнительные зависимости при
частичном обновлении сохранять; новые добавлять только для символов, которые не
покрываются автоматическим набором.

При ошибке `type or namespace could not be found`:

1. остановиться;
2. найти рабочий пример символа;
3. проверить `Usings`;
4. проверить `References`;
5. проверить подключённые Function Libraries;
6. только затем изменять Source.

Не угадывать DLL или namespace.

## 13. JSON и HTTP Service

Вход и выход:

```csharp
PostData
ResultData
```

Для новых и мигрируемых .NET 10 макросов использовать System.Text.Json, для исходящего
HTTP — System.Net.Http.HttpClient. Старые JavaScriptSerializer/System.Web.Extensions.dll
и слой совместимости не являются рабочим путём разработки. Подробный цикл и готовые
фрагменты: [HTTP/JSON .NET 10](Fastkore-NET10-Macro-Agent-Guide.md).
Для устойчивого JSON-контракта использовать DTO со свойствами и JsonPropertyName
из подключённой Function Library; для неизвестного JSON — JsonDocument.
Секреты Authorization, токены и пароли нельзя выводить, логировать или переносить в исходник.

Для панелей аналитики на обновлённом движке читать
[инструкцию Dashboard](Fastkore-Dashboard-Agent-Guide.md): API осей, легенды,
динамических рядов, сплайна, порогов, обновления и приёмки. Примеры Chart относятся
к макросам элемента панели; их не переносить в Command/HTTP Service.

## 14. Формы ввода

Использовать только подтверждённые методы текущего UI API, например:

```csharp
var form = UI.CreateInputForm("Введите значения");
var nameField = form.AddString("Наименование");
nameField.IsRequired = true;

if (form.Show())
{
    SelectedEntity.Name = nameField.Value;
}
```

Доступность `AddText`, `AddInteger`, `AddFloat`, `AddDate`, `AddFlag`, `AddValueSelect`,
`AddEntitySelect`, `SetPosition`, `MinWidth` и `MaxWidth` проверять по установленной версии и
рабочему примеру. Для headless-выполнения вопросы и формы передаются через контракт `command
invoke`, а ответы не угадываются агентом.

## 15. Null-safety и типы

Перед цепочкой ссылок проверить каждое необязательное звено:

```csharp
if (EventEntity.Contractor != null &&
    EventEntity.Contractor.MainContact != null)
{
    var emails = EventEntity.Contractor.MainContact.EMail;
}
```

Для ValueList сначала определить физический тип свойства: `Int32`, `Guid` и `String` требуют
разных значений. Для дат, длительностей и единиц измерения не полагаться на отображаемый текст.

## 16. Workflow и статусы

Если существует специализированный API перехода, использовать его вместо прямого присваивания
поля статуса. Перед выполнением через CLI сначала вызвать `workflow check`, передать точный текущий
stage token, revision и modified timestamp, затем выполнить переход только после разрешения.

## 17. Ошибки компиляции и выполнения

При ошибке компиляции:

```text
STOP
-> найти рабочий пример
-> проверить контекст
-> проверить схему
-> проверить Usings
-> проверить References
-> проверить Function Libraries
-> внести минимальное исправление
```

При runtime-ошибке нельзя добавлять пустой `catch`. Нужно определить объект, событие, тип значения,
связь и вызываемый специализированный API. Журнал читается через CLI и сопоставляется с историей
целевого объекта.

## 17.1. Название нового элемента конфигурации

Перед созданием команды, события, фильтра, доступа, отчёта, службы, задания, панели или другого
элемента Solution проверить его create-контракт. Если модель элемента имеет отдельное поле
`Name`/`name`/«Название», агент обязан заполнить его сразу при создании.

Название должно:

- быть непустым и понятным человеку;
- кратко описывать назначение элемента, например «Уведомление на почту о создании заявки на закупку»;
- отличать элемент от соседних элементов того же владельца;
- не содержать секреты, технические токены или случайные GUID;
- сохранять язык пользовательского интерфейса целевой конфигурации.

Нельзя оставлять поле пустым, рассчитывая на последующее ручное редактирование. Нельзя подменять
отдельное название значением `MacroName`, именем файла, текстом кнопки или комментарием к изменению.
Эти поля могут иметь разные назначения и одновременно присутствовать в модели.

Обязательная проверка:

```text
create contract/template
-> name заполнено в spec
-> dry-run показывает name
-> create
-> element show возвращает сохранённое name
```

Если модель платформы содержит название, но CLI не принимает его при создании, не создавать
неполный элемент. Зафиксировать это как пробел create-контракта CLI и передать в разработку.

## 18. Минимальный patch и сохранение metadata

При изменении существующего элемента сохранять без необходимости:

- GUID и тип элемента;
- Event/Command и placement;
- роли и правила доступа;
- ValidationFilter и ValidationMacro;
- Usings, References и Function Libraries;
- остальные макро-слоты;
- включённость и настройки владельца.

Отсутствующее поле update-спецификации должно означать «сохранить», а не «очистить». Явный `null`
используется только когда контракт команды документирует очистку.

## 19. Секреты и переносимость

Никогда не переносить между серверами без проверки:

- GUID пользователя, роли, организации, склада или счёта;
- ValueList и workflow GUID;
- сериализованные фильтры;
- endpoint identifiers;
- API keys, токены, пароли и Authorization.

В выводе и примерах секрет заменяется на `<SECRET>` или `<TOKEN>`.

## 20. Финальный pre-flight

Перед записью агент должен ответить:

- какой сервер и профиль используются;
- какой Solution, компонент, тип и элемент изменяются;
- какой контекст макроса выбран;
- где подтверждены свойства, связи и API;
- какие Usings, References и Function Libraries нужны;
- какие события и побочные эффекты возможны;
- почему изменение минимально;
- какой hash/revision прочитан;
- чем проверен dry-run;
- какое понятное название задано новому элементу, если модель содержит `Name`;
- как будет проверен результат и журнал.

Для файлов дополнительно пройти checklist раздела 11.6. Если критическая информация неизвестна,
не применять изменение.
