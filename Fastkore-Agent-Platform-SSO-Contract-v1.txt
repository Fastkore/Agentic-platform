1. РЕЗУЛЬТАТ И ГРАНИЦЫ

Пользователь открывает Agent Platform из общей кнопки ассистента в карточке, основном или связанном списке ERP. В существующем окне WebView2 показываются доступные ему проекты и чаты без повторного ввода пароля. Выбор агента, инструментов и проекта остаётся на стороне платформы.

Архитектура Fastkore является исходной: существующий реестр сервисов, штатная ERP-сессия, GUID пользователей, права и серверный конфиг. Дополнительные справочники пользователей/подключений в ERP не создаются. Единственный локальный парольный вход в Agent Platform предназначен администраторам платформы для настройки ERP-подключений, проектов и прав. Обычные пользователи появляются при подтверждённом обращении из ERP и входят только через Fastkore.

Обмен билетом не содержит объекта ERP, suggestedAgent или ID чата. Контекст текущего представления передаётся отдельным сообщением WebView2 после входа, см. дополнение. Открытие окна не привязывает объект к чату и не запускает анализ.

Предустановленный сервис и синий режим WebView2 уже подготовлены в Fastkore Dev. SSO, серверный секрет доверия, выпуск/проверка билетов и cookie-аутентификация в обеих кодовых базах ещё требуют реализации. Настройка Codex, очередь и ограничения исполнения сохраняются; успешный SSO сам по себе не включает BRIDGE_EXECUTION и не даёт доступа к данным ERP.

2. ЧТО УЖЕ ЕСТЬ В AGENTIC-PLATFORM

server/access.ts:
- Access.issue создаёт credential с хешем случайного токена; текущая локальная session живёт 12 часов. Access.authenticate повторно проверяет существование credential, срок и disabled пользователя.
- Access.change сериализует изменения доступа и сохраняет их через существующий Store.
- Access.createKey разрешает выпуск бессрочного API-ключа любому credential.kind === 'session'. Поэтому одного kind для SSO недостаточно: необходимо учитывать source.

server/app.ts:
- /api/auth/login, /api/auth/me и /api/auth/logout уже есть. Аутентификация сейчас только Bearer; principal(request) заново читает Authorization, в том числе после await.
- Общая защита API отклоняет чужой Origin только при наличии заголовка. Это не полная CSRF-защита для cookie.
- Маршруты /auth/* находятся вне текущей ветки проверок /api/*: им отдельно нужны no-store, ограничения размера/частоты и проверки входа.
- Парсер application/x-www-form-urlencoded и cookie-поддержка не подключены. Общий обработчик ошибок выдаёт { "error": "сообщение" }.

client/main.tsx и client/AccessPanel.tsx:
- bridge-key читается из sessionStorage и подставляется в Authorization; начальный loggedIn зависит от наличия этого ключа.
- bridge-project/bridge-chat сохраняются в localStorage, остальные данные и черновики — в состоянии React.
- Панель аккаунта сейчас показывает смену пароля и выпуск API-ключа без разделения способов входа.

shared/types.ts и server/store.ts:
- Уже существуют ExternalIdentity, State.externalIdentities и SQLite-таблица external_identities с PRIMARY KEY(installation_id, external_user_id). Новый реестр пользователей или вторую таблицу соответствий создавать не надо.
- Credential уже содержит необязательные source: 'local' | 'fastkore' и installationId. Поля надо начать заполнять и проверять.
- Записи пользователей/credentials сохраняются существующим Store; выдача cookie должна происходить только после успешного сохранения.

server/corporate.ts и server/workspace.ts:
- Административный role и рабочий roleId различаются. Стандартная рабочая роль employee уже разрешает universal/chat — она не является ролью без прав.
- Job хранит credentialId. Очередь проверяет срок/отзыв credential перед выполнением и во время работы; активное задание перепроверяется каждые 200 мс. Для SSO этот контроль необходимо сохранить и дополнить состоянием установки.

В коде пока нет выдачи/обмена SSO-билетов, cookie-сессий и действующего реестра доверенных ERP-подключений. Их упоминание в проекте контракта — план, а не готовый API.

3. ИДЕНТИФИКАТОРЫ И НАСТРОЙКИ

IntegrationServiceGuid = 33040cfb-9073-43a5-a184-5039db13924b.
Это GUID предустановленной ЗАПИСИ в справочнике «Сервисы» Fastkore; её штатный тип остаётся «Сервис». GUID одинаков для всех установок и не является секретом или идентификатором установки.

installation_id: отдельный UUID регистрации конкретной логической установки ERP. Его создаёт Agent Platform при административной регистрации подключения, а Fastkore получает вместе с ключом. Смена DNS, обновление и восстановление той же установки ID не меняют. Независимая тестовая копия получает отдельную регистрацию, ID и секрет. В ERP это значение защищённой конфигурации одной предустановленной интеграции, не новый объект справочника.
fastkore_user_id: существующий Connection.UserGuid. Не Connection.UserId, не логин, не SID, не номер сотрудника. При удалении и повторном создании пользователя новый GUID означает новую внешнюю личность.
audience: точная строка fastkore-agent-platform.
UUID в обмене: нижний регистр, стандартная запись с дефисами. Время: UTC RFC 3339, например 2026-11-11T12:00:00Z.

На стороне Fastkore:
- BaseUrl остаётся в существующей карточке сервиса. Для пилота это https://agentic-platform.fastkore.ru/; маршруты ниже размещены в корне origin.
- Один AgentPlatformConnectionKey и enabled хранятся в защищённой серверной конфигурации и логически привязаны к IntegrationServiceGuid. installation_id извлекается из ключа, отдельная запись/таблица не нужна. Состояние и публичный installation_id могут сообщаться клиенту; ключ — никогда.
- Обычное поле Service.Secret с HideValue нельзя использовать как серверное защищённое хранилище: скрытие значения в интерфейсе не запрещает его загрузку клиентом.
- Ключ создаёт платформа из криптографически случайного секрета, не пользователь вручную. Он не связан с паролем пользователя и не поставляется предзаполненным. Использовать защищённое серверное хранение для выбранной ОС. На Windows — защита под учётной записью службы/штатный серверный механизм защищённых секретов; на Linux — серверный secret store с ограниченным доступом. Не подменять защиту маской в форме или общей зашитой в код константой шифрования.
- Адрес сервиса и ключ меняет только администратор. Для BaseUrl/записи сервиса это обеспечивается штатными серверными правами Fastkore; одного скрытия кнопок недостаточно. Обычный пользователь, способный изменить доверенный origin, смог бы направить вход на чужую страницу. Новое поле ключа не должно попасть в универсальную загрузку EntitySet даже для просмотра карточки.
- Право запуска: для v1 предлагается штатное право ReadEntity на фиксированную запись сервиса, проверяемое сервером, плюс действующий пользователь и включённая интеграция. Это не заменяет права платформы и права на бизнес-объекты. Если потребуется отдельное право запуска, согласовать его до реализации.

На стороне Agent Platform:
- BRIDGE_PUBLIC_ORIGIN=https://agentic-platform.fastkore.ru (без завершающего слеша).
- В административном интерфейсе добавить подключения Fastkore: название, installation_id, доверенный HTTPS validate_ticket_url, состояние и действие выпуска/смены ключа. Это настройки платформы; универсальный конструктор подключений и новый ERP-справочник не нужны.
- Метаданные подключений сохранять сервером через существующий Store отдельным непубличным разделом; секрет хранить защищённо. Если размещение требует отдельного secret store, в метаданных сохранять только ссылку на секрет. Не заводить одновременно независимые файловый и SQLite-реестры подключений.
- Не включать секрет в Settings/shared DTO: /api/status сейчас возвращает settings. Административное чтение также не должно выдавать секрет обратно.
- Файлы секретов не входят в репозиторий, web-root и проекты агента. Доступ процесса исполнения к ним должен быть исключён в целевой среде; одно расположение вне проекта не доказывает изоляцию общего OS-пользователя.

Логическая модель подключения платформы (пример без секрета, не публичный Settings):
{
  "version": 1,
  "installations": [{
    "name": "Основная ERP",
    "installation_id": "<UUID установки ERP>",
    "enabled": false,
    "validate_ticket_url": "https://<доверенный сервер ERP>/api/ai/validate-ticket",
    "secret_ref": "<внутренняя ссылка на защищённый секрет>",
    "auto_provision": true,
    "default_role_id": "sso_pending",
    "session_ttl_seconds": 1800
  }]
}

3.1. ВЫПУСК КЛЮЧА И НАСТРОЙКА ПОДКЛЮЧЕНИЯ

1) Локальный администратор платформы регистрирует конкретную ERP и её HTTPS-адрес проверки. Платформа создаёт installation_id и 32 случайных байта секрета; подключение пока выключено.
2) Платформа однократно показывает ключ подключения в формате:
   fkap1.<installation_id в формате UUID>.<43 символа Base64URL секрета>
   Например fkap1.<UUID>.<СЕКРЕТ>, без реальных значений в документации.
3) Администратор Fastkore указывает BaseUrl в существующем сервисе, а ключ вводит через настройки СЕРВЕРА в защищённое поле AgentPlatformConnectionKey. В WPF-клиент ключ не возвращается. Если настройка выполняется удалённой административной командой, она должна быть write-only, по защищённому каналу, с проверкой полномочий сервером; отдельный справочник не требуется.
4) Администраторы подтверждают, что адрес проверки относится именно к этой ERP, и включают интеграцию с обеих сторон. Выполняется тест входа обычного ERP-пользователя с проверкой его GUID, а не только проверка HTTP 200.
5) При смене ключа installation_id сохраняется, секрет заменяется. Ключ от другой регистрации не принимается как ротация текущей. Старый ключ немедленно перестаёт работать; платформа отзывает SSO credentials этой установки, ERP инвалидирует её непогашенные билеты. Для пилота ротация требует повторного входа, без одновременного окна действия старого/нового ключа.

Платформа предъявляет полный ключ fkap1... в Authorization: Bearer серверу ERP при validate-ticket. Fastkore сверяет версию ключа, installation_id и секрет. В обратную сторону платформа доверяет только ответу заранее зарегистрированного ERP endpoint по проверенному HTTPS, строго сверяя поля ответа. Никакой URL из браузера не участвует в выборе этого endpoint. Секрет НЕ является персональным ccb_k_ ключом и не разрешает проекты, чаты, запуск задач или произвольный ERP API. Публичный веб-вход сам по себе не создаёт авторизованную сессию.

Платформе нужна защищённая восстанавливаемая копия ключа для исходящего validate-ticket. Нельзя просто положить его хеш в существующий список пользовательских API-ключей: по одному хешу платформа не сможет авторизовать обратный запрос. В ERP можно хранить защищённый ключ/проверочное значение согласно реализации; секрет никогда не пересылается через WebView2.

Предлагаемые административные операции платформы (только локальная admin-сессия; для cookie обязательно CSRF, для legacy Bearer сохраняются проверки Origin):
- GET /api/admin/fastkore/installations — метаданные, enabled, hasKey; без ключа и secret_ref;
- POST /api/admin/fastkore/installations — name и validateTicketUrl; в ответе installationId и однократно connectionKey, Cache-Control: no-store;
- PATCH /api/admin/fastkore/installations/:installationId — включение/выключение и метаданные; изменение адреса требует отключения и повторного подтверждения администратором;
- POST /api/admin/fastkore/installations/:installationId/rotate-key — однократно новый connectionKey и отзыв прежних сессий.
UUID-параметры нельзя проверять существующей схемой identifier для ролей: она требует первую букву, а UUID может начинаться цифрой. За пределами выдачи/ротации API никогда не возвращает connectionKey. Кнопка «показать сохранённый ключ» не нужна.

4. ПОСЛЕДОВАТЕЛЬНОСТЬ ВХОДА

4.1. Подготовка в том же WebView2 — НОВОЕ УТОЧНЕНИЕ К ЧЕРНОВИКУ

GET https://agentic-platform.fastkore.ru/auth/fastkore/start

Платформа создаёт краткоживущую попытку входа (120 секунд) и устанавливает отдельную cookie __Host-bridge_sso_start: случайное значение, Secure, HttpOnly, SameSite=Lax, Path=/, без Domain. Ей сопоставляется независимый случайный login_challenge (32 байта Base64URL). Хранятся проверочные значения, размер и число ожидающих попыток ограничены.

Стартовая страница с same-origin скриптом передаёт через chrome.webview.postMessage:
{
  "type": "fastkore.sso.challenge",
  "version": 1,
  "login_challenge": "<43 символа Base64URL>"
}

WPF принимает сообщение только от точного HTTPS origin из BaseUrl, в ожидаемой фазе входа и от стартового документа верхнего уровня. Это сообщение не является контекстом ERP.

Причина дополнительного шага: один POST с билетом не доказывает, что вход инициирован в этом браузере. Привязка к HttpOnly cookie и challenge защищает от login CSRF — попытки авторизовать чужой браузер под владельцем подставленного билета. Проверка только User-Agent, имени WebView2 или произвольного заголовка Origin этого не заменяет. Постоянный секрет в браузер для такой защиты не передаётся.

4.2. WPF -> Fastkore: выдача билета

Предлагаемый штатный RPC: CreateAgentPlatformLaunchTicket(loginChallenge).
Используется действующая ERP-сессия через существующие IServerService/ServerServiceProxy/gRPC. Примерный POST /api/ai/launch-ticket из ТЗ НЕ нужен как второй внешний HTTP-вход для WPF. Новый RPC требует защищённого транспорта; использовать существующий gRPC TLS, не возвращать билет по открытому соединению.

Клиент не передаёт userId, login, роли, секрет или URL проверки. Сервер сам берёт пользователя из Connection.UserGuid, проверяет сессию, disabled/deleted, право запуска и настройки. GUID сервисной записи фиксирован сервером.

Данные успешного результата (имена полей показаны для согласования):
{
  "version": 1,
  "installation_id": "<UUID установки>",
  "fastkore_user_id": "<Connection.UserGuid>",
  "ticket": "<43 символа Base64URL>",
  "expires_at": "<UTC время>"
}

Билет: 32 криптографически случайных байта, срок 60 секунд от выдачи, одно назначение audience. На сервере хранится SHA-256 билета и привязки: установка, UserGuid, ERP-сессия, audience, SHA-256(login_challenge), срок. Это не JWT и не производная от пароля.

Для пилота с одним процессом Fastkore подходит ограниченный по размеру серверный буфер через штатный ServiceContainer: очистка по TTL, ограничение выдачи на пользователя, атомарное погашение. Перезапуск инвалидирует билеты; пользователю выдаётся новый. При нескольких процессах, обслуживающих одну установку, требуется общее атомарное хранилище в существующей БД либо гарантированный единый сервер проверки — локальный буфер без этого не подходит.

4.3. WebView2 -> Agent Platform: обмен

POST /auth/fastkore/exchange
Content-Type: application/x-www-form-urlencoded
Cookie: __Host-bridge_sso_start=<браузер передаёт автоматически>

version=1&installation_id=<UUID>&ticket=<билет>&login_challenge=<challenge>

WPF отправляет тело через CoreWebView2Environment.CreateWebResourceRequest и NavigateWithWebResourceRequest в ТОМ ЖЕ WebView2. Билет не записывается в URL, HTML, JS, историю приложения и постоянное хранилище; не следует сохранять POST-тела и заголовки авторизации в журналах/трассировке.

В навигационный запрос не добавляется Authorization с ключом подключения или токеном пользователя. Во время входа WPF запрещает переходы/redirect вне точного доверенного origin, включая смену порта, а также новые окна; 307/308 с повторной отправкой тела не являются допустимым результатом обмена. Успех завершает только указанный ниже 303 на фиксированный путь того же origin. На Refresh/Back не повторяем старую POST-навигацию: для нового входа нужны новая попытка и билет. Политику открытия внешних ссылок рабочего интерфейса согласовать отдельно; привилегированные сообщения хосту принимаются только от доверенного документа.

Платформа принимает только эти четыре поля, ограничивает тело 4 KiB, отклоняет неизвестные/повторяющиеся поля и неправильные длины. Cookie попытки входа должна существовать, быть действующей и соответствовать challenge. Попытка атомарно резервируется, чтобы два параллельных обмена из одного браузера не создали разные сессии. Неактивная/неизвестная установка отклоняется до обращения к ERP.

При присутствующем Origin допускается только BRIDGE_PUBLIC_ORIGIN. Отсутствие Origin в нативной POST-навигации допустимо лишь при успешной проверке cookie/challenge; это исключение не распространяется на обычные изменяющие API-запросы.

4.4. Agent Platform -> Fastkore: онлайн-проверка

POST <validate_ticket_url из серверного конфига установки>
Authorization: Bearer fkap1.<installation_id>.<секрет установки>
Content-Type: application/json
Accept: application/json

{
  "version": 1,
  "installation_id": "<UUID установки>",
  "ticket": "<билет>",
  "audience": "fastkore-agent-platform",
  "login_challenge": "<challenge из этой попытки входа>"
}

Проверяются TLS и сертификат. Платформа не следует redirect, не принимает validate URL/секрет от браузера. Для пилота: общий timeout 10 секунд, ответ не более 8 KiB; автоматических повторов запроса проверки нет. Настроенный частный адрес ERP допустим, если его явно зарегистрировал администратор; произвольные адреса клиента — нет.

Fastkore проверяет серверный секрет сравнением с постоянным временем, установку и audience; затем атомарно проверяет срок/состояние билета и challenge и погашает его. Действительность пользователя, исходной ERP-сессии и права запуска повторно проверяется при погашении. Неверный серверный секрет не должен погашать билет. Из двух одновременных корректных предъявлений успешным может быть только одно.

Успех — только HTTP 200 с такой структурой (сохраняем вложенный user из черновика платформы):
{
  "version": 1,
  "valid": true,
  "installation_id": "<UUID установки>",
  "audience": "fastkore-agent-platform",
  "user": {
    "id": "<Connection.UserGuid>",
    "display_name": "Иван Иванов"
  }
}

Здесь user.id соответствует fastkore_user_id / ExternalIdentity.externalUserId. Платформа строго сверяет version, valid, installation_id, audience и формат user.id; display_name ограничен 200 символами и не служит ключом поиска. ERP-роли и пароли в ответ не входят. HTTP 200 с valid:false не используется.

Ошибки Fastkore:
- 400 invalid_request: формат/версия/audience неверны;
- 401 invalid_server_credentials: неверный секрет;
- 403 integration_disabled / access_denied: отключена интеграция, пользователь/сессия/право больше недействительны;
- 400 invalid_ticket: неизвестный, просроченный, погашенный билет или несовпадение его привязок; без раскрытия различий внешнему клиенту;
- 429 rate_limited; 503 temporarily_unavailable.
JSON: { "error": "Безопасное сообщение", "code": "invalid_ticket" }.

После успешной проверки платформа в одной операции связывает/создаёт пользователя и сохраняет credential, затем выдаёт session cookie и HTTP 303 Location: /?embedded=fastkore. Удаляет cookie подготовки, завершает попытку входа. ReturnUrl от клиента не принимается. При уже открытой браузерной сессии её credential отзывается и cookie заменяется после успешного подтверждения новой личности; при неуспехе старый интерфейс не показывается как результат нового входа.

Сбой/timeout после возможного погашения билета означает новый запуск с /auth/fastkore/start и НОВЫЙ билет. Не пробуем повторно старый билет, локальную проверку и другой ИИ-сервис.

5. ПОЛЬЗОВАТЕЛИ И ПРАВА ПЛАТФОРМЫ

Использовать существующую external_identities и пару (installation_id, user.id). Создание связи, нового UserRecord и credential выполняется сериализованно через Access.change/Store с проверкой уникальности. Два первых одновременных входа создают одного пользователя; SQLite PRIMARY KEY служит последней защитой. При ошибке сохранения cookie не выдаётся, а доверенный credential не остаётся действующим только в памяти.

Auto-provision по умолчанию для пилота разрешён, но:
- role = employee (административный флаг, не рабочая роль);
- roleId = sso_pending: новая штатная рабочая роль с enabled=true и пустыми profileIds, operationIds, readDatasetIds;
- пользователь не включается ни в один проект, не получает API-ключ или фиктивный пароль;
- passwordHash пустой; локальный парольный вход для такой записи закрыт;
- username генерируется платформой с уникальностью по паре ID, в пределах её существующей проверки 3–48 символов. Имя ERP — только name/display_name;
- интерфейс показывает подтверждённое имя и сообщение «Доступ к проектам и специалистам назначает администратор».

Нельзя назначать стандартный roleId=employee как эквивалент нулевых прав: он уже разрешает universal/chat. Нельзя объединять по совпавшему username/name или автоматически превращать ERP-администратора в администратора платформы.

Для сохранения истории прежнего сотрудника привязка внешней личности к существующему platform_user_id допускается только отдельным явным действием локального администратора. Это не сохраняет сотруднику обходной локальный вход. Повторный SSO не меняет назначенные администратором права и disabled. Первоначальная настройка локального администратора должна быть завершена до включения SSO; bootstrap через ERP запрещён.

При переходе на согласованный режим «сотрудники только через ERP» платформе нужно явно изменить прежнее поведение:
- Access.login допускает парольный вход только пользователю с административной ролью admin и настроенным локальным паролем; обычные сотрудники отклоняются независимо от наличия старого passwordHash.
- Старые source=local session/API credentials обычных сотрудников отзываются; наличие действующего старого токена не должно обходить новую политику. Проверку источника доступа применить и к очереди. История/пользовательские ID/назначения проектов сохраняются.
- Обычные пользователи создаются только после успешной ERP-проверки. Ручная форма/POST /api/users для локального пользователя остаётся только для создания локального администратора; добавление проектов, блокировка и назначение рабочих ролей ERP-пользователям остаются штатными административными действиями.
- SSO credential даже пользователя с назначенной административной ролью не открывает управление доверенными ERP-подключениями: для этих маршрутов обязательны role=admin и source=local. Назначение административных прав — только отдельное действие администратора платформы, никогда не следствие ERP-роли.
- Программная автоматизация при необходимости согласуется отдельно как явно выданный администратором доступ. Вход сотрудника по SSO сам по себе такой доступ не создаёт.

6. COOKIE, ОБЫЧНЫЙ API И CSRF

Переиспользовать существующий Credential: kind=session, source=fastkore, installationId=<ID>, expiresAt=<срок>. В cookie — новый случайный session token; в базе — только его хеш. Cookie:
__Host-bridge_session=<token>; Secure; HttpOnly; SameSite=Lax; Path=/
Domain не задаётся. Сервер и браузер согласованно ограничивают срок. Токен не возвращается в JSON, JS, localStorage или sessionStorage. Локальный вход администратора сохраняет существующий password/Bearer-контракт. source, отсутствующий у старых credentials, трактуется как local, но старые токены обычных сотрудников не принимаются согласно разделу 5.

Выбор аутентификации:
- только Authorization: существующий Bearer-контракт локального администратора/отдельно разрешённой автоматизации; SSO session credential через Bearer не принимается;
- только session cookie: новый cookie-контракт;
- оба носителя одновременно: 400 ambiguous_credentials, без выбора по приоритету, даже для одного пользователя;
- нет ни одного либо credential недействителен: 401; недействительная cookie удаляется.

В server/app.ts надо изменить не только onRequest, но и повторную проверку principal(request): она должна использовать первоначально выбранный носитель и перепроверять credential после await. Проверяется пользователь, допустимый способ входа, срок и включённая доверенная установка для source=fastkore. В рабочей очереди требуется та же проверка источника/установки, а не только наличие credentialId.

GET /api/auth/me сохраняет user и setupRequired, дополнительно возвращает:
{
  "user": {
    "id": "<UUID пользователя платформы>",
    "username": "<внутренний логин платформы>",
    "name": "Иван Иванов",
    "role": "employee",
    "roleId": "sso_pending",
    "disabled": false
  },
  "setupRequired": false,
  "authentication": {
    "source": "fastkore",
    "installationId": "<UUID>",
    "externalUserId": "<GUID ERP>",
    "expiresAt": "<UTC>",
    "csrfToken": "<CSRF-токен этой сессии, не session token>",
    "canChangePassword": false,
    "canCreateApiKey": false
  }
}
user сохраняет форму существующего publicUser; его id — ID ПЛАТФОРМЫ, а authentication.externalUserId — GUID ERP. Имена camelCase сохраняют стиль существующего внутреннего API платформы.

Для cookie-аутентифицированных POST/PUT/PATCH/DELETE обязательны точный Origin и X-CSRF-Token, связанный с credential, включая logout, загрузку файлов и операции администратора. Не полагаться только на SameSite. CSRF-механизм должен поддерживать несколько вкладок одной сессии. /auth/fastkore/exchange использует отдельную cookie/challenge-схему из раздела 4. Существующий Bearer-API не должен внезапно требовать браузерный CSRF-токен.

Запросы /auth/* и ответы auth/me получают Cache-Control: no-store. Не ослаблять CSP, X-Frame-Options и frame-ancestors: WebView2 загружает верхнеуровневую страницу, а не iframe. За reverse proxy использовать заданный BRIDGE_PUBLIC_ORIGIN и доверенные proxy; не верить произвольному X-Forwarded-Proto/Host.

7. ИНТЕРФЕЙС, API-КЛЮЧИ И ВЫХОД

client/main.tsx должен начинать с состояния «проверка входа», а не !!bridge-key. Сначала выполнить cookie-only GET /api/auth/me без Authorization. При подтверждённом SSO удалить старый bridge-key и очистить состояние прежней личности. В режиме embedded=fastkore не переходить автоматически к сохранённому Bearer-токену или парольной форме при неудаче SSO. При обычном посещении сайта оставить вход администратора; сотруднику объяснить, что нужно открыть платформу из Fastkore. Параметр embedded является подсказкой интерфейсу, не доказательством полномочий.

api() при cookie-режиме не выставляет Authorization, передаёт cookie same-origin и CSRF-заголовок для изменений. При смене личности очищаются проекты, чаты, вложения, черновики и bridge-project/bridge-chat. Поздние ответы запросов прежней сессии не должны восстанавливать их в React: использовать поколение auth-состояния/отмену запросов.

В AccountPanel скрыть неподдерживаемые операции согласно authentication capabilities. На сервере запретить source=fastkore для POST /api/auth/keys и /api/auth/password, независимо от kind=session и видимости кнопки. Иначе краткая SSO-сессия сможет выдать бессрочный доступ. Отдельная выдача ключей SSO-пользователю — не часть v1; её можно согласовать позже.

Использовать существующий POST /api/auth/logout с cookie/CSRF. Он отзывает credential и удаляет cookie с теми же Path/атрибутами. WPF при выходе или смене ERP-пользователя завершает ВСЕ связанные экземпляры WebView2 независимо от наличия карточки/списка; это надо связать с жизненным циклом соединения ERP, а не только Unloaded одного контрола. Отдельные приватные профили не должны передавать cookie/хранилища следующему ERP-пользователю. Сворачивание окна не является выходом.

При возможности WPF инициирует logout через страницу; при сетевом сбое локальная изоляция и закрытие обязательны всё равно. Отсутствие успешного logout означает, что серверная сессия может жить до TTL; не обещаем серверный мгновенный отзыв без подтверждения.

После cookie-only /api/auth/me страница сообщает WPF:
{ "type": "fastkore.ready", "version": 1, "installation_id": "<UUID>", "fastkore_user_id": "<GUID ERP>" }
WPF сверяет обе личности с результатом выдачи билета. При несовпадении закрывает браузер и показывает ошибку. На 401 в embedded-режиме:
{ "type": "fastkore.sso.required", "version": 1, "reason": "session_expired" }
Повтор начинается с новой подготовки и билета; после неудачи — понятная кнопка повтора, без бесконечного цикла. Сообщения logout/повторного входа не принимают URL или исполняемый код от страницы.

8. СРОК СЕССИИ И ЗАДАНИЯ — РЕШЕНИЕ ДЛЯ СОГЛАСОВАНИЯ

Предложение пилота: абсолютный срок SSO-сессии 30 минут, как в черновике платформы. Это отдельный срок для source=fastkore; нынешние 12 часов локального администратора не менять. Без скользящего бессрочного продления по активности. По истечении нужен новый билет.

У текущей очереди это имеет прямое следствие: задание с истёкшим/отозванным credential не начинается или прекращается, даже если принято раньше. v1 сохраняет такое поведение; новый вход не перепривязывает старые Job.credentialId и не перезапускает внешние действия. Открытие ещё одного окна само по себе не отзывает сессии остальных окон, кроме обычного ограничения числа сессий. Более долгие задания потребуют отдельного согласованного срока/делегирования, не скрытого снятия проверки.

Блокировка пользователя в платформе или отключение доверенной установки прекращает новые запросы и очередь на следующей проверке. Блокировка только в ERP обнаруживается при следующей выдаче/погашении билета: действующая cookie-сессия может жить до 30 минут. Если требуется немедленный общий отзыв по событию ERP, нужен дополнительный контракт уведомления/проверки; в v1 его нет. SSO не подменяет проверку прав при будущих вызовах ERP API.

9. HTTPS, ОШИБКИ И ЖУРНАЛЫ

Agent Platform должна иметь сетевой HTTPS-доступ к точному validate_ticket_url ERP. Нынешний ServerInfoHttpHost с http://.../info/ не является готовой точкой SSO. Реализовать ограниченный endpoint на существующей серверной HTTP-инфраструктуре, с TLS/доверенным reverse proxy, без новой службы идентификации. Не объявлять внешний endpoint работающим после одного добавления RPC.

Если перед сайтом установлена дополнительная HTTP BasicAuth на reverse proxy, cookie приложения её не заменяет: это надо отдельно согласовать при настройке пилота, иначе повторный запрос пароля сохранится.

Ошибка обмена не делает 303 в рабочий интерфейс. Платформа возвращает безопасную HTML-страницу для нативной POST-навигации с понятным повтором; для API — привычный объект error с добавленным машинным code. Собственные коды: invalid_request (400), invalid_login_attempt (400), installation_unavailable (403), identity_denied (403), invalid_ticket (401), ambiguous_credentials (400), csrf_failed (403), rate_limited (429), fastkore_unavailable (503). Ответы не содержат URL внутреннего сервера, секрет или текст его исключения. WPF допускает только штатный повтор SSO.

Билеты, session cookies, серверные секреты, Authorization, challenge и POST-тела auth-маршрутов не записываются в логи. Нынешняя redact() не покрывает все новые поля автоматически: дополнить её и проверить журналы reverse proxy. Разрешены идентификатор операции, установки, результат и безопасный код ошибки. Ограничить частоту start/exchange/validate и размер ожидающих попыток/билетов; для лимитов за proxy корректно определить адрес клиента, не доверяя произвольным forwarded-заголовкам.

10. ФАЙЛЫ И РАСПРЕДЕЛЕНИЕ РАБОТ

Agent Platform:
- server/access.ts: выдача/аутентификация SSO credential, provision/link через existing externalIdentities, source-based capabilities, отзыв и повторная проверка установки; парольный вход только администратора, закрытие старых локальных токенов сотрудников.
- server/app.ts: start/exchange, ограниченный form parser, cookie + CSRF, выбор носителя и повторный principal(), расширение me/logout; auth-route headers и rate limits.
- server/store.ts: переиспользовать existing external_identities; при добавлении новых служебных метаданных обеспечить сохранение/восстановление. Не хранить секреты в публичных Settings.
- shared/types.ts: существующие source/installationId/ExternalIdentity плюс описанные поля authentication DTO; без активации erpContext.
- server/corporate.ts: минимальная sso_pending, совместимая с текущими WorkRole.
- server/workspace.ts: включённость установки в проверке credential задания; сохранить авторство, роли, проекты и правила очереди.
- client/main.tsx и client/AccessPanel.tsx: cookie bootstrap, capabilities, очистка при смене личности, сообщения хосту; внешний вид чатов не переписывать.
- административный интерфейс/API и server config/deployment: публичный origin, доверенные установки, генерация/однократная выдача/ротация fkap1 ключей, защищённое хранение и HTTPS-связность. Не возвращать эти секреты в общих settings.
- tests: тесты ниже с fake ERP validation server и отдельный реальный WebView2-пилот.

Fastkore:
- Contract/IServerService, существующий gRPC-контракт/прокси и Server/ServerService: штатный метод выдачи билета по ERP-сессии и требование TLS для него.
- Server.Services: ограниченный сервис билетов в ServiceContainer, актуальная проверка пользователей/ReadEntity, атомарное погашение и инвалидация при закрытии ERP-сессии.
- Server/configuration и существующий HTTP host: один защищённый ключ подключения к существующему сервису, извлечение installation_id, enabled, HTTPS validate-ticket endpoint. Никаких новых справочников ERP.
- Presentation/Services/AIAssistant и Controls/EntityView: получение билета через существующее соединение, WebView2 start -> challenge -> POST exchange -> ready; доверенный origin/фаза, управление всеми окнами при смене пользователя.
- Кнопка: неподготовленная/явно отключённая интеграция сохраняет старый режим. Отказ в праве, ошибка конфигурации активной интеграции, недоступность и сбой SSO не разрешают автоматически отправлять вопрос PolzaAI. Текущей проверки одного BaseUrl для полного SSO-режима недостаточно; состояние сообщает сервер.

11. ПРИЁМОЧНЫЕ ПРОВЕРКИ

1) Локальный логин администратора и его существующий допустимый Bearer-доступ продолжают работать. Пароль, старые local session/API-токены обычного сотрудника больше не дают вход; его история сохраняется и после явной связи доступна по SSO. Выключенный сервис в ERP сохраняет старый ИИ-режим.
2) Реальный WebView2 получает pre-auth cookie, challenge, билет и session cookie после 303; /api/auth/me подтверждает текущего ERP-пользователя. Проверить фактическую передачу cookie в NavigateWithWebResourceRequest, а не только mock Fastify.
3) Два параллельных предъявления билета: ровно один успех. Просроченный билет, неверный secret/audience/installation/challenge, чужая pre-auth cookie и повтор start/exchange без новой попытки не создают сессию. Неверный секрет не расходует корректный билет.
4) Попытка подставить билет другого пользователя в чужой WebView2 без соответствующей browser-bound подготовки отклоняется; смена userId/validation URL/роли в теле не влияет на личность.
5) Timeout после погашения, restart ERP, неправильный JSON, 3xx ответа ERP, превышение лимита ответа и ошибка SQLite не создают неподтверждённую сессию; повтор получает новый билет.
6) Первый вход создаёт одну внешнюю связь и sso_pending без проектов/профилей. Совпавшее имя/логин локального администратора не даёт его аккаунт. Два первых входа одновременно и перезапуск не создают дубликатов.
7) Старый bridge-key, cookie плюс Authorization, поздний HTTP-ответ прежней личности и сохранённые chat/project/drafts не подменяют пользователя SSO.
8) Cookie без CSRF/Origin, cross-site POST, чужой CSRF и попытка выпуска API-ключа/смены пароля через SSO отклоняются на сервере. Проверить и JSON, и multipart.
9) Logout, переключение пользователя ERP и отключение установки закрывают доступ; при недоступной сети следующий пользователь не видит прежнюю страницу/cookie/черновики. Сворачивание и повторное раскрытие окна сохраняют текущую сессию.
10) При expiry/logout/блокировке проверить queued и running с текущей привязкой credentialId, включая отказ перед внешним действием; никаких автоматических повторов задания.
11) В логах приложения и proxy, URL, localStorage/sessionStorage и доступных странице данных отсутствуют ticket/secret/SSO session token. Сам SSO session token хранится браузером только в описанной HttpOnly cookie; это ожидаемое исключение, а не web storage. Локальная admin-сессия сохраняет свой 12-часовой срок. Выпуск/ротация connectionKey доступен только локальному администратору и показывает ключ один раз; обычный GET не возвращает его. Старый ключ и его SSO credentials перестают работать после ротации. Обычный ERP-пользователь не может изменить BaseUrl или прочитать ключ через универсальные API. Проверить запрет redirect с телом билета на другой origin.
12) Отдельно подтвердить окно задержки блокировки только в ERP и согласованный TTL: обещаний мгновенного межсистемного logout в v1 нет.

12. ЧТО ПОДТВЕРДИТЬ ОБЕИМ СТОРОНАМ

A. Fastkore остаётся источником личности. Native RPC вместо отдельного HTTP launch-ticket; публичный HTTPS validate-ticket и вложенный user в ответе, как в черновике платформы. Новые справочники ERP не нужны.
B. Дополнительный GET start и browser-bound login_challenge. Это главное расширение исходной трёхоперационной схемы; его нельзя незаметно опустить, оставив только POST билета.
C. Сессия source=fastkore: 30 минут, без выпуска API-ключей и смены локального пароля; текущая очередь прекращает действия при expiry/отзыве.
D. Локальный вход платформы только для администраторов; обычные пользователи только из ERP, auto-provision в sso_pending без проектов/профилей и явная административная связь с прежним аккаунтом для сохранения истории. Закрытие старых локальных токенов сотрудников — обязательная часть перехода.
E. ReadEntity на фиксированную запись сервиса как право запуска со стороны ERP; собственные роли платформы остаются отдельными.
F. Ключ fkap1 с installation_id создаёт администратор Agent Platform, а администратор Fastkore сохраняет его в защищённой конфигурации существующего сервиса. Адрес HTTPS-проверки регистрируется заранее. Конкретные ключи пилота передаются по защищённому каналу, не в этом документе/репозитории. Пароль администратора сайта не используется как серверный секрет.
G. Контекст текущего представления передаётся отдельно после входа. Постоянная привязка чатов к объектам ERP в этот этап не входит.

ДОПОЛНЕНИЕ: ТЕМА ИНТЕРФЕЙСА

Fastkore передаёт результат TelerikThemes.IsDark: true = dark (TelerikTheme.FluentDark), остальные темы = light. Начальный адрес /auth/fastkore/start?theme=dark|light; платформа сохраняет тему в pre-auth попытке и переносит её в фиксированный 303 /?embedded=fastkore&theme=dark|light. В POST exchange по-прежнему ровно четыре поля, тема туда не добавляется.

При загрузке документа/повторном раскрытии WPF передаёт через CoreWebView2.PostWebMessageAsJson:
{ "type": "fastkore.ui", "version": 1, "theme": "dark" }
Платформа слушает window.chrome.webview message, принимает только light/dark и подтверждает:
{ "type": "fastkore.ui.applied", "version": 1, "theme": "dark" }

Тема ERP имеет приоритет в embedded-режиме, применяется ко всему интерфейсу до первого показа и меняется без перезагрузки/повторного SSO. Собственный переключатель сайта в этом режиме отключён. Тема не меняет глобальные настройки аккаунта и обычного браузера. Если ERP применяет смену темы после перезапуска, новое значение передаётся при следующем запуске окна; live-переключение всей ERP не требуется.

ДОПОЛНЕНИЕ: ТЕКУЩИЙ КОНТЕКСТ ERP

После подтверждения пользователя и темы Fastkore отправляет странице сообщение
WebView2 с type: "fastkore.context" и version: 1. При повторном раскрытии окна
передаётся новый снимок. Платформа слушает тот же window.chrome.webview message,
что и для темы. Обработчик темы и подтверждение SSO не зависят от этого сообщения.

- view: "card", "list" или "link_list". entity_set_id — GUID компонента,
  entity_set_name — его подпись. entity_id — GUID сохранённой открытой карточки
  или одной выбранной строки, иначе null. Выбор строки сам по себе не сужает список.
- tile_id — GUID плитки, если она есть. filter_xml — штатный сериализованный
  EntitySetFilter для того же компонента, который включает условия плитки,
  расширения, периода и поиска, применяемые при серверной загрузке списка.
  filter_status: "included", "none" или "unavailable". В последнем случае
  нельзя считать выборку неограниченной. Фильтры полей со скрытым значением,
  справочника сервисов и XML свыше 32 КиБ не передаются.
- catalog_id и folder_id — GUID реального каталога и папки. Если открыт каталог
  целиком, folder_id равен null. Для чтения применяйте штатную выборку каталога
  или папки с родительскими условиями и принадлежностью записей к папкам,
  совместно с filter_xml. tree_parent_id ограничивает список дочерними записями.
- Для табличной части owner_entity_set_id и owner_entity_id указывают документ,
  link_id — исходящую связь от документа к строкам, control_uid — UID элемента
  интерфейса. deleted повторяет режим загрузки удалённых строк: true, false или
  null (без ограничения). Для виртуальных папок и других неповторимых ограничений
  scope_reproducible: false. Данные, скрытые только локальной логикой UI, и
  несохранённые изменения не входят в серверную выборку.

Agent Platform заменяет текущий контекст целиком, включая поля со значением null,
а для сообщения { "type": "fastkore.context", "version": 1, "view": "none" }
сбрасывает его. Так главное окно ERP сообщает, что активная страница не содержит
карточки или списка.

Для карточки, списка и табличной части платформа передаёт снимок агенту
с запросом сотрудника. Само получение сообщения не
запускает работу. Карточку можно читать адресно по entity_set_id и entity_id.
Для списка CLI или MCP должны поддерживать штатный фильтр и переданные
ограничения. Если они не умеют повторить выборку, агент сообщает об этом.
Контекст не выдаёт прав или учётных данных. Инструменты читают ERP с правами
сотрудника, под которым запущен запрос.
