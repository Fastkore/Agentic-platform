Fastkore Agent Platform — вход Linux CLI от имени сотрудника, v1

Дополнение к Fastkore-Agent-Platform-User-Access-v1.txt.

1. Получение билета

Обновить ERP-сервер и Linux CLI из новой поставки. В существующей привязке
должно быть включено «Разрешить доступ к ERP». После обновления сотрудник
заново открывает ассистента из ERP, чтобы получить действующий SSO-сеанс.
Использовать delegation.grant именно этой серверной сессии, связанной с
installation_id и user.id. Смена чата не меняет личность сотрудника.

Перед каждым запуском CLI доверенный backend Agent Platform запрашивает билет
по тому же доверенному HTTPS-адресу ERP, который используется для validate-ticket.

POST /api/ai/cli-ticket
Authorization: Bearer <существующий ключ привязки fkap1.…>
Content-Type: application/json

{ "version": 1, "delegation": "<grant из validate-ticket>" }

HTTP 200, Cache-Control: no-store

{ "version": 1, "ticket": "<непрозрачный билет fkct1.…>",
  "expires_in": 30, "audience": "fastkore-cli" }

Строго сверять поля version и audience. Ответ использовать сразу.
Билет одноразовый, живёт до 30 секунд и погашается при входе в ERP.
Введённый билет никогда не переиспользуется, в том числе при обрыве.
Сессия CLI после входа действует максимум 5 минут с момента выдачи билета
и только пока действует исходное разрешение. Выход из ERP, отзыв grant,
запрет доступа, перепривязка и перезапуск ERP прекращают доступ.
ERP проверяет штатные права сотрудника, изменения идут в его журнал.
Текущие MCP/WebAPI-аудитории и обмен /api/ai/user-token сохраняются.

2. Вызов через существующий закрытый исполнитель

Доверенный исполнитель выбирает gRPC TLS-адрес из административной привязки
той же ERP и передаёт аргументы массивом. Пример argv без секрета:

["docker","compose","-p","fastkore-cli","exec","-T","cli","fastkore-cli",
 "auth","info","--user-ticket-stdin","--json"]

Передать билет одной ASCII-строкой с LF через перенаправленный stdin
процесса и закрыть stdin. Для прямого запуска используется тот же флаг.
FASTKORE_SERVER задаётся как grpc://host:port в настройках контейнера
или через --server в доверенной конфигурации исполнителя. Для частного CA
использовать FASTKORE_CA_FILE или --ca с проверенным PEM. TLS и проверка имени
обязательны. Подключение по билету не допускает логин или источник пароля.
При билете файлы для команд передаются по пути, а не через stdin.

Для чтения использовать отдельный инструмент с типизированными параметрами
и разрешить только data get и data query. Исполнитель добавляет флаг входа,
запрашивает билет и подставляет доверенный адрес ERP. Модель получает только
данные, статус и безопасное сообщение об ошибке. Не давать модели запуск
произвольных команд, менять адрес ERP или читать stdin чужого процесса.
Не передавать билет, grant или ключ через argv, environment, URL, проект,
prompt, браузер или логи. Существующий fastkore_cli_describe остаётся офлайн.

3. Обработка результата и приёмка

- 401 invalid_server_credentials — проверить привязку и ключ на backend.
- 403 invalid_delegation — пользователю нужен новый вход из ERP либо доступ
  выключен. Старый билет и пароль сотрудника не использовать.
- 404 — серверу требуется обновление с поддержкой этого маршрута.
- 400 invalid_request — проверить версию, Content-Type и поля запроса.
- 429 rate_limited и 503 temporarily_unavailable — ограничить частоту и
  обработать временную недоступность штатно.
- После запуска учитывать exit code и JSON CLI. Ошибки CLI приходят в stderr.
  При ошибке авторизации можно получить новый билет для безопасного чтения,
  если grant действует. Изменяющие команды автоматически не повторять.

Для приёмки получить новый билет и выполнить auth info --json. Сверить
data.user.guid с user.id из SSO. Для каждого data get и data query получить
отдельный билет, прочитать известный объект и проверить ограничения прав
под двумя сотрудниками. Повторное предъявление использованного билета должно
отклоняться. После выхода из ERP выдача новых билетов должна прекратиться.
Проверить, что логи содержат только результат и время запроса, без секретов.
