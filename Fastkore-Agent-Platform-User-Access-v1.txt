FASTKORE → AGENT PLATFORM: ДОСТУП К MCP И WEBAPI ОТ ИМЕНИ СОТРУДНИКА
Дополнение к действующему SSO-контракту. 11 ноября 2026 г.
Статус: реализация подготовлена в исходниках Fastkore Dev и Fastkore.Business Dev.
Сборка, запуск проверок поведения C# и сквозная проверка не выполнялись.
Синтаксис исходников проверен парсером C# без компиляции.

1. Границы

Этот контракт описывает MCP Fastkore.Business: POST /webapi/mcp и прямой WebAPI.
MCP описывает инструменты и вызывает существующие методы WebAPI. У них одна
проверка пользователя; отдельной реализации бизнес-операций не добавляется.
Прямой WebAPI также поддерживает новый вход, но требует отдельной аудитории токена.
Делегированный вход CLI описан в Fastkore-Agent-Platform-CLI-Ticket-v1.txt.
CLI и MCP входят в основную архитектуру Agent Platform. CLI имеет приоритет
как канал работы на уровне клиентского приложения Fastkore. Агент выбирает
подходящий инструмент для каждого шага с сохранением полномочий сотрудника.
Основная концепция закреплена в манифесте AGENT-PLATFORM-MARKETING.md,
сценарии и принципы работы раскрыты в AGENT-PLATFORM-OVERVIEW.md.

Сотрудник входит в ERP и открывает ассистента как сейчас. Пароль сотрудника,
постоянные персональные API-токены и повторный пользовательский вход не нужны.
Привязка установки и проверка TLS остаются существующими. Клиентские сертификаты,
доверенные корни и проверку имени сервера не отключать.

2. Однократная настройка

Администратор Fastkore в записи сервиса Fastkore Agent Platform открывает штатную
команду «Подключение» и выбирает «Разрешить доступ к ERP». Команда доступна только
после привязки и проверяет полномочия администратора на сервере.
По умолчанию доступ запрещён, в том числе для существующих привязок после обновления.
После включения требуется новый SSO. Сворачивания уже открытой панели недостаточно;
для первой проверки можно перезапустить клиент ERP и снова открыть ассистента.
Разрешение сохраняется сервером рядом с существующей привязкой автоматически.
Новых справочников, миграций БД и ручной правки XML нет.
Разрешение включает чтение И ИЗМЕНЕНИЕ в пределах штатных прав сотрудника.
Отдельного серверного режима «только чтение для агента» этот контракт не вводит.

В Agent Platform администратор один раз задаёт доверенный URL MCP конкретной ERP
(например, https://mcp.fastkore.ru/webapi/mcp). Адрес платформенного TLS API берётся
из существующего подключения, которым уже проверяется SSO-билет. Это разные
слушатели: /api/ai/* размещены на TLS-порту платформы (в текущей установке 17050),
/webapi/* — в Fastkore.Business за настроенным HTTPS-входом. Адрес PostgreSQL не нужен.
Разрешённые адреса задаёт администратор; модель и содержимое чата их не меняют.

3. Разрешение пользователя при SSO

Существующий POST /api/ai/validate-ticket, его запрос, Bearer-ключ привязки,
login_challenge и одноразовость SSO-билета сохраняются.
В успешный ответ добавляется необязательное поле delegation:

{
  "version": 1,
  "valid": true,
  "installation_id": "<UUID установки>",
  "audience": "fastkore-agent-platform",
  "user": { "id": "<GUID пользователя ERP>", "display_name": "<имя>" },
  "delegation": {
    "grant": "<непрозрачная строка fkug1.…>",
    "expires_in": 28800,
    "audiences": ["fastkore-mcp", "fastkore-webapi"]
  }
}

Если администратор не разрешил доступ, delegation = null. Сам SSO при этом работает.
Отсутствующее поле (старый ERP-сервер) также означает отсутствие доступа к инструментам.

Agent Platform сохраняет grant только в серверной пользовательской сессии,
с привязкой к installation_id И user.id. Не связывать его только с проектом/чатом.
При смене сотрудника/ERP использовать разрешение соответствующей сессии.
Grant не возвращать в браузер, WebView2, /api/status, настройки, prompt, историю
сообщений, каталоги проектов, окружение песочницы агента или журналы.
Ключ привязки установки также остаётся только у доверенного backend.
Самого ключа привязки недостаточно, чтобы выбрать произвольного пользователя.

Grant живёт максимум 8 часов и только пока действует исходная ERP-сессия.
SSO-билет повторно использовать нельзя. По окончании grant нужен новый SSO из ERP.
Сворачивание панели не завершает ERP-сессию. Фоновые задания после выхода из ERP
в этой редакции не поддерживаются.

4. Выдача временного токена инструментов

Запрос отправляет backend Agent Platform к известному TLS-серверу ERP:

POST /api/ai/user-token
Authorization: Bearer <существующий connectionKey привязки fkap1.…>
Content-Type: application/json

{
  "version": 1,
  "delegation": "<grant из успешного SSO>",
  "audience": "fastkore-mcp"
}

Ответ 200:

{
  "version": 1,
  "access_token": "<непрозрачная строка fkua1.…>",
  "token_type": "Bearer",
  "expires_in": 300,
  "audience": "fastkore-mcp"
}

Для прямого WebAPI запросить отдельно audience = "fastkore-webapi".
Обе аудитории фиксированы. Произвольные URL, user_id, логины и дополнительные
поля в этом запросе не принимаются. Обе версии сообщений остаются 1.

Токен действует максимум 5 минут; окончание/отзыв grant может сократить этот срок.
Обновление — повторить тот же запрос с действующим grant. Refresh token не выдаётся.
Backend может кэшировать токен по (пользовательская сессия, ERP, аудитория) и обновлять
незадолго до истечения. Не выпускать токен для каждого отдельного tools/call.
Токен добавляет доверенный исполнитель HTTP-инструментов; модель получает только
описания инструментов, аргументы и результаты. Не помещать секрет в строку команды,
аргументы инструмента, URL, текст ошибки или тело чата. HTTP-клиенту запретить
перенаправления на другие адреса с передачей Authorization.

5. Вызовы инструментов

POST https://<доверенный MCP-хост>/webapi/mcp
Authorization: Bearer <access_token для fastkore-mcp>
Content-Type: application/json

Далее обычные MCP initialize, tools/list и tools/call, с существующими схемами.
В MCP-клиенте Agent Platform настроить свой серверный поставщик Bearer-токена
по этому контракту. При ошибке не переключаться на отдельный OAuth-вход с паролем
или общую учётную запись: пользователь уже определён проверенным SSO из ERP.
Для методов /webapi/* вне /webapi/mcp использовать токен fastkore-webapi.
MCP-токен отвергается при прямом вызове WebAPI; WebAPI-токен — на /webapi/mcp.
Fastkore-Login и Fastkore-Password в новом режиме не передаются.

Внутри ERP только доверенный системный адаптер Business обменивает внешний токен
на одноразовый билет клиентского подключения. Билет действует 30 секунд и создаёт
обычный UserRequestContext сотрудника. Наружу этот билет не выдаётся.
MCP может несколько раз войти в общую проверку пользователя в одном tools/call.
Внешний access_token поэтому многоразовый в пределах срока, а билет внутреннего
подключения каждый раз новый. Повторное использование билета отклоняется атомарно.
Внутренний обмен и вход по билету допускаются по TLS либо через loopback самого
ERP-сервера; передача этих билетов по открытому сетевому соединению запрещена.

Каждый запрос делегированной сессии проверяет срок, исходную сессию, состояние
пользователя, актуальные группы/роли, доступ к сервису и действительность привязки.
Права на объекты и изменения проверяются штатными серверными механизмами.
EntitySet/Entity/фильтр из fastkore.context помогают выбрать объект, но не дают прав.
Изменения записываются штатным журналом под GUID сотрудника; схему журнала и
комментарии изменений не меняем. Полный аудит всех чтений в этот этап не входит.

6. Выход и отзыв

При выходе пользователя из Agent Platform backend вызывает:

POST /api/ai/revoke-delegation
Authorization: Bearer <connectionKey>
Content-Type: application/json

{ "version": 1, "delegation": "<grant>" }

Ответ 200: { "version": 1, "revoked": true }.
Операция идемпотентна. Удалить grant и связанные токены из серверной сессии.
Новый SSO в той же сессии должен заменить старое разрешение с отзывом старого.

Выход из исходной ERP-сессии, отключение пользователя, изменение/перепривязка
сервиса, запрет доступа администратором и перезапуск ERP прекращают доступ.
Повторное включение не восстанавливает старые grants/токены.
Уже открытая делегированная сессия проверяется на каждом следующем запросе;
неактивные соединения также убирает штатная фоновая проверка соединений.
Операция, допущенная до отзыва, может завершиться: отзыв не откатывает транзакцию
задним числом и не является отменой уже начатой бизнес-операции.

7. Ошибки и повторения

TLS API /api/ai/* возвращает JSON с code без секретов; ответы имеют no-store.
401 invalid_server_credentials — неверный/отозванный ключ привязки.
403 invalid_delegation — нужен новый SSO, grant истёк или доступ запрещён.
400 invalid_request — ошибка полей, версии или аудитории.
429 rate_limited — ограничить частоту, повторять с задержкой.
503 temporarily_unavailable — временная ошибка сервера.
Лимиты: до 4096 живых записей каждого вида, общий вход /api/ai/* ограничен
100 запросами за 10 секунд и 8 одновременно обрабатываемыми запросами.

MCP сохраняет прежний формат ошибок: отказ при входе — HTTP 401; ошибки методов
API внутри tools/call — существующий ответ инструмента. Прямой WebAPI сохраняет
свои WebResponse Success/Error. Не считать HTTP 200 доказательством успеха операции.
При 401 можно запросить свежий токен с тем же grant. Если выдача отвечает 403,
требуется новый SSO; не запускать бесконечное обновление или вход под общей учёткой.
Потеря ответа на изменяющую операцию не разрешает повторить её автоматически.
Нужно проверить фактический результат штатным чтением или средствами конкретного API.

8. Приёмка после сборки обеих сторон

- Со старой привязкой SSO работает, delegation=null до разрешения администратора.
- Обычный сотрудник не может включить доступ или обменять токен через системный RPC.
- После разрешения и нового SSO grant выдан правильному user.id.
- Два сотрудника с разными правами видят и меняют только разрешённые им данные.
- MCP initialize/tools/list/tools/call и прямой WebAPI работают со своими токенами.
- Перекрёстное использование аудиторий, чужой ключ установки, испорченный токен
  и повторный внутренний билет отклоняются, без перехода к другому способу входа.
- Нормализованные маршруты /webapi//mcp/ также требуют именно MCP-токен.
- tools/call с внутренним повторным ValidateUser работает, билет не используется повторно.
- На границах 30 секунд / 5 минут / 8 часов доступ прекращается.
- Выход, блокировка сотрудника, смена прав, запрет доступа и перепривязка прекращают
  последующие операции уже открытого подключения; повторный вход работает корректно.
- Изменение тестового объекта видно в стандартном журнале под сотрудником.
- Старые способы входа WebAPI/MCP по паролю, API-токену и OAuth продолжают работать.
- Секретов нет в браузере, prompts, окружении агента, /api/status и логах.

Обновлять совместно Fastkore Platform и Fastkore.Business Dev. Номера RPC,
продукта и БД в этих правках не повышены. Порядок отдельного коммита версии сохраняется.
