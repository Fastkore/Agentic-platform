ТЗ ДЛЯ РАЗРАБОТЧИКА AGENT PLATFORM
Вход из Fastkore ERP через WebView2 и управление темой
Редакция 1.1 — 11 ноября 2026 года

Статус: схема принята владельцем Fastkore. Это задание на реализацию ответной стороны Agent Platform, а не описание уже работающего API. Сквозной запуск требует готовности и проверки обеих сторон. Ведущая сторона контракта — Fastkore ERP.
Проверенная основа Agentic-platform: commit 77c035b7ed3c453a6492c6a2310579dff760b883, версия 0.5.0.
Адрес пилота: https://agentic-platform.fastkore.ru/

1. ЧТО ПОЛУЧАЕТ ПОЛЬЗОВАТЕЛЬ

В Fastkore пользователь открывает существующее окно ассистента синей кнопкой. Внутри WebView2 открывается Agent Platform с его доступными проектами и чатами, без отдельного пароля. Кнопка работает в карточках и списках. Сворачивание/разворачивание сохраняет открытую сессию. Объект ERP и привязку чата к заказу на этом этапе не передаём.

Agent Platform принимает тему интерфейса из Fastkore. Встроенное окно должно выглядеть светлым или тёмным в соответствии с фактической темой ERP; собственная настройка темы сайта и тема Windows её не переопределяют.

Локальный парольный вход Agent Platform предназначен только администраторам платформы. Обычные пользователи входят из Fastkore и создаются после успешной серверной проверки билета. SSO подтверждает личность, но не выдаёт автоматически права на проекты, выполнение команд или доступ к ERP API.

2. ЧТО ИСПОЛЬЗОВАТЬ ИЗ ТЕКУЩЕЙ РЕАЛИЗАЦИИ

Не создавать вторую систему пользователей, сессий и прав. Использовать:
- server/access.ts: Access, существующие credentials, хеширование токенов, блокировку пользователей;
- server/store.ts: существующий Store и SQLite external_identities;
- shared/types.ts: ExternalIdentity и Credential.source/installationId;
- server/corporate.ts: действующие рабочие роли и права проектов;
- server/workspace.ts: существующую очередь и привязку задания к credentialId;
- client/main.tsx и client/AccessPanel.tsx: существующий интерфейс чатов и аккаунта.

В изученном commit SSO пока не реализован. Текущий Bearer из sessionStorage не является готовым входом из ERP.

3. ПОДКЛЮЧЕНИЕ ERP: ЧТО СОЗДАЁТ АДМИНИСТРАТОР ПЛАТФОРМЫ

Добавить в административный интерфейс регистрации подключений Fastkore. Для каждой логической установки ERP:
- installation_id: UUID, создаётся платформой один раз;
- name: название для администратора;
- validate_ticket_url: точный HTTPS endpoint этой ERP, заранее введённый администратором;
- enabled: по умолчанию false;
- auto_provision: true;
- default_role_id: sso_pending;
- session_ttl_seconds: 1800;
- защищённая ссылка на ключ либо защищённое серверное значение ключа, недоступное обычному API.

GUID записи сервиса Fastkore: 33040cfb-9073-43a5-a184-5039db13924b. Он одинаков во всех ERP и НЕ является ключом доступа. installation_id отличает конкретную ERP. Тестовая копия ERP должна иметь отдельную регистрацию и ключ.

При создании подключения платформа генерирует 32 криптографически случайных байта. Ключ:
fkap1.<installation_id UUID в нижнем регистре>.<секрет Base64URL без padding, 43 символа>

Полный ключ содержит 86 ASCII-символов. Это отдельный серверный ключ, не пользовательский ccb_k_ и не пароль администратора. Предъявляется только платформой серверу ERP при проверке билета.

Показать ключ администратору один раз при создании/ротации. GET настроек, /api/status и обычные административные ответы его не возвращают. Платформе нужна восстанавливаемая защищённая копия ключа: она отправляет его ERP. Одного хеша на стороне платформы недостаточно.

Хранить метаданные через существующий Store в непубличном разделе. Не помещать ключ в общие Settings: текущий /api/status их возвращает. Секреты не должны попадать в репозиторий, web-root, проекты, промпты, stdout, дампы запросов и окружение запускаемых агентом процессов. У исполнителя команд не должно быть доступа к файлам/хранилищу серверных секретов; один и тот же OS-пользователь без дополнительной изоляции этого не обеспечивает.

Для Fastkore платформа также вычисляет проверочное значение:
fkap1.<тот же installation_id>.<SHA256 UTF-8 байтов ПОЛНОГО ключа, 64 hex-символа>

Хешировать точную строку ключа без пробелов, перевода строки и BOM. Это проверочное значение, а не ключ: оно не должно приниматься в Authorization. ERP достаточно хранить его; восстанавливать исходный ключ ей не требуется.

Что передаётся администратору Fastkore:
1) BaseUrl Agent Platform, для пилота https://agentic-platform.fastkore.ru/;
2) проверочное значение AgentPlatformKeyVerifier;
3) installation_id для сверки;
4) подтверждённый validate_ticket_url, доступный с сервера платформы.

На стороне ERP BaseUrl остаётся в существующей карточке сервиса. AgentPlatformEnabled и AgentPlatformKeyVerifier — настройки сервера, без нового справочника. В Windows это поля Configuration.xml; в Linux — одноимённые поля серверного JSON. Включение/ротация настроек ERP на первом этапе применяется перезапуском службы, который также уничтожает непогашенные билеты. Обычное поле карточки Service.Secret для этого не используется.

Предлагаемые административные API платформы:
GET /api/admin/fastkore/installations — метаданные без ключа и secret_ref;
POST /api/admin/fastkore/installations — name, validateTicketUrl; ответ installationId, connectionKey, erpKeyVerifier; no-store;
PATCH /api/admin/fastkore/installations/:installationId — состояние и метаданные;
POST /api/admin/fastkore/installations/:installationId/rotate-key — новый connectionKey и erpKeyVerifier, показанные однократно.

Разрешать эти операции только role=admin и source=local. При смене validate URL сначала отключить подключение и потребовать явное подтверждение нового адреса администратором. Ротация сохраняет installation_id, немедленно отзывает прежние SSO credentials платформы; новый ключ начинает проверяться ERP после применения её настроек. В переходный период допустим отказ входа, но не одновременное неограниченное действие двух ключей.

4. ПОДГОТОВКА ВХОДА В WEBVIEW2

Fastkore открывает верхнеуровневую страницу:
GET /auth/fastkore/start?theme=dark
или:
GET /auth/fastkore/start?theme=light

Платформа создаёт попытку входа на 120 секунд:
- отдельная случайная cookie __Host-bridge_sso_start: Secure, HttpOnly, SameSite=Lax, Path=/, без Domain;
- независимый login_challenge: 32 случайных байта Base64URL без padding, 43 символа;
- привязка cookie, challenge, срока и выбранной темы; ограниченный серверный буфер попыток.

Страница применяет тему сразу и отправляет в WPF:
window.chrome.webview.postMessage({
  type: "fastkore.sso.challenge",
  version: 1,
  login_challenge: "<challenge>"
});

Начальная cookie и challenge связывают вход с этим браузером и защищают от подстановки билета другого пользователя. Один POST с билетом без этой подготовки недостаточен. Успешная сессия получает новый токен; cookie подготовки не превращается в session cookie.

5. ВЫДАЧА БИЛЕТА И ОБМЕН

WPF вызывает штатный RPC Fastkore CreateAgentPlatformLaunchTicket(loginChallenge) по действующей ERP-сессии через TLS. Платформе не нужно реализовывать HTTP launch-ticket. Пользователя определяет ERP; WPF не выбирает userId и не получает серверный ключ.

Билет: непрозрачное случайное значение из 32 байт, Base64URL без padding, 43 символа. Срок 60 секунд. Однократное погашение. Это не JWT; не пытаться проверять его локально или извлекать из него пользователя.

В том же WebView2 WPF выполняет нативную POST-навигацию:
POST /auth/fastkore/exchange
Content-Type: application/x-www-form-urlencoded
Cookie: __Host-bridge_sso_start=<cookie браузера>

version=1&installation_id=<UUID>&ticket=<билет>&login_challenge=<challenge>

Ровно четыре поля. Тема НЕ добавляется пятым полем обмена: она уже сохранена в подготовке входа. Максимальное тело 4 KiB. Отклонять неизвестные/повторяющиеся поля и неправильные типы/длины. Проверить cookie, срок, challenge и включённость установки, затем атомарно зарезервировать попытку. Два параллельных обмена не должны создавать две сессии.

Если Origin присутствует, он должен точно равняться BRIDGE_PUBLIC_ORIGIN. Отсутствующий Origin допустим только здесь для нативного POST при успешной проверке cookie/challenge; это не исключение для обычных API.

6. СЕРВЕРНАЯ ПРОВЕРКА БИЛЕТА

Agent Platform обращается к заранее зарегистрированному validate_ticket_url. Ни URL ERP, ни ключ не берутся из браузерного запроса.

POST https://<ERP-сервер>:<TLS-порт>/api/ai/validate-ticket
Authorization: Bearer fkap1.<installation_id>.<секрет>
Content-Type: application/json
Accept: application/json

{
  "version": 1,
  "installation_id": "<UUID>",
  "ticket": "<билет>",
  "audience": "fastkore-agent-platform",
  "login_challenge": "<challenge>"
}

Endpoint ERP размещается в существующем TLS-хосте сервера, а не в открытом /info/. Если используется reverse proxy, соединение proxy -> ERP также должно быть HTTPS. Проверка сертификата обязательна. Для собственного CA Fastkore добавить его в доверие HTTP-клиента платформы; не отключать TLS-проверку.

Общий timeout 10 секунд, ответ максимум 8 KiB, redirect запрещены, автоматические повторы проверки запрещены. Администратор может явно зарегистрировать внутренний адрес ERP. Запросы не должны позволять браузеру выбирать другой хост/порт/путь.

Успех — HTTP 200:
{
  "version": 1,
  "valid": true,
  "installation_id": "<UUID>",
  "audience": "fastkore-agent-platform",
  "user": { "id": "<GUID пользователя ERP>", "display_name": "Иван Иванов" }
}

Платформа строго сверяет version, valid, installation_id, audience, формат user.id. UUID — стандартные строки с дефисами в нижнем регистре. display_name — отображаемая строка до 200 символов, не ключ поиска. Права, пароль или токены ERP из ответа не выводятся.

Отказы ERP: 400 invalid_request/invalid_ticket; 401 invalid_server_credentials; 403 integration_disabled/access_denied/https_required; 408 request_timeout; 429 rate_limited; 503 temporarily_unavailable. JSON: { "error": "безопасный текст", "code": "машинный код" }.

После timeout, ошибки сохранения или неопределённого результата прежний билет не повторять. Начать новую подготовку и получить новый билет. Нельзя на основании сетевой ошибки выдавать локальную сессию или переключаться на парольный вход сотрудника.

7. ПОЛЬЗОВАТЕЛЬ, СЕССИЯ И ПРАВА

Личность определяется парой (installation_id, user.id). Использовать existing external_identities с её PRIMARY KEY. Не связывать аккаунты по логину, имени или email. Для сохранения истории старого аккаунта разрешить только явную административную привязку.

Первый вход: создать одного пользователя с role=employee и roleId=sso_pending. Эта рабочая роль enabled=true с пустыми profileIds, operationIds, readDatasetIds, без проектов. Стандартный roleId=employee сейчас уже даёт universal/chat, поэтому не использовать его как роль без прав. passwordHash пустой; фиктивный пароль не создавать.

Создание пользователя, внешней связи и credential должно сохраняться одной сериализованной операцией Access/Store. При ошибке SQLite не выдавать cookie и не оставлять рабочий credential только в памяти. Повторный вход сохраняет ранее назначенные администратором права и блокировку пользователя.

Переиспользовать Credential: kind=session, source=fastkore, installationId, expiresAt. Срок SSO — 30 минут абсолютного времени. В базе хранить хеш случайного session token.

Set-Cookie: __Host-bridge_session=<token>; Secure; HttpOnly; SameSite=Lax; Path=/
Domain отсутствует, срок cookie ограничен сроком credential.

После успешного сохранения удалить pre-auth cookie и ответить:
HTTP 303
Location: /?embedded=fastkore&theme=dark
либо theme=light — из сохранённой попытки входа, строго по allow-list.

Произвольный returnUrl не принимать. Билет, ключ и session token не попадают в URL, JS, localStorage/sessionStorage или обычный JSON. Тема секретом не является.

GET /api/auth/me сохраняет текущие user/setupRequired и добавляет authentication:
{
  "source": "fastkore",
  "installationId": "<UUID установки>",
  "externalUserId": "<GUID ERP>",
  "expiresAt": "<UTC RFC3339>",
  "csrfToken": "<отдельный CSRF-токен>",
  "canChangePassword": false,
  "canCreateApiKey": false
}

user.id остаётся ID пользователя ПЛАТФОРМЫ. Это не externalUserId.

Встроенный клиент начинает с cookie-only /api/auth/me. Старый bridge-key не подставлять. При успешном SSO очистить старый bridge-key и состояние прежнего пользователя: чаты, проекты, вложения, черновики. Поздние ответы старых запросов не должны восстанавливать прежнее состояние.

Все изменяющие cookie API требуют точный Origin и X-CSRF-Token, включая logout и multipart. Cookie плюс Authorization одновременно отклонять как ambiguous_credentials. SSO credential не принимать через Bearer. Повторная principal(request) после await должна проверять тот же выбранный носитель, пользователя, срок и состояние установки.

Парольный вход разрешён только локальным администраторам. Старые локальные session/API credentials обычных сотрудников отозвать, в том числе для очереди. Для source=fastkore запретить смену пароля и создание API-ключей НА СЕРВЕРЕ независимо от role и видимости кнопок. Локальный администратор сохраняет существующий 12-часовой вход.

После подтверждённого /api/auth/me и применения темы страница отправляет:
{ "type": "fastkore.ready", "version": 1, "installation_id": "<UUID>", "fastkore_user_id": "<GUID ERP>", "theme": "dark" }

WPF сверяет личность с выданным билетом. При 401 встроенная страница отправляет:
{ "type": "fastkore.sso.required", "version": 1, "reason": "session_expired" }

Повтор входа требует новой попытки; бесконечные автоматические циклы запрещены.

8. ТЕМА: ОБЯЗАТЕЛЬНЫЙ КОНТРАКТ FASTKORE -> AGENT PLATFORM

Источник истины — фактическая тема клиента Fastkore:
TelerikThemes.IsDark == true -> "dark";
все остальные темы -> "light".

Внутреннее обозначение тёмной темы Fastkore — TelerikTheme.FluentDark. Не сравнивать русские подписи и не передавать названия Telerik в веб-приложение. При автоматическом выборе в ERP передаётся уже выбранный результат, а не значение "system".

Начальное значение приходит в GET start?theme=light|dark, сохраняется в pre-auth попытке и переносится в фиксированный 303, как указано выше. Применить его до первого отображения start, рабочей страницы и страниц ошибок, чтобы не было белой вспышки при тёмной теме.

Дополнительно Fastkore отправляет в текущий документ через CoreWebView2.PostWebMessageAsJson:
{ "type": "fastkore.ui", "version": 1, "theme": "dark" }
или то же с "light".

Платформа принимает сообщения так:
window.chrome?.webview?.addEventListener("message", event => {
  const message = event.data;
  if (!message || message.type !== "fastkore.ui" || message.version !== 1) return;
  if (message.theme !== "light" && message.theme !== "dark") return;
  // Подключить существующий механизм темы React/CSS, не только фон страницы.
  applyEmbeddedTheme(message.theme);
  window.chrome.webview.postMessage({
    type: "fastkore.ui.applied", version: 1, theme: message.theme
  });
});

Это иллюстрация контракта, applyEmbeddedTheme требуется реализовать в принятой архитектуре интерфейса. Обработчик зарегистрировать до fastkore.ready; события принимать без eval, HTML-вставок и выполнения переданного кода. Не смешивать этот канал с window.postMessage сторонних iframe.

Применение охватывает весь интерфейс: фон, текст, поля ввода, чаты, боковые панели, модальные окна, ошибки, код и прокрутку. Установить также CSS color-scheme. Последнее корректное сообщение хоста имеет приоритет над theme URL. Не перезагружать приложение, не очищать чат и не выполнять повторный SSO при смене темы.

Fastkore передаёт тему при загрузке документа и повторном раскрытии окна. Если применённая тема ERP изменяется без перезапуска, новое сообщение меняет её на лету; если ERP применяет настройку только после перезапуска, новое значение приходит при следующем запуске окна. Наличие live-переключения всей ERP не является требованием к этому этапу.

Тема действует только в данном встроенном окне. Не менять глобальную настройку аккаунта, localStorage обычного браузера или тему других пользователей. Для восстановления при Reload допускается сохранить только light/dark в sessionStorage этого окна. Вне режима embedded=fastkore сохраняется обычное поведение сайта.

В embedded-режиме скрыть/заблокировать собственный переключатель темы с пояснением «Тема задаётся в Fastkore». При отсутствующем/неверном значении использовать light до корректного сообщения хоста. Ни theme, ни embedded, ни наличие chrome.webview не являются доказательством авторизации.

9. ВЫХОД, ОТЗЫВ И ОЧЕРЕДЬ

Переиспользовать POST /api/auth/logout: проверить CSRF, отозвать credential, удалить cookie с теми же атрибутами. Fastkore закрывает приватные экземпляры WebView2 при закрытии/смене ERP-соединения; сворачивание окна не является logout.

Отключение установки платформой, блокировка пользователя, expiry или logout должны учитываться HTTP API и текущими проверками Job.credentialId. В нынешней реализации задания при expiry/отзыве прекращаются. Новый вход не перепривязывает старые задания и не повторяет внешние действия автоматически.

Блокировка только в ERP обнаруживается при следующей выдаче/погашении билета. Уже выданная cookie может жить до 30 минут. Немедленный межсистемный отзыв — отдельное расширение, его в этом этапе не обещаем. Аналогично при недоставленном logout серверный credential живёт до TTL.

10. ЗАЩИТА И ПРИЁМКА

На /auth/* явно добавить no-store, безопасные заголовки, ограничения размера и частоты: текущая ветка onRequest обрабатывает только /api/*. Не ослаблять CSP/frame-ancestors ради WebView2: это верхнеуровневое окно, не iframe. BRIDGE_PUBLIC_ORIGIN задаётся сервером, не заголовками произвольного клиента.

Не журналировать билеты, challenge, cookie, ключи, Authorization и тела auth-запросов. Дополнить существующий redact и настройки reverse proxy. Не принимать redirect при проверке ERP; WPF не должен переносить POST билета на другой origin. Если перед сайтом BasicAuth, согласовать его отдельно: SSO cookie не отменяет пароль reverse proxy.

Обязательные совместные проверки:
1) Обычный пользователь входит без пароля; администратор платформы сохраняет локальный вход.
2) Повтор/просрочка билета, чужая cookie/challenge, неверный ключ/installation/audience отклоняются; при двух параллельных погашениях только один успех.
3) Подставленный билет другого пользователя не авторизует чужой WebView2.
4) Ошибка ERP, timeout, 3xx, неверный JSON и ошибка SQLite не создают сессию; повтор использует новый билет.
5) Автосоздание не даёт проектов/прав, совпавшее имя не объединяет аккаунты, параллельный первый вход не создаёт дубликаты.
6) SSO не позволяет создать API-ключ/пароль; старый локальный ключ сотрудника не обходит запрет; cookie API защищены CSRF.
7) Выход/смена пользователя ERP не показывают следующему пользователю чужие чаты; сворачивание сохраняет текущий интерфейс.
8) Ротация ключа/отключение установки и expiry учитываются очередью; старые задания не перезапускаются.
9) В тёмной ERP start, чат, модальные окна и ошибки тёмные с первого показа; все прочие темы ERP дают light. Повторное раскрытие/Reload и fastkore.ui корректно восстанавливают тему без нового входа. Обычный браузер сохраняет свою тему.
10) Проверить настоящий WebView2 с POST-навигацией, cookie и 303, а не только HTTP mocks. Убедиться, что секреты отсутствуют в логах и JS-хранилищах.

11. ЧТО НЕ ВХОДИТ В ЭТОТ ЭТАП

Персональная авторизация CLI/MCP от имени пользователя ERP — второй этап. Не выпускать сейчас бессрочные ключи пользователей и не передавать ERP-пароли модели.

Цель второго этапа: CLI/MCP получают серверно подтверждённые ограниченные полномочия и обычную ERP-сессию соответствующего пользователя. Все операции выполняются стандартными методами Fastkore с его правами. Авторство изменений и действий фиксирует ШТАТНЫЙ журнал Fastkore в пределах существующего покрытия журналирования. Отдельный параллельный журнал и подстановка имени в текст лога не нужны. Детальный протокол делегирования и дополнительная отметка вызова агентом будут отдельным ТЗ.
